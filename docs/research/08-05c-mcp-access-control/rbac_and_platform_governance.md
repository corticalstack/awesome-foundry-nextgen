# Azure RBAC and Foundry / Entra platform governance as controls over which news categories a Foundry agent may read from a third-party MCP server

State as of 29 October 2026. Scenario: two Microsoft Foundry agents in the same project; agent A may see all news categories on a third-party remote news MCP server, agent B only a subset. Question: can this be done off the shelf (RBAC, agent identity, or another platform mechanism) with no custom code?

Short answer (details and sources below): No platform mechanism enforces category-level (argument-level) restrictions on a third-party MCP server without code somewhere. Azure RBAC cannot express or evaluate permissions on a non-Azure API. The closest off-the-shelf pieces are (1) per-agent `allowed_tools` on the agent's MCP tool definition (tool-level, developer-controlled, not admin-enforced), (2) Azure Policy's preview "approved tools" built-in (endpoint-level, uniform across every agent at the assigned scope, no per-agent exemption), (3) per-agent Entra agent identities plus Conditional Access or app roles (identifies the agent; CA gives all-or-nothing per resource; app roles need the server to read the `roles` claim), and (4) hosted-agent egress controls (host-level only, preview). Category enforcement always ends up in the MCP server, a gateway policy, or a wrapper.

## Key question 1: What Azure RBAC can and cannot authorize; custom roles; the checkAccess API

### Takeaway
Azure RBAC authorizes operations on Azure resources only. Role definitions are built from resource-provider operation strings, data actions must be flagged `isDataAction` by a registered resource provider, and evaluation happens in Azure Resource Manager or in an RBAC-integrated Azure data plane. A third-party news MCP server is none of these, so no RBAC role can carry a "news category" permission, and nothing evaluates RBAC for that server unless the server itself queries Azure. There is no publicly documented `checkAccess` REST operation; the documented alternatives (`permissions/read`, role assignment listing) would require the server to run Azure-aware custom code.

### Cited Findings
- Azure RBAC "is an authorization system built on Azure Resource Manager that provides fine-grained access management to Azure resources." A role assignment is security principal + role definition + scope. Scope levels are management group, subscription, resource group, resource. [Azure RBAC overview](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview)
- Evaluation flow: the principal "acquires a token for Azure Resource Manager", calls ARM, ARM retrieves role and deny assignments for the resource, checks Actions/NotActions and DataActions/NotDataActions, then evaluates conditions. "These steps apply to Azure Resource Manager or data plane services integrated with Azure RBAC." [Azure RBAC overview](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview)
- Action strings have the format `{Company}.{ProviderName}/{resourceType}/{action}`; `Actions` "is a collection of strings that identify securable actions of Azure resource providers." [Understand Azure role definitions](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-definitions)
- "Only data plane actions can be added to the DataActions and NotDataActions properties. Resource providers identify which actions are data actions, by setting the isDataAction property to true." "Authorization for all control plane API calls is handled by Azure Resource Manager. Authorization for data plane API calls is handled by either a resource provider or Azure Resource Manager." "Each resource provider provides its respective set of APIs to fulfill data actions." [Understand Azure role definitions](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-definitions)
- Custom roles: you "determine the resource providers that map to the Azure services" and "search the available permissions" (the resource provider operations list). Limits: 5,000 custom roles per tenant; no wildcard or root in AssignableScopes; one wildcard per action string; custom roles with DataActions cannot be assigned at management group scope. [Azure custom roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles)
- Role assignment conditions exist (`Condition`, `ConditionVersion` 2.0) in role definitions and assignments; ARM evaluates conditions after the action match. [Understand Azure role definitions](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-definitions); [Azure RBAC overview](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview)
- The Microsoft.Authorization resource provider operations list contains no `checkAccess` operation. It does contain `Microsoft.Authorization/permissions/read` ("Lists all the permissions the caller has at a given scope") and `Microsoft.Authorization/roleAssignments/read`. [Azure permissions for Management and governance](https://learn.microsoft.com/en-us/azure/role-based-access-control/permissions/management-and-governance)
- The portal "Check access" feature lists a principal's role and deny assignments at a scope; the page documents only the Azure portal, no REST or CLI equivalent. [Check access for a user to a single Azure resource](https://learn.microsoft.com/en-us/azure/role-based-access-control/check-access)
- The only official mention of a `checkAccess` call is the Azure Arc-enabled Kubernetes RBAC design: the guard webhook "makes a checkAccess call on the authorization service in Azure to see if the requesting Microsoft Entra entity has access to the resource of concern", returning allowed or denied. This is Microsoft's own component acting against Azure resource scopes. [Azure RBAC on Azure Arc-enabled Kubernetes](https://learn.microsoft.com/en-us/azure/azure-arc/kubernetes/conceptual-azure-rbac)
- The documented, supported way for software to answer "what does principal X hold at scope Y" is the role assignments REST API with the `assignedTo('{objectId}')` filter (api-version 2022-04-01, first stable). [List Azure role assignments using the REST API](https://learn.microsoft.com/azure/role-based-access-control/role-assignments-list-rest); [API versions of Azure RBAC REST APIs](https://learn.microsoft.com/rest/api/authorization/versions)
- Foundry's own custom-role example uses the data action `Microsoft.CognitiveServices/accounts/AIServices/agents/*`; the VNet guide states the minimum Foundry User data permissions are `agents/*/read`, `agents/*/action`, and `agents/*/delete`. These govern agent CRUD and invocation inside Foundry, not downstream tools. [Role-based access control for Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/concepts/rbac-foundry); [Set up private networking for Foundry Agent Service](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/virtual-networks)

### Inferences
- A custom role cannot define a data action such as `Contoso.News/categories/sports/read`: the string must name a registered Azure resource provider operation with `isDataAction` set by that provider. A third-party MCP server is not a resource provider. (Direct consequence of the role-definitions page.)
- Even if an organization created a "news category" custom role by reusing some unrelated Azure operation on a placeholder resource (for example a resource group per category), nothing in Azure would enforce it on the MCP server. The server would have to authenticate the caller with an Entra token, extract the caller's object ID, call the role assignments list API (or `permissions/read` as the caller), map the result to categories, and filter. That is custom code on the server, and it abuses RBAC semantics; it is not an off-the-shelf control.
- The undocumented `checkaccess` endpoint used by the portal and by Arc guard is not a supported public API: no REST reference exists, no operation string exists, and no SDK method was found. Building a third-party entitlement check on it is not sensible.
- RBAC can identify a specific agent as the principal (see question 2), but that only matters for Azure resources.

### Gaps
- I could not retrieve a public specification for `Microsoft.Authorization/checkaccess` (request shape, api-version). Searches of Learn and REST version listings returned nothing; a PowerShell module that search results suggested contained it did not. Treat it as undocumented.
- I did not fetch the full Microsoft.CognitiveServices data-action list to prove there is no tool-level data action; the Foundry docs show only `agents/*`-level actions. Stated as inference.
- I did not verify the "Permissions - List For Resource" REST page URL this session; the operation `Microsoft.Authorization/permissions/read` is confirmed, the REST page is not.

## Key question 2: Can an Azure RBAC role assignment target a Foundry agent identity?

### Takeaway
Yes. Each newly created Foundry agent gets its own Entra agent identity (a special service principal under an agent identity blueprint), and Azure RBAC roles are assigned to it by object ID with `--assignee-principal-type ServicePrincipal`. This proves the platform can distinguish two agents in one project at the identity layer. It does not make RBAC apply to a third-party server.

### Cited Findings
- "An agent identity is a special service principal in Microsoft Entra ID, created under an agent blueprint. It represents an agent instance when it accesses downstream resources." "In the current agent object model, creating an agent provisions a unique agent blueprint and the identity for its default instance." "A newly created agent identity starts without resource permissions." [Agent identity concepts in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity) (ms.date 2026-10-28)
- "For Azure RBAC assignment procedures, use the object ID of the agent identity used for the tool call as the assignee." Authorization mechanisms listed: Azure RBAC, service-specific data-plane roles, application permissions or app roles, resource-specific authorization policies. [Agent identity concepts in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- "Per-agent identities let you scope permissions and audit activity to individual agents. Legacy agents that share a project identity don't have that identity-level separation." The shared project identity remains for legacy agents. [Agent identity concepts in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Entra: agent identities can hold "Microsoft Graph permissions, Azure RBAC roles, Microsoft Entra directory roles, Microsoft Entra app roles, and more." [What are agent identities?](https://learn.microsoft.com/en-us/entra/agent-id/what-are-agent-identities)
- Entra guidance: "If an agent needs to access Azure resources: Assign Azure roles for those specific resources." [Authorization in Microsoft Entra Agent ID](https://learn.microsoft.com/en-us/entra/agent-id/authorization-agent-id)
- Runtime token exchange for agent-identity tool auth: blueprint credential -> agent identity token -> scoped token for the downstream audience -> "Agent Service passes the scoped access token to the MCP server or A2A endpoint. The downstream resource validates the token and checks the agent identity's RBAC role assignments before granting or denying access." "Authentication to that resource doesn't itself grant access." [Agent identity concepts in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- MCP auth types: "Microsoft Entra - agent identity" ("ideal when you have multiple agents that need different levels of access to the same MCP server"), "Microsoft Entra - project managed identity" ("when you want all agents in a project to share the same access level"), key-based, Entra client user delegation, OAuth identity passthrough, unauthenticated. Agent identity connection is created with `azd ai connection create ... --auth-type agentic-identity --audience "<entra-audience>"`. [Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication) (ms.date 2026-09-29)
- The ID Governance page describes the older model ("agents in the project authenticate by using the shared project's agent identity" until published); the Foundry agent-identity page (newer) says every new agent gets its own identity at creation. [Governing Agent Identities](https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview); contradicted in detail by [Agent identity concepts in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)

### Inferences
- For the scenario, the per-agent identity is the one platform primitive that lets a third-party server tell agent A from agent B, provided the server accepts Entra tokens for an audience you control and the MCP connection uses `agentic-identity`. The server still has to implement the category filter.
- The sentence "checks the agent identity's RBAC role assignments" applies to Azure services (the example is Azure Storage). For a non-Azure server, the server checks whatever it implements (app roles, its own ACL).

### Gaps
- Whether legacy-model projects in the user's environment still use the shared project identity depends on when the agents were created; migration changes the identity and role assignments do not transfer (documented on the agent-identity page).

## Key question 3: Foundry built-in roles, and whether any governs which tools or MCP servers an agent may call

### Takeaway
Five Foundry roles exist (Foundry Agent Consumer, Foundry User, Foundry Project Manager, Foundry Account Owner, Foundry Owner; four of them renamed from "Azure AI ..." with unchanged IDs). They control who can build, manage, publish, and call agents. None restricts which tools or MCP servers an agent can call. Agent-scope role assignments exist but are evaluated only for inbound endpoint access.

### Cited Findings
- Role table and IDs: Foundry Agent Consumer `eed3b665-ab3a-47b6-8f48-c9382fb1dad6` ("interact with agent endpoints ... least-privilege"), Foundry User `53ca6127-db72-4b80-b1b0-d745d6d5456d`, Foundry Project Manager `eadc314b-1a2d-4efa-be10-5d325db5065e`, Foundry Account Owner `e47c6f54-e4a2-4754-9501-8e0985b135e1`, Foundry Owner `c883944f-8b7b-4483-af10-35834be79c4a`. The role IDs and core permissions are unchanged by the rename." [Role-based access control for Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/concepts/rbac-foundry) (ms.date 2026-09-16)
- Permission matrix columns are: create projects, create accounts, build and develop (data actions), complete role assignments, reader access, manage models, publish agents, interact with agent endpoints. No column or row concerns tool or MCP invocation. [Role-based access control for Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/concepts/rbac-foundry)
- "Don't use the Azure AI Developer role for Foundry work. Despite the name, this role is scoped to Azure Machine Learning workspaces and Foundry hubs." No "Foundry Developer" role is listed. - Toolbox access: grant "the Foundry User role on the Foundry project to each identity" that consumes the toolbox (agent identity, hosted agent identity, end user for OAuth flows). [Create and manage a toolbox in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/toolbox) (ms.date 2026-10-26)

- OAuth identity passthrough for MCP needs end users to hold at least Foundry Agent Consumer on the project. [Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- RBAC applies only with Entra authentication; "If you use key-based authentication instead, the key grants full access without role restrictions." [Role-based access control for Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/concepts/rbac-foundry)

### Inferences
- Foundry roles answer "who may call or edit agent X", not "what may agent X call". A Foundry User who can edit agent B's definition can also remove or widen its `allowed_tools`, so the agent definition is not an admin-enforced boundary unless Azure Policy (question 4) constrains it.
- Agent-scope RBAC is the inbound mirror of the question: useful for restricting which clients can invoke agent A vs B, useless for restricting outbound tool access.

It concerns inbound session isolation, not tool access.

## Key question 4: Foundry platform tool governance (allow-lists, Azure Policy, tool catalog, toolboxes, AI gateway, Control Plane, Agent 365, Defender, Purview, guardrails, egress controls)

### Takeaway
As of October 2026 the platform offers: a per-agent `allowed_tools` and `require_approval` setting on the MCP tool (tool-level, developer-set); two preview Azure Policy built-ins that allow- or deny-list tool types, MCP endpoint URLs (wildcards) and MCP connectors for agents and toolboxes (endpoint-level, uniform across the assigned scope, no per-agent exemption); toolboxes (GA June 2026) with a centrally managed tool list, `allowed_tools` filtering and content-safety guardrails; an API Center-backed private tool catalog (preview, discovery only); an APIM AI gateway for MCP tools (preview; rate limits, IP filters, header and routing policies); Foundry Control Plane (preview; inventory, guardrail policies for model deployments, Defender and Purview surfaces); hosted-agent network egress controls (preview; host-level allow/deny/transform/rewrite per agent version). None enforces category-level restrictions on a third-party server without custom logic.

### Inferences
- `allowed_tools` is the only built-in per-agent, tool-level restriction. It is a property of the agent definition, so anyone with Foundry User on the project can change it, and it cannot express "category X only" unless the MCP server exposes one tool per category (server-side design choice).
- The Azure Policy built-ins are the only admin-enforced, platform-level control, and they apply uniformly to every agent and toolbox under the assignment scope (subscription, resource group, or Foundry account resource). Because both agents live in the same project, and RP-mode policies do not support component-level exemptions and only support built-in definitions, you cannot write a policy that allows endpoint E for agent A but not agent B, and you cannot write a custom data-plane policy that inspects tool arguments. The `serverUrl` wildcard could separate categories only if the third-party server published distinct endpoint URLs per category, and even then the rule would bind all agents at that scope the same way.
- Toolboxes let you build two toolboxes (one full, one with `allowed_tools` trimmed) and point each agent at one of them. That distinguishes agents by configuration, not by enforcement; the agent author chooses the toolbox, and the toolbox guardrail is content filtering, not an ACL. An admin could combine Azure Policy `approvedMcpEndpoints` set to toolbox URLs only, forcing all agents through toolboxes, but still could not pin agent B to the trimmed one.
- The APIM AI gateway can inspect the JSON-RPC body (tool name, arguments) with policy expressions and block or rewrite calls; that is a configuration artifact rather than application code, but it is custom policy logic. Distinguishing agents at the gateway requires the request to carry an agent-identifying credential (agent identity bearer token readable with `validate-jwt`, or a transform-injected header). The doc's IP-filter and rate-limit examples key on client IP, which is shared (see question 6).
- Egress controls could, in principle, give agent B a transform rule that injects a category-scoped API key header for the news server while agent A gets a full-scope key; the policy is per hosted-agent version, so it distinguishes agents. The categories would still be enforced by the news server's key scoping. Hosted agents only, preview, no production SLA.
- Control Plane, Defender and Purview observe and alert; none of them is an authorization point for tool calls. Purview DLP enforcement is limited to user-context chat completions and needs app integration.

### Gaps

- The denied-tools policy JSON was not fetched; it is assumed to mirror the approved-tools structure.

## Key question 5: Microsoft Entra governance for agent identities (app roles, access packages, Conditional Access, Permissions Management)

### Takeaway
Entra can tell the two agents apart (each has its own agent identity), can assign them different app roles on an Entra-registered API (so the token carries a `roles` claim the server can act on), can gate token issuance per agent and per target resource with Conditional Access, and can manage those grants with access packages and access reviews. Enforcement of what a role means (which categories) is the resource server's job; CA is all-or-nothing per resource; none of it applies if the MCP server authenticates with API keys. Entra agent features need Agent 365 licensing.

### Cited Findings
- App roles: "For applications that recognize role claims on service principals, you can assign an agent's service principal or agent identity to an application's app role ... This results in application permissions." The app role must have `allowedMemberTypes` of `Application`; assignment via admin center, Graph `servicePrincipals/{id}/appRoleAssignedTo`, or PowerShell. [Manage assignment of agent identities to an application](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/assign-agent-identities-to-applications) (ms.date 2025-11-19)
- Agent identities may hold Azure roles, Entra roles (a restricted allow-list; Global Administrator and similar are blocked), Graph permissions (high-risk ones blocked), app role assignments, access package assignments, group memberships; "Custom roles can be assigned to agents." Blueprints support inheritable permissions. [Authorization in Microsoft Entra Agent ID](https://learn.microsoft.com/en-us/entra/agent-id/authorization-agent-id) (ms.date 2026-06-12)
- Foundry's own statement: "Application permissions or app roles: An API grants the identity application-level permissions for access without a signed-in user, where supported." [Agent identity concepts in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Conditional Access for agents: evaluated "whenever Microsoft Entra ID issues or refreshes an access token"; for app-only access "the agent identity is the subject" and policies target the agent identity or its blueprint; "The target resource validates the token and uses its claims to make authorization decisions." Limits: "Conditional Access only protects resources secured by Microsoft Entra ID. For example, if an agent accesses resources using an API key, it bypasses the Microsoft Entra ID authentication and token issuance pipeline entirely and Conditional Access policies won't apply." [Conditional Access for agents in Microsoft Entra](https://learn.microsoft.com/en-us/entra/identity/conditional-access/agent-id) (ms.date 2026-07-31)
- Policy construction: Assignments > "Users, agents or workload identities" > Agents > include All agent identities, exclude selected agent identities or blueprints (enhanced object picker) or select by custom security attributes; Target resources > "All resources (formerly 'All cloud apps')"; Grant > Block; report-only first. Agent risk condition is in preview. Licensing: M365 E7, or Agent 365 plus Entra P1 / M365 E3 (P2 / E5 for risk-based). [Secure autonomous agents with Conditional Access](https://learn.microsoft.com/en-us/entra/identity/conditional-access/policy-autonomous-agents)
- ID Governance: access packages can grant agent identities security group membership, OAuth API permissions (delegated and application, for Graph and applications), and Entra roles; requests by the agent itself, its sponsor, or an admin; expiry with sponsor notifications; lifecycle workflows for sponsor transfer. Licensing: M365 E7 or Agent 365 plus Entra P1 / M365 E3. [Governing Agent Identities](https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview) (ms.date 2026-06-05)
- Foundry agent identities appear in the tenant-wide Entra inventory with Conditional Access, Identity Protection, network access and governance controls available. [Agent identity concepts in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Foundry blocks sending Microsoft-audience tokens to third-party MCP servers under managed OAuth ("Cannot pass Microsoft token to untrusted MCP endpoint"); custom servers must register their own audience. [Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)

### Inferences
- Off-the-shelf pattern that gets closest: register the news MCP server as an Entra application exposing app roles `News.All` and `News.Subset`; assign agent A's identity the first and agent B's the second (direct or via access package); configure each agent's MCP connection with `agentic-identity` and that audience. The token Foundry sends will carry the agent's `roles` claim. The third-party server must validate Entra tokens and filter categories by role; if it is truly third-party and not Entra-aware, this collapses to custom code (a proxy that validates the token and filters).
- Conditional Access can block agent B from ever obtaining a token for the news API (resource-level block) but cannot say "token OK, but only for sports". It gives an identity-level kill switch per agent per resource, nothing finer.
- Entra Permissions Management (CIEM) was not covered by any fetched page in the agent context; it reports and right-sizes permissions, it does not define app-specific categories.

### Gaps
- The Conditional Access target-resource step in the fetched how-to selects "All resources"; the page does not show selecting a single custom API, though the "enhanced object picker" for target resources is mentioned. Per-resource targeting is standard CA behaviour but was not verified for agents this session.
- Entra Permissions Management for agent identities: no source fetched; omitted from the verdict grid beyond this note.

## Key question 6: Network-level controls (private endpoints, managed or BYO VNet, IP allow-lists) and why they cannot distinguish two agents in one project

### Takeaway
Network isolation in Foundry Agent Service is configured per Foundry account and shared by every project and agent in it; all tool calls from prompt agents in a project leave through one single-tenant data proxy, and hosted-agent tool calls also route through that proxy. A server-side IP allow-list therefore sees the project (or account), never the agent. Private endpoints secure the Azure side and do not reach a third-party server. The only network-adjacent per-agent control is the hosted-agent egress policy (host-level, preview).

### Cited Findings
- "Single-tenant data proxy: A platform-managed networking component dedicated to your Foundry project that handles outbound connectivity for your agents. Each project gets its own isolated data proxy instance. All tool calls route through the data proxy." "Prompt agents use the single-tenant data proxy for all outbound connectivity. IPs are allocated at the project level, so all prompt agents within a project share the same data proxy infrastructure." For hosted agents: "Even though the Micro VM has its own NIC, any tool invocation is routed through the data proxy." [Deep dive into Foundry Agent Service networking](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agents-networking-deep-dive) (ms.date 2026-09-07)
- "Subnet configuration applies at the Foundry account level. All projects in the account share the same subnet configuration, and hosted and prompt agents share the same delegated subnet." "The agent subnet can't be shared by multiple Foundry resources." [Deep dive into Foundry Agent Service networking](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agents-networking-deep-dive); [Set up private networking for Foundry Agent Service](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/virtual-networks)
- Standard Setup with private networking: "No public egress", delegated subnet injection, private endpoints for Storage, Cosmos DB, AI Search and the Foundry account; optional Azure Firewall with required FQDN allow-list; "The deployed agent endpoint URL stays publicly addressable" for azd hosted agents in this preview. [Set up private networking for Foundry Agent Service](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/virtual-networks) (ms.date 2026-06-15)
- Private MCP servers can be hosted inside the VNet on a dedicated MCP subnet; unauthenticated access is suggested only for "private MCP servers within your virtual network that rely on network-level isolation". [Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- APIM gateway `ip-filter` policy allows requests "from only trusted networks" (network ranges, not agents). [Govern MCP tools by using an AI gateway](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/governance)
- Azure Policy built-ins "Azure AI Services resources should restrict network access" and "...should use Azure Private Link" apply to the Foundry account's inbound network ACLs. [Built-in policy definitions for Foundry Tools](https://learn.microsoft.com/en-us/azure/ai-services/policy-reference)

### Inferences
- With BYO VNet plus a NAT gateway or Azure Firewall, the third-party server sees one or a few egress IPs for the whole Foundry account; two agents in one project are indistinguishable by source address. Without BYO VNet, egress comes from Microsoft-managed addresses with the same property.
- Azure Firewall or NSG rules on the delegated subnet can block a destination FQDN for everyone in the account, never for one agent.
- Private endpoints are irrelevant to a public third-party MCP server; they only make Azure resources reachable privately.

### Gaps
- No page states a documented static outbound IP for non-BYO-VNet Agent Service egress; this was not researched further because the conclusion (shared egress) holds either way.

## Key question 7: Verdict grid

### Takeaway
No single mechanism satisfies "identifies the agent" and "enforces category-level" without custom code. The identity layer (per-agent Entra agent identity with app roles or Conditional Access) is the only platform piece that both distinguishes the two agents and is admin-controlled, and it still needs the server (or a proxy) to enforce the category rule.

### Inferences
- Minimal-code answer for the stated scenario: give each agent its own Entra identity (default for new agents), register the news MCP server (or a thin proxy in front of it) as an Entra API with two app roles, assign roles per agent, and have the server or proxy filter categories from the `roles` claim. Everything except the filter is off the shelf; the filter is code.
- If the third-party server cannot validate Entra tokens, the enforcement point must be a gateway (APIM policy or a proxy) or distinct server endpoints per category combined with per-agent `allowed_tools` and an Azure Policy endpoint allow-list to stop agent authors from adding the wider endpoint. Even then the policy cannot differ between agents in one project, so separating the agents into different projects (or accounts) is the only way to get admin-enforced, per-agent endpoint allow-lists from Azure Policy.
