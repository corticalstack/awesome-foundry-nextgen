# Agent identity solves identification, not enforcement

Azure RBAC cannot restrict which news categories a Microsoft Foundry agent reads from a third-party MCP server. RBAC authorizes operations on Azure resources, its role definitions are built from resource-provider operation strings, and Azure Resource Manager or an RBAC-integrated Azure data plane evaluates it; a news server is none of those, so no role can name a category and nothing evaluates one ([Azure RBAC overview](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview)). What Foundry gives you off the shelf is identification. **Every agent created in the current object model gets its own Microsoft Entra agent identity** (Entra Agent ID reached general availability in May 2026), and an MCP project connection with the `agentic-identity` auth type makes Foundry send that agent's app-only token to the server, carrying `appid`/`azp`, `oid` and a `roles` claim that you populate by assigning Entra app roles to each agent identity. Microsoft's own guidance calls this method "ideal when you have multiple agents that need different levels of access to the same MCP server" ([Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)). Neither Foundry nor Entra enforces what a role means. Enforcement happens wherever the token is validated: in the third-party server's code when it can validate Entra tokens, or in a gateway such as Azure API Management (pass-through MCP servers in APIM have been GA since November 2025) when the server cannot change. Foundry's only per-agent control, `allowed_tools`, filters by tool name, lives in the agent definition where any Foundry User can edit it, and never reaches the server. The tool shape therefore sets the floor: with one tool per category, `allowed_tools` plus a tool-name check at the server or gateway is enough; with a single tool and a `category` argument, only code that reads the argument (a server handler or an APIM policy expression) can enforce the restriction. The recommendation is agent identity plus app roles plus a small role-to-category check in the server when the server validates Entra tokens, and an APIM pass-through MCP server with a JWT-validating, body-inspecting policy (or per-agent vendor credentials, if the vendor's entitlement model already covers categories) when the server cannot be modified.

## RBAC names the agent but cannot name a news category

Azure RBAC is "an authorization system built on Azure Resource Manager that provides fine-grained access management to Azure resources"; a role assignment is a principal plus a role definition plus a scope, and scopes are management group, subscription, resource group or resource ([Azure RBAC overview](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview)). Action strings take the form `{Company}.{ProviderName}/{resourceType}/{action}`, and "Only data plane actions can be added to the DataActions and NotDataActions properties. Resource providers identify which actions are data actions, by setting the isDataAction property to true" ([Understand Azure role definitions](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-definitions)). A custom role therefore cannot carry `Contoso.News/categories/sports/read`: the string must name a registered resource provider operation, and a third-party MCP server is not a resource provider. Even if you misused an unrelated Azure operation as a marker, nothing would evaluate it, because the evaluation steps "apply to Azure Resource Manager or data plane services integrated with Azure RBAC" ([Azure RBAC overview](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview)). The Microsoft.Authorization operations list contains `permissions/read` and `roleAssignments/read` but no public `checkAccess` operation ([Azure permissions for Management and governance](https://learn.microsoft.com/en-us/azure/role-based-access-control/permissions/management-and-governance)). A server that wanted to consume RBAC would have to authenticate the agent, read its role assignments through the Role Assignments REST API with the `assignedTo('{objectId}')` filter ([List Azure role assignments using the REST API](https://learn.microsoft.com/azure/role-based-access-control/role-assignments-list-rest)) and map them to categories itself. That is custom Azure-aware code and an abuse of RBAC semantics, not an off-the-shelf control.

RBAC does answer the identification half. Agent identities "can be assigned Azure RBAC roles and Microsoft Entra built-in roles, the same as standard service principals", while blueprints cannot ([Agent service principals](https://learn.microsoft.com/en-us/entra/agent-id/agent-service-principals)), and Foundry says to "use the object ID of the agent identity used for the tool call as the assignee" ([Agent identity concepts](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)). The same page says the downstream resource "checks the agent identity's RBAC role assignments before granting or denying access", but its example is Azure Storage. For a non-Azure server the check is whatever that server implements, and the Foundry page lists the alternatives explicitly: Azure RBAC, service-specific data-plane roles, "Application permissions or app roles", and resource-specific authorization policies.

The other platform-level governance controls share the same limit. Foundry's five built-in roles (Foundry Agent Consumer, Foundry User, Foundry Project Manager, Foundry Account Owner, Foundry Owner) decide who may build, publish and call agents; the permission matrix has no column for tool or MCP invocation, and agent-scope role assignments are assessed "only for agent endpoint access" ([Role-based access control for Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/concepts/rbac-foundry)). The two Azure Policy built-ins "[Preview]: Microsoft Foundry agents and toolboxes should only use approved tools" and its denied-tools twin (both **1.0.0-preview**, Audit/Deny/Disabled) restrict `tools[*].type`, `tools[*].serverUrl` (wildcard match such as `https://mcp.contoso.com/*`) and `tools[*].connectorId` ([Built-in policy definitions for Foundry Tools](https://learn.microsoft.com/en-us/azure/ai-services/policy-reference); [AllowAgentAndToolboxTools_Audit.json](https://github.com/Azure/azure-policy/blob/master/built-in-policies/policyDefinitions/Cognitive%20Services/AllowAgentAndToolboxTools_Audit.json)). They run in the `Microsoft.CognitiveServices.Data` resource-provider mode, and for RP modes "exemptions are not supported at the component-level" and only built-in definitions are supported ([Azure Policy definition structure basics](https://learn.microsoft.com/en-us/azure/governance/policy/concepts/definition-structure-basics)). A policy therefore applies the same way to every agent under its scope: it cannot allow the news endpoint for Agent A and deny it for Agent B when both live in one project, and it cannot read tool arguments. Putting the agents in different projects or accounts is the only way to get admin-enforced, per-agent endpoint allow-lists from Azure Policy.

Network controls cannot help either. "All tool calls route through the data proxy", "IPs are allocated at the project level, so all prompt agents within a project share the same data proxy infrastructure", and hosted-agent tool calls also go through it ([Deep dive into Foundry Agent Service networking](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agents-networking-deep-dive)). A server-side IP allow-list sees the project, never the agent. Conditional Access for agents can block a specific agent identity from obtaining a token for a specific resource, but it runs at token issuance, decides all-or-nothing per resource, requires Microsoft 365 E7 or an Agent 365 license paired with Entra P1 or Microsoft 365 E3, and "if an agent accesses resources using an API key, it bypasses the Microsoft Entra ID authentication and token issuance pipeline entirely and Conditional Access policies won't apply" ([Conditional Access for agents](https://learn.microsoft.com/en-us/entra/identity/conditional-access/agent-id)). Hosted-agent network egress controls (public preview, "not GA, have no preview SLA, and are not intended for production use") match on destination host per hosted-agent version and can transform outbound headers, with nothing on path or body ([Egress controls for hosted agents](https://devblogs.microsoft.com/foundry/egress-controls-hosted-agent)).

## Every new agent carries an Entra identity that reaches the server as claims

Microsoft Entra Agent ID "is now generally available" per the Entra what's-new page dated 1 May 2026 ([What's new in Agent ID](https://learn.microsoft.com/en-us/entra/agent-id/whats-new-agent-id)). It defines an agent identity blueprint (an application-type object that holds credentials and app roles) and an agent identity, "a special service principal in Microsoft Entra ID" that "doesn't have credentials on its own" and is the subject of tokens ([Overview of agent identities](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities)). Foundry maps one blueprint and one identity onto each agent: "In the current agent object model, creating an agent provisions a unique agent blueprint and the identity for its default instance", and "A newly created agent identity starts without resource permissions. Foundry doesn't automatically assign RBAC roles or other downstream permissions to it" ([Agent identity concepts](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)). The identity belongs to the agent object, not to a version: "The agent's identity, endpoint, and authorization surface stay consistent as its underlying versions evolve", and `GET {endpoint}/agents/{agent_name}?api-version=v1` returns `instance_identity` with `principal_id` and `client_id` plus the blueprint reference ([Configure an agent](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-agent)). Hosted agents get the same kind of identity at deploy time and obtain tokens through a token service that imitates the managed identity endpoint but "doesn't give your code access to the project managed identity"; the optional `client_id` parameter accepts only the current or default instance identity, and for any other value the rule is "Rejected. The caller can't select an arbitrary identity" ([Hosted agent token service reference](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agent-token-service)).

Legacy agents are the exception. "Foundry still provisions a shared agent blueprint and agent identity at the project level. Legacy agents without a unique identity use this shared identity" ([Agent identity concepts](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)); "If instance_identity is null in the response, it's a legacy agent", and "There's currently no way to upgrade a legacy agent to a unique identity in place" ([Migrate agent applications](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/migrate-agent-applications)). Migration mints a new identity and "existing role assignments don't transfer". The Architecture Center baseline (June 2026) still says all agents within a project share one managed identity, which is true only for the legacy model ([Baseline Microsoft Foundry chat architecture](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/architecture/baseline-microsoft-foundry-chat)). A community thread from May 2026 reported a .NET MCP server seeing the caller alternate between an agent-specific identity and the shared project identity, which moderators attributed to publish state ([Q&A: Foundry agent app id keeps changing](https://learn.microsoft.com/en-us/answers/questions/5888036/foundry-agent-app-id-keeps-changing)). Decode a real token before hard-coding either value.

The MCP project connection carries this identity to the server. Foundry documents six MCP authentication methods: key-based, Entra agent identity, Entra project managed identity, Entra client user delegation, OAuth identity passthrough and unauthenticated ([Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)). The agent identity method is a `remote-tool` connection with auth type `agentic-identity` and a required `audience`; project managed identity (`project-managed-identity`) is for "when you want all agents in a project to share the same access level", which is the opposite of the requirement here. At run time Agent Service presents the blueprint's federated credential to Entra, obtains a token for the agent identity, exchanges it for "a new access token scoped to the audience of the downstream service", and "passes the scoped access token to the MCP server"; "The audience identifies the resource that accepts the token, which isn't necessarily the tool endpoint's URL" ([Agent identity concepts](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)). For a custom server the audience must be an app registration you control: "Your custom MCP server must be registered with an audience that you control rather than a known Microsoft audience" ([Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)). Because the identity comes from the agent and not from the connection, **one `agentic-identity` connection can be shared by Agent A and Agent B** and the server still tells them apart.

The token the server receives is app-only: `idtyp` = `app`, `azp` (v2) or `appid` (v1) = the agent identity's application ID, `oid` = its object ID, `roles` = "Permissions granted to the agent identity", `scp` empty, and `xms_par_app_azp` = the blueprint; Microsoft warns that "It isn't recommended to use the parent application ID for authorization decisions, as it would result in widespread access by many agents" ([Token claims reference for agent IDs](https://learn.microsoft.com/en-us/entra/agent-id/agent-token-claims)). The agent identity's object ID and app ID "always have the same value and can be reliably used for authentication and authorization decisions" ([Overview of agent identities](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities)). Downstream validation is signature against the tenant JWKS, issuer, audience and expiry, with `xms_par_app_azp` as the marker that distinguishes an agent token from a plain app-only token ([Validate agent identity tokens in a downstream API](https://learn.microsoft.com/en-us/entra/agent-id/how-to-validate-agent-tokens-downstream-api)).

Per-agent entitlements go into the `roles` claim through app roles. "For applications that recognize role claims on service principals, you can assign an agent's service principal or agent identity to an application's app role"; the role must have `allowedMemberTypes` of `Application`, and the assignment is `POST /servicePrincipals/{resourceSpId}/appRoleAssignedTo` with `principalId` set to the agent identity's object ID ([Manage assignment of agent identities to applications](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/assign-agent-identities-to-applications)). There is no first-class `az` command; the managed-identity guide shows the same Graph call through `az rest` ([Assign a managed identity to an app role](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-to-assign-app-role-managed-identity-cli)). Groups do not substitute: "Group optional claims are only emitted in the JWT for user principals. Service principals aren't included in group optional claims emitted in the JWT" ([Optional claims](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims)), and "if you add a service principal to a group, and then assign an app role to that group, Microsoft Entra ID doesn't add the roles claim to tokens it issues" ([Add app roles and get them from a token](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps)). Role changes also lag, because issued tokens are cached and "any changes to the managed identity's roles can take significant time to process" ([Assign a managed identity to an app role](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-to-assign-app-role-managed-identity-cli)). Microsoft's advice is to use app roles "for stable authorization categories" and keep finer-grained permissions in the application's own authorization data ([Add app roles and get them from a token](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps)); for a handful of news categories, `News.Read.All` plus one `News.Read.<Category>` role each fits well under the 700-definition limit, with the server treating `News.Read.All` as implying the rest. If categories are many or change often, keep a per-caller allow-list keyed on `oid` in the server's own store behind a single gate role.

Status as of October 2026: Agent ID is GA; the Foundry MCP tool page (updated 29 October 2026) and the agent identity method carry no preview banner, while `AgentOnBehalfOfUser`, the `AgentBlueprint` endpoint scheme, long-running MCP operations and the .NET SDK are explicitly preview ([Connect agents to MCP server endpoints](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol); [Configure user delegation for tools](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-user-delegation)). Two cautions. The data-plane connections TypeSpec on GitHub `main` still names the credential type `AgenticIdentityToken_Preview` ([azure-rest-api-specs connections models.tsp](https://github.com/Azure/azure-rest-api-specs/blob/main/specification/ai-foundry/data-plane/Foundry/src/connections/models.tsp)), so the API contract has not dropped the preview suffix even though the docs have. And no Microsoft sample shows a Foundry agent token issued for a custom `api://` audience; the documented examples use Microsoft audiences, so the exact `aud` form and v1-versus-v2 claim names need a test against a real token.

## Foundry's runtime controls stop at the tool name

Foundry has one per-agent tool restriction: `allowed_tools` on the MCP tool definition. "If you omit this value or set it to an empty list (`[]`), the agent can access all tools exposed by the MCP server. To allow only specific tools, provide a nonempty list of their names", and selecting a subset of tools in the portal catalog "is equivalent to specifying an `allowed_tools` list in code" ([Connect agents to MCP server endpoints](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)). The filter matches by name against what the server returns ("make sure the tool name matches what the MCP server exposes"), it is a field in the agent definition and not part of the MCP wire protocol, so **the Foundry runtime enforces it and the server never sees it**. It cannot constrain a tool argument. It is also editable by anyone with Foundry User on the project, the role needed "to create and test agents" ([Connect agents to MCP server endpoints](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)), which makes it prompt hygiene rather than an administrative boundary. `require_approval` (`always` by default, `never`, or per-tool lists) adds a human or client gate per call, surfaced as `mcp_approval_request` output items ([Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)); it can put a reviewer in front of a category argument but does not decide automatically.

Toolboxes package the same idea centrally. A toolbox exposes a curated tool set "through a single MCP-compatible endpoint", each tool inside it carries its own `project_connection_id`, `require_approval` and `allowed_tools`, and the calling agent authenticates to the toolbox with its own Entra identity, which "gates access to the toolbox itself, not the individual tools inside it" ([Toolbox authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-authentication); [Create and manage a toolbox](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/toolbox)). Two toolboxes (full and trimmed) attached to the two agents give a clean configuration split, but access to each toolbox is only the binary Foundry User role on the project, and nothing pins Agent B to the trimmed one. The 2 June 2026 Build post listed toolboxes as public preview ([What's new in Microsoft Foundry, Build 2026](https://devblogs.microsoft.com/foundry/whats-new-in-microsoft-foundry-build-2026/)); Azure update AZ563481 of 30 June 2026 announced general availability ([Azure update AZ563481](https://mc.merill.net/message/AZ563481)).

Credentials in connections can also distinguish agents without any identity. A `custom-keys` connection stores arbitrary headers (`Authorization: Bearer <token>`, `X-API-Key`), the agent references it by `project_connection_id`, and "If you provide different endpoints in the connection versus `server_url`, the endpoint in the connection is used" ([Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)). Two connections with the same target and different keys, one per agent, work with any server that already scopes its keys. The documented weakness is visibility: "People who have access to the project can access an API key stored in a project connection" ([Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)), and nothing stops a developer from pointing Agent B at the full-access connection. The `headers` field on `MCPTool` still exists in `azure-ai-projects` 2.9.0 ([MCPTool class](https://learn.microsoft.com/en-us/python/api/azure-ai-projects/azure.ai.projects.models.mcptool)), but the docs steer to connections "instead of passing them at runtime", and no page says agent-level headers are redacted when the agent definition is read back. OAuth identity passthrough (`OAuth2` connections) identifies the end user, not the agent; two connections with different OAuth client registrations would let the server tell agents apart by client ID, at the cost of a separate consent per user per connection ([Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)), and the method does not survive the Microsoft 365 Copilot or Teams channel, where a reporter's server "received only the project managed identity" ([Q&A: OAuth identity passthrough not supported for Foundry agents published to M365 Copilot](https://learn.microsoft.com/en-us/answers/questions/5839438/oauth-identity-passthrough-not-supported-for-found)). Microsoft's own samples show one connection per agent, and none shows two agents with different credentials to one server.

## A server that validates Entra tokens finishes the job in one handler

The MCP specification gives a server two sanctioned levers. Since the 2026-07-28 revision, the `tools/list` result "MAY vary by the authorization presented on the request - for example, returning only the tools the caller's granted scopes permit - since credentials are per-request input, not connection state" ([MCP Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). For a call the token does not cover, the server "SHOULD return 403" with `WWW-Authenticate: Bearer error="insufficient_scope"`, and "The required scopes may be determined dynamically based on the specific request arguments and context" ([MCP Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). A client-credentials client "MAY attempt the step-up authorization flow or abort the request immediately", so for a Foundry agent a 403 ends the call. The spec defines no scope vocabulary and no per-tool permission model, and its security guidance lists "Treating claimed scopes in token as sufficient without server-side authorization logic" as a common mistake ([MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)). The category decision is always the server's own logic.

Microsoft's guidance for Entra-protected MCP servers is specific: set `requestedAccessTokenVersion: 2`, make the Application ID URI equal the canonical MCP URL so the RFC 8707 `resource` value matches, publish Protected Resource Metadata with the v2.0 authority, validate signature, `iss`, `tid`, `aud` and expiry with a library, then "check that the subject (sub or oid) of the token is authorized for the requested operation using the role (roles) claim"; app roles assigned "to the MCP client's agent identity" mean that "Assigned roles appear in the roles claim of the access token, and your server checks that claim before it runs a tool" ([Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)). An Application ID URI cannot end with a slash, so a client sending a trailing-slash `resource` fails with `AADSTS9010010`; list every URL form clients might send in `identifierUris`.

How much code this takes depends on the stack. The C# SDK copies `HttpContext.User` into the request context, supports `[Authorize(Roles = "...")]` on tools once `AddAuthorizationFilters()` is on, and "For list operations, the filters automatically remove unauthorized items from the results", while unauthorized calls throw an "Access forbidden" exception ([C# SDK Filters](https://csharp.sdk.modelcontextprotocol.io/v1/concepts/filters.html); [C# SDK Identity](https://csharp.sdk.modelcontextprotocol.io/v2/concepts/identity/identity.html)). FastMCP 3 offers component-level `auth=` with any `(AuthContext) -> bool` callable, and a component the caller fails "is hidden from list responses" ([FastMCP v3 Authorization](https://gofastmcp.com/v3/servers/authorization)); its built-in `require_scopes` checks scopes rather than `roles`, so an app-only Entra caller needs a custom check or a verifier that copies `roles` into scopes. The TypeScript SDK v2 adds per-tool `scopeChallenge`, which also accepts a callback that can inspect the request and "returns undefined to continue, or the required scope set to send a 403 before the handler runs", plus a per-request server factory that "can register a different tool set for each caller before any handler runs" ([TypeScript SDK v2 Authorization](https://ts.sdk.modelcontextprotocol.io/v2/serving/authorization)). The Python SDK gives only a global `required_scopes` and `get_access_token()` inside handlers, with no list-filtering primitive and no bundled JWKS verifier ([Python SDK v2 Authorization](https://py.sdk.modelcontextprotocol.io/v2/run/authorization/)); CVE-2026-116684 (27 October 2026) shows what happens when a `TokenVerifier` skips the audience check ([CVE-2026-116684](https://app.opencve.io/cve/CVE-2026-116684)).

For the one-tool-per-category shape this is enough: one role per tool, the SDK filters hide the tools Agent B lacks from `tools/list` and reject direct calls, and Foundry's `allowed_tools` on Agent B removes the same names from the model's view as defence in depth. For the single-tool-with-argument shape, every stack needs an in-handler check: read `roles`, compare with `arguments.category` (or filter the result set when the argument is omitted), and return a tool error or a 403 naming the missing role. A hybrid keeps the single tool but computes the `category` enum in `inputSchema` per caller so the model only sees valid values; the handler must still validate because schemas are advisory. A server that varies `tools/list` by caller should mark the result `cacheScope: "private"`, which the 2026-07-28 revision made required and which "controls whether shared intermediaries may cache the response" ([2026-07-28 Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)), so a gateway cache never serves Agent A's list to Agent B.

Azure Functions' MCP extension does not shortcut this. App Service built-in authentication can allow-list caller app IDs and object IDs, but "MCP server authorization defines access to the server, and it doesn't provide granular control to individual MCP tools" ([Configure MCP server authorization, App Service](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-mcp)); the roles check is code you write, and Foundry's Entra option for Functions-hosted servers "only supports Project managed identity" ([Connect an MCP server on Azure Functions to Foundry Agent Service](https://learn.microsoft.com/en-us/azure/azure-functions/functions-mcp-foundry-tools)), which cannot tell two agents in one project apart. The custom code in this case is small and bounded: the token verifier (library-backed) and the role-to-category check; everything else, from identity creation to role assignment to the connection, is configuration.

## APIM pass-through enforces per agent when the server is frozen

When the vendor's server cannot change, exactly two things can happen upstream. The first is credential separation the server already supports: if the vendor issues keys or OAuth clients with different entitlements, one `custom-keys` (or `OAuth2`) connection per agent carries the matching credential and the vendor enforces. That covers both tool shapes only if the vendor's entitlement model already covers categories, and it inherits the project-wide key visibility described above. The second is an enforcing proxy that terminates the agent's identity and holds the vendor credential. Azure API Management is the Azure-native choice.

APIM's MCP governance, including "proxying and governing external MCP servers", reached general availability on 18 November 2025 "across API Management classic and v2 tiers, including the Developer tier and the Self-hosted Gateway" ([Azure update AZ527626](https://mc.merill.net/message/AZ527626)); the Consumption tier and workspaces are excluded, and for external servers APIM supports tools and resources but not prompts ([MCP server overview](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview); [Expose an existing MCP server](https://learn.microsoft.com/en-us/azure/api-management/expose-existing-mcp-server)). The external server "must conform to MCP version 2025-06-18 or later" over Streamable HTTP or SSE, and a pass-through server "forwards all MCP requests directly to an external MCP backend" with the backend defining the tool surface ([Expose an existing MCP server](https://learn.microsoft.com/en-us/azure/api-management/expose-existing-mcp-server); [Manage MCP servers with the REST API](https://learn.microsoft.com/en-us/azure/api-management/manage-mcp-servers-rest-api)). March 2026 added native OAuth 2.1 for APIM-managed MCP servers and removed the 20-tool limit ([APIM service release 2026-03](https://github.com/Azure/API-Management/releases/tag/release-service-2026-03)); June 2026 made products, versioning, observability and Bicep automation for MCP servers generally available, with Microsoft's own example of one product per copilot ([Productize, observe, version and automate MCP servers in APIM](https://techcommunity.microsoft.com/blog/integrationsonazureblog/productize-observe-version-and-automate-mcp-servers-in-azure-api-management/4526931)).

Identification at the gateway uses either of two credentials Foundry can send. With the agent identity, the Foundry connection's `audience` is the Application ID URI of an app registration that fronts APIM, and `validate-azure-ad-token` checks `audiences`, optionally `client-application-ids`, and `required-claims` such as `roles` with `match="any"`, exposing the parsed token through `output-token-variable-name` for later expressions ([validate-azure-ad-token policy](https://learn.microsoft.com/en-us/azure/api-management/validate-azure-ad-token-policy)). Foundry documents this exact validation pattern for its managed-identity-to-APIM model gateway ([Foundry BYOM via AI gateway](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/ai-gateway)). With subscription keys, two products bound to the same pass-through server, one subscription per agent, and the key stored as `Ocp-Apim-Subscription-Key` in each agent's `custom-keys` connection identify the caller through `context.Product.Id` or `context.Subscription.Id` ([Secure MCP servers](https://learn.microsoft.com/en-us/azure/api-management/secure-mcp-servers); [Policy expressions](https://learn.microsoft.com/en-us/azure/api-management/api-management-policy-expressions)); the one community report of a Foundry agent reaching an APIM MCP server used this path ([Q&A: Trouble connecting Foundry agent to MCP server behind APIM](https://learn.microsoft.com/en-us/answers/questions/5827099/trouble-connecting-foundry-agent-to-mcp-server-beh)). Project managed identity is useless for this purpose because every agent in the project presents the same principal.

Enforcement is one policy at the MCP server scope. "Currently, policies apply to all API operations exposed as tools in the MCP server" ([MCP server overview](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)); there is no per-tool scope and no MCP-specific policy or `context` member, and the JSON-RPC `method` is in the body, so one inbound policy handles `tools/list` and `tools/call` alike. The policy reads the request with `context.Request.Body.As<JObject>(preserveContent: true)`, branches on `method`, `params.name` and `params.arguments.category`, and answers a disallowed call with `return-response` ([Policy expressions](https://learn.microsoft.com/en-us/azure/api-management/api-management-policy-expressions)). The denial shape Microsoft uses for its own gateway-side tool blocking is HTTP 200 with a JSON-RPC `result.isError: true` and a text such as "blocked by the gateway. Do not retry this tool", chosen so agents are "aware of the policy" and refrain from retrying ([Agent 365 integration with APIM](https://learn.microsoft.com/en-us/azure/api-management/agent-365)); a 403 is also valid under the spec but surfaces as a transport error. The same policy strips the inbound `Authorization` header or subscription key, injects the vendor key from a secret named value with `set-header`, and meters the caller with `rate-limit-by-key` on `oid` or subscription ID; the pass-through doc already prescribes `set-header` for a backend that answers 401 ([Expose an existing MCP server](https://learn.microsoft.com/en-us/azure/api-management/expose-existing-mcp-server)). Telemetry carries `gen_ai.operation.name`, `gen_ai.tool.name` and, when payload logging is opted in, `gen_ai.tool.call.arguments`, which gives an audit trail of category requests per caller ([Monitor MCP servers](https://learn.microsoft.com/en-us/azure/api-management/monitor-mcp-servers)). A community post from September 2025 demonstrates the body-parsing, `validate-jwt`, `roles`-to-tool-name pattern end to end ([Fine-grained role control for MCP tools with APIM](https://dev.to/imdj/fine-grained-role-control-for-mcp-tools-with-apim-2pn7)); it is not Microsoft guidance, and no Microsoft doc confirms request-body parsing for MCP pass-through at scale, so treat the pattern as sound but untested by Microsoft.

**APIM cannot filter `tools/list` per caller.** "Don't access the response body by using the `context.Response.Body` variable within MCP server policies. Doing so triggers response buffering, which interferes with the streaming behavior required by MCP servers and might cause them to malfunction" ([Expose an existing MCP server](https://learn.microsoft.com/en-us/azure/api-management/expose-existing-mcp-server)), and the monitoring doc repeats that reading the body "breaks the stream" ([Monitor MCP servers](https://learn.microsoft.com/en-us/azure/api-management/monitor-mcp-servers)). Agent B's model will therefore see every tool the vendor exposes, and only the `tools/call` denial is enforced; `allowed_tools` on Agent B closes the visibility gap for the one-tool-per-category shape and does nothing for the argument shape. The "Tool-level access policies for granular governance" item from APIM's August 2025 roadmap has no matching release note through October 2026 ([Tech Community, MCP in APIM v2 SKUs](https://techcommunity.microsoft.com/blog/integrationsonazureblog/-/4440294)). The separate AI Gateway tier (`Microsoft.ApiManagement/aigateways`, public preview, East US 2 and Sweden Central only) supports Agent 365 tool blocking, but that blocks a tool for all callers of a server "registered in the AI Gateway tier", needs a static allowed-tools list, and "Azure API Management v2 tiers don't support tool-level access control" ([Agent 365 integration with APIM](https://learn.microsoft.com/en-us/azure/api-management/agent-365); [AI Gateway overview](https://learn.microsoft.com/en-us/azure/ai-gateway/overview)); its runtime API keys "grant gateway-wide access", so it adds no per-agent entitlement either ([AI Gateway concepts](https://learn.microsoft.com/en-us/azure/ai-gateway/concepts)).

If per-caller list filtering is a hard requirement, the enforcement point has to be an MCP-aware proxy you run. A thin server built with the C# SDK filters or FastMCP on Container Apps gives list filtering, call denial and argument inspection in one place at the cost of owning code, authentication and session handling. Among open-source gateways, Kong AI Gateway 3.13 "filters the tool list in the response from the upstream API based on the authenticated user's permissions" with tool-level ACLs by consumer group and nothing below tool level ([Kong: Introducing MCP Tool ACLs](https://konghq.com/blog/product-releases/mcp-tool-acls-ai-gateway)); agentgateway filters lists and denies calls on JWT claims and tool name with JSON-RPC `-32602` ([agentgateway tool access](https://agentgateway.dev/docs/kubernetes/latest/mcp/tool-access/)); Microsoft's own MCP Gateway applies Entra app roles per registered resource and requires 2026-07-28 clients ([microsoft/mcp-gateway](https://github.com/microsoft/mcp-gateway)). The 2026-07-28 spec requires `Mcp-Method` and `Mcp-Name` headers on Streamable HTTP POSTs so gateways can authorize without parsing bodies, and lets a tool mirror parameters into `Mcp-Param-{name}` headers via `x-mcp-header` ([2026-07-28 Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)); the Foundry client's protocol version is undocumented and the vendor's tool schema is outside your control, so an APIM policy should keep parsing the body.

Operational limits to design around: "Non-streaming MCP tool calls have a timeout of 100 seconds" in Foundry ([Connect agents to MCP server endpoints](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)); APIM's `forward-request` timeout defaults to 300 seconds and "Values greater than 240 seconds may not be honored" ([forward-request policy](https://learn.microsoft.com/en-us/azure/api-management/forward-request-policy)); APIM forwards request headers "with certain exclusions" that are not enumerated ([Secure MCP servers](https://learn.microsoft.com/en-us/azure/api-management/secure-mcp-servers)), so strip credentials explicitly. Foundry's "govern MCP tools by using an AI gateway" feature (preview, connected v2-tier APIM, "Only new MCP tools created in the Foundry portal that don't use managed OAuth are routed through an AI gateway") is not needed, because pointing each agent's connection at the APIM URL achieves the routing for existing agents with full policy control ([Govern MCP tools by using an AI gateway](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/governance)). No Microsoft source demonstrates the end-to-end agent-identity-to-APIM custom-audience path for an MCP tool; the subscription-key path is the one with a field report.

## Choose app roles at the server, or APIM policy when the server is frozen

The table collapses the options against the two questions that matter: does the mechanism tell Agent A from Agent B, and where is the category rule enforced.

When the third-party server can validate Microsoft Entra tokens, use agent identity with app roles. Register the server (or ask the vendor to register it) as an Entra application with v2 tokens, an Application ID URI matching its canonical MCP URL, and app roles `News.Read.All` and one `News.Read.<Category>` per category with `allowedMemberTypes` of `Application`. Create both agents first, because the agent identity's object ID does not exist until then, read each `instance_identity.principal_id`, and assign `News.Read.All` to Agent A and the subset roles to Agent B through Graph `appRoleAssignedTo`. Create one `remote-tool` connection with auth type `agentic-identity` and the server's Application ID URI as `audience`, and attach it to both agents. The server validates signature, issuer, tenant, audience and expiry, confirms `idtyp` is `app`, and reads `roles`. For the one-tool-per-category shape, map one role to each tool and let the C# SDK filters or a FastMCP `auth=` check hide and reject; add `allowed_tools` on Agent B as a second layer. For the single-tool shape, the handler compares `arguments.category` with the caller's roles and returns `isError` or a 403, optionally narrowing the `category` enum per caller. The custom code is the verifier plus that one check. Before production, decode a real token from each agent to confirm `aud`, `azp` and `roles`, confirm the shared project identity never appears, and expect role changes to lag behind cached tokens. Conditional Access can add a per-agent kill switch for the resource if the tenant holds Agent 365 licensing, and Entra sign-in logs show "which agent identity obtained a token for which resource" ([Agent identity concepts](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)).

When the third-party server cannot be modified at all, first check whether the vendor already issues category-scoped credentials; if so, one `custom-keys` connection per agent is the whole solution, with the caveat that any project member can read both keys and reassign them, so keep the agents in a project with tight membership. Otherwise, publish the vendor endpoint as an APIM pass-through MCP server on a classic or v2 tier and point both agents' connections at the APIM URL. Prefer the agent identity for the inbound leg (no shared secret in the project, per-agent audit in Entra) with `validate-azure-ad-token` against an app registration you own and the same `News.Read.*` app roles; fall back to one product and subscription per agent if the agent-identity-to-custom-audience path fails in your tenant, since that path has a field report and the identity path does not. The inbound policy derives the allowed category set from `roles` or `context.Product.Id`, parses the JSON-RPC body with `preserveContent: true`, denies `tools/call` by `params.name` (one tool per category) or `params.arguments.category` (single tool) with an HTTP 200 JSON-RPC `isError` result that tells the agent not to retry, strips the inbound credential, injects the vendor key from a Key Vault-backed named value, and rate-limits per caller. Accept that `tools/list` reaches Agent B unfiltered; set `allowed_tools` on Agent B for the one-tool-per-category shape and state the permitted categories in Agent B's instructions for the single-tool shape, knowing the prompt is guidance and the gateway is the control. Test the denial response with the Foundry client, because whether APIM frames a `return-response` body correctly for a client that sent `Accept: text/event-stream` is undocumented. If a filtered tool list for Agent B is non-negotiable, replace APIM with a thin MCP-aware proxy you own, or add one behind APIM.

## The agent identity carries the entitlement, and app roles are the slot to put it in

A natural reading of "agents get an identity, so use RBAC" is not that Azure RBAC should enforce anything on the news server, but that the identity could carry a label saying which categories the agent may see, and that a server you own, acting as a wrapper around the third-party server, could read that label and apply it. That design is sound. The identity is the only thing that tells Agent A from Agent B, and a wrapper you own is the cleanest enforcement point when the vendor's server cannot change. The only correction is the slot the label goes in.

Azure RBAC is a poor slot for three concrete reasons. First, an Azure role assignment produces no claim in the agent's token; the `roles` claim carries Entra app roles, not Azure roles ([Agent ID token claims](https://learn.microsoft.com/en-us/entra/agent-id/agent-token-claims)). A wrapper that wanted to read Azure role assignments would need its own Azure credential with role-assignment read permission and would call the Role Assignments REST API with the `assignedTo('{objectId}')` filter on every request or with its own cache ([List Azure role assignments using the REST API](https://learn.microsoft.com/azure/role-based-access-control/role-assignments-list-rest)). Second, a custom role definition cannot be an empty label; its `Actions` and `DataActions` must be operations of a registered resource provider, so a "News Sports Reader" role would have to carry a placeholder action such as a read on the Foundry account, granting the agent a real, if small, Azure permission it does not need, with the category semantics living only in a naming convention ([Azure custom roles](https://learn.microsoft.com/en-us/azure/role-based-access-control/custom-roles)). Third, role assignments propagate with a delay of minutes and every lookup is an ARM round trip.

Entra app roles are the same idea with the label delivered in the token. The assignee is the same object, the agent identity's object ID. The call is the same shape, `POST /servicePrincipals/{wrapperSpId}/appRoleAssignedTo` with `principalId` set to the agent identity ([Grant an appRoleAssignment to a service principal](https://learn.microsoft.com/en-US/graph/api/serviceprincipal-post-approleassignments?view=graph-rest-1.0)). The difference is that the assignment lands in the `roles` claim of the token the wrapper receives, so the wrapper needs no lookup, no second credential and no Azure subscription binding, and the grant is visible to Entra governance. The role must declare `allowedMemberTypes` of `Application`; an app registration can hold up to 700 app role and scope definitions combined ([Add app roles to your application](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps)).

Other carriers exist, and none beats app roles for this purpose. Custom security attributes on the agent identity can hold richer multi-valued data and Microsoft documents them as a Conditional Access targeting criterion for agents ([Conditional Access policy for autonomous agents](https://learn.microsoft.com/en-us/entra/identity/conditional-access/policy-autonomous-agents)); the research found no documentation of them appearing as token claims, so a wrapper would read them through Microsoft Graph with its own permission. Security group membership is supported for agent identities, but group claims are not emitted for service principals, so the wrapper would again need a Graph lookup. Per-agent static `headers` on the MCP tool definition and `custom-keys` connections do reach the wrapper, but any Foundry User who can edit the agent can change them, so they are hints, not authorization. Azure role assignments remain the right primitive when the agent must act on an Azure resource; for a label read by your own API they are the wrong one.

With app roles in place the runtime flow has three hops. Hop one, Foundry to the wrapper: for a prompt agent the Foundry runtime, not agent code, performs the exchange at tool-call time (blueprint credential, agent identity token, then a token scoped to the audience set on the project connection, which is the wrapper's Application ID URI) and sends it as the bearer token on every MCP request ([Agent identity in Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)); for a hosted agent the container code acquires the same token through the hosted token service and attaches it ([Hosted agent token service](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agent-token-service)). Hop two, inside the wrapper: validate signature, issuer, tenant, audience and expiry, confirm `idtyp` is `app`, read `azp` or `appid` and `oid` to identify the agent, read `roles` to derive the allowed categories, then filter `tools/list`, reject disallowed `tools/call` requests, or inject the category filter into the upstream call ([Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)). Hop three, wrapper to vendor: the wrapper calls the third-party server with the vendor credential it alone holds, so the vendor only ever sees the wrapper and the agents never see the vendor URL. The phrase "downstream resource" in the Foundry agent identity doc means whatever the connection's target URL points at, so in this design it is the wrapper; and "role assignments" there is generic, meaning Azure RBAC for an Azure resource and app role assignments for a custom API such as the wrapper. Because the audience is fixed on the connection, Foundry sends the token directly and the wrapper needs no OAuth discovery for this path. Tokens are cached until expiry, so a role change on an agent takes effect at the next token refresh.

## Microsoft's guidance and the standards describe the same design

There is no alternative, better-supported mechanism for agent-level entitlement than the one above. What Microsoft publishes and what the OAuth and MCP standards require converge on it, and the room for improvement is in how it is applied.

Microsoft's position is stated in four places. The Foundry MCP authentication page calls agent identity auth "ideal when you have multiple agents that need different levels of access to the same MCP server" ([Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)). The Foundry agent identity page describes the runtime passing a scoped token to the MCP server, where the downstream resource "validates the token and checks the agent identity's RBAC role assignments before granting or denying access" ([Agent identity in Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)). The Entra guide for securing an MCP server says app roles limit what a client may do and the server checks the `roles` claim before running a tool ([Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)). The Microsoft Security blog of 16 July 2026 sets the principles: each agent should be "a unique, dedicated agent principal with a named owner and an explicit purpose", roles should be "least-privilege, task-based roles that are scoped to the specific resources and data the agent needs", the agent should see "a curated and approved set of tools/actions", and downstream tools "must re-check claims, roles, and scope on each call" ([Least privilege for AI agents: identity, access, and tool binding](https://www.microsoft.com/en-us/security/blog/2026/07/16/least-privilege-for-ai-agents-identity-access-and-tool-binding)). No Azure Well-Architected Framework or Cloud Adoption Framework page goes deeper than this for MCP tool authorization.

The standards say the same. The MCP specification makes the server an OAuth 2.1 resource server that validates audience-bound tokens and enforces authorization itself ([MCP authorization, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)). Its security best practices list "treating claimed scopes as sufficient without server-side authorization logic" as a mistake ([MCP security best practices](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)). The 2026-07-28 revision states that `tools/list` may vary by the authorization presented on the request, which is the per-caller tool view the wrapper returns ([MCP tools, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). The engineering pattern underneath is policy enforcement at the resource, or at a gateway that owns the resource's credential, with identity taken from a signed token and entitlements from claims or a policy store the enforcement point trusts.

Five refinements make the standard approach better in practice.

- Keep roles coarse and data fine. Put capability tiers in app roles (for example `News.Read.All` and `News.Read.Restricted`) and keep the exact category list per tier in the wrapper's own configuration or table. App roles are static, capped at 700 definitions per application, and changes lag until cached tokens expire; a table changes instantly and scales to many categories.
- Govern the grants with Entra ID Governance. Assign the app roles to agent identities through access packages with a sponsor, expiry and access reviews, which is Microsoft's governance model for agent identities and requires Agent 365 licensing ([Agent ID governance overview](https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview)).
- Force all traffic through the wrapper. Keep the vendor credential only in the wrapper, and use the preview Azure Policy "approved tools" built-in to allow only the wrapper's MCP endpoint for agents in that scope, so no agent definition can bypass the restriction by pointing at the vendor directly ([Azure Policy built-in: agents and toolboxes should only use approved tools](https://github.com/Azure/azure-policy/blob/master/built-in-policies/policyDefinitions/Cognitive%20Services/AllowAgentAndToolboxTools_Audit.json)).
- Layer the Foundry-side controls. Set `allowed_tools` on the restricted agent, or publish a full and a trimmed toolbox and attach one to each agent ([Foundry toolbox](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/toolbox)). These are defence in depth; the wrapper remains the enforcement point.
- Log the agent object ID on every call, so an audit can tie a tool invocation to a specific agent and its sponsor.

Avoid Azure RBAC as a metadata store, self-asserted headers in the agent definition, the project managed identity (both agents look identical), and relying on a gateway alone when the server or wrapper can enforce.

One check on the requirement. Everything above restricts the agent. If the real intent is that the people using Agent B may only see some categories, the standard answer shifts to delegated identity: Entra user delegation or OAuth passthrough carries the user's token, and the wrapper authorizes on the user's scopes or roles instead. The MCP Enterprise-Managed Authorization extension covers that user-centred case, not the agent-level one ([Enterprise-Managed Authorization extension](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)).

## Conclusion

The question "can RBAC do it, given that agents have identities" splits into two answers. The identity half is solved and off the shelf: a Foundry agent is now a first-class Entra service principal, the MCP connection carries it to the server, and app roles on the server's registration give an administrator a directory-governed, per-agent entitlement that security teams can review without reading policy XML or server code. The RBAC half is a plain no, and the instinct behind it maps onto Entra app roles instead: same assignee (the agent identity object ID), same Graph call shape, but a claim the server reads rather than an ARM evaluation the server cannot reach. Everything downstream of the token is code at the point of validation, and the only question is whose: the vendor's, yours in a proxy, or a gateway operator's in APIM policy.

Two things to watch. The 2026-07-28 MCP revision moved tool names and methods into request headers and made per-caller `tools/list` explicit, so gateways will get simpler rules and servers will get standard list filtering; Foundry's client protocol version and `tools/list` caching remain undocumented, and the Foundry data-plane contract still labels the agent-identity credential type as preview even though the Learn pages do not. Until a Microsoft sample shows a Foundry agent token for a custom audience arriving at an APIM policy or a third-party server, treat the agent-identity path as documented but unproven in your tenant, and budget one afternoon of token decoding before the design is fixed.
