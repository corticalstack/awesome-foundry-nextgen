# MCP server-side per-caller authorization (tools and data categories), with Entra ID token validation, as of 2026-10-29

Scope of these notes: what the MCP spec mandates and leaves open, how a remote (Streamable HTTP) MCP server validates an Entra token and maps the caller to allowed tools or categories, what the official SDKs / FastMCP / Azure Functions / Agent Framework give you, and what has to happen upstream when the third-party server cannot be changed. The scenario is a news MCP server with two Foundry agents: one unrestricted, one limited to a subset of categories, in both tool shapes (one tool per category vs. one tool with a `category` argument).

Spec versions referenced: `2025-06-18`, `2025-11-25`, `2026-07-28` (current). Dates are stated per source. Code is illustrative unless marked as quoted from a source.

## Key question 1: What does the MCP authorization spec mandate, what does it say about scopes, and is there any standard for per-tool permission or per-client tool visibility?

### Takeaway
The spec (all three revisions) makes the MCP server an OAuth 2.1 resource server that MUST publish RFC 9728 Protected Resource Metadata, MUST validate audience (RFC 8707 resource binding), and MUST return 401/403 correctly; it defines a scope *mechanism* (challenges in `WWW-Authenticate`, `scopes_supported`, step-up) but no scope *vocabulary* and no per-tool permission model. As of `2026-07-28` the Tools page explicitly permits the `tools/list` result to vary by the authorization presented on the request, which is the only normative hook for per-client tool visibility; everything finer (category arguments) is left to server-side authorization logic, which the security-best-practices page says you must have.

### Cited Findings

Core requirements (stable across 2025-06-18 and 2026-07-28):
- Authorization is OPTIONAL; HTTP transports SHOULD conform; STDIO SHOULD NOT and should use environment credentials. Authorization servers MUST implement OAuth 2.1 (draft-ietf-oauth-v2-1-13). MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC 9728) and clients MUST use it for AS discovery. [MCP Authorization 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization); [MCP Authorization 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Clients MUST send the RFC 8707 `resource` parameter in authorization and token requests, set to the canonical server URI (e.g. `https://mcp.example.com/mcp`, no trailing slash, no fragment). [2026-07-28 Authorization, Resource Parameter Implementation](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Quoted: "MCP servers, acting in their role as an OAuth 2.1 resource server, MUST validate access tokens as described in OAuth 2.1 Section 5.2. MCP servers MUST validate that access tokens were issued specifically for them as the intended audience ... Invalid or expired tokens MUST receive a HTTP 401 response." And: "MCP servers MUST NOT accept or transit any other tokens." [2026-07-28 Authorization, Token Handling](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Error table: 401 "Authorization required or token invalid"; 403 "Invalid scopes or insufficient permissions"; 400 "Malformed authorization request". [2026-07-28 Authorization, Error Handling](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- 2025-06-18 also: authorization MUST be included on every HTTP request, even within one logical session; access tokens MUST NOT go in the query string; PKCE MUST be implemented by clients. [MCP Authorization 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)
- 2025-06-18 "Access Token Privilege Restriction": "MCP servers MUST validate access tokens before processing the request, ensuring the access token is issued specifically for the MCP server, and take all necessary steps to ensure no data is returned to unauthorized parties." [MCP Authorization 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)

Scopes:
- 2026-07-28 "Scope Selection Strategy": servers SHOULD include `scope` in the `WWW-Authenticate` challenge (RFC 6750 s3); the challenged set MAY be a subset, superset, or unrelated to `scopes_supported`; clients MUST treat the challenge as authoritative for the current operation. Example given: `WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource", scope="files:read"`. [2026-07-28 Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- 2026-07-28 "Scope Challenge Handling": on insufficient scope at runtime the server SHOULD return `403` with `WWW-Authenticate: Bearer error="insufficient_scope", scope="...", resource_metadata="..."`. Quoted: "The required scopes may be determined dynamically based on the specific request arguments and context, but once determined, they should be emitted together." And: "Servers MUST account for scope hierarchies, where a broader scope implies narrower ones, when deciding whether a token is sufficient for an operation." [2026-07-28 Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Step-up: clients acting for a user SHOULD step up; "Clients acting on their own behalf (`client_credentials` clients) MAY attempt the step-up authorization flow or abort the request immediately." [2026-07-28 Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- The spec defines no scope names and no mapping between scopes and tools; `files:read` / `files:write` appear only as examples. [2026-07-28 Authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)
- Security Best Practices, "Scope Minimization", lists as a common mistake: "Treating claimed scopes in token as sufficient without server-side authorization logic", and recommends a minimal initial scope set with incremental elevation via `WWW-Authenticate scope="..."` challenges. [MCP Security Best Practices (2025-11-25 text)](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)

Per-client tool visibility:
- 2026-07-28 Tools page, quoted: "Servers that declare the `tools` capability MUST respond to `tools/list` requests with the set of tools currently available to the requesting client. This set MAY be empty and MAY change over time (see List Changed Notification), but MUST NOT vary per-connection or as a side effect of other requests on the connection. The set MAY vary by the authorization presented on the request - for example, returning only the tools the caller's granted scopes permit - since credentials are per-request input, not connection state." (dashes in the quote normalised to hyphens) [MCP Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Same page, Security Considerations: "Servers MUST: Validate all tool inputs; Implement proper access controls; Rate limit tool invocations; Sanitize tool outputs." [MCP Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- 2026-07-28 makes `tools/list` results carry required `ttlMs` and `cacheScope` (`"public"` or `"private"`); `cacheScope` "controls whether shared intermediaries may cache the response" (SEP-2549). Servers SHOULD return tools in deterministic order. [2026-07-28 Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- `notifications/tools/list_changed` in 2026-07-28 is delivered only to clients that opened a `subscriptions/listen` stream with `toolsListChanged: true`; protocol sessions and `Mcp-Session-Id` were removed (SEP-2567, SEP-2575). [MCP Tools 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/server/tools); [2026-07-28 Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog)
- Security Best Practices: "MCP servers that implement authorization MUST verify all inbound requests. MCP Servers MUST NOT use sessions for authentication." [MCP Security Best Practices](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)

Revision history and working-group state:
- 2025-11-25: Client ID Metadata Documents (CIMD) added as recommended registration (SEP-991); DCR moved from SHOULD to MAY; OpenID Connect Discovery added; `WWW-Authenticate` made optional with `.well-known` fallback (SEP-985); incremental scope consent via `WWW-Authenticate` (SEP-835); client credentials (SEP-1046) and Cross App Access (SEP-990) published as authorization extensions rather than core. [2025-11-25 Changelog](https://modelcontextprotocol.io/specification/2025-11-25/changelog); [Den Delimarsky, November 2025 auth spec](https://den.dev/blog/mcp-november-authorization-spec/); [Aaron Parecki, client registration and enterprise management](https://aaronparecki.com/2025/11/25/1/mcp-authorization-spec-update); [Auth0 blog](https://auth0.com/blog/mcp-november-2025-specification-update/)
- 2026-07-28 (released 2026-07-28 with updated TypeScript, Python, Go, C# SDKs): RFC 9207 `iss` validation (SEP-2468); `application_type` in DCR (SEP-837); client credentials bound to issuer (SEP-2352); DCR formally deprecated in favour of CIMD (PR #2858); `extensions` field in client/server capabilities; `Mcp-Method` and `Mcp-Name` headers required on Streamable HTTP POSTs so gateways can route and authorize without parsing bodies (SEP-2243). [2026-07-28 Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [MCP blog, The 2026-07-28 Specification](https://blog.modelcontextprotocol.io/posts/2026-07-28/)
- Authorization extensions (2026-07-28 Authorization page): optional, additive, composable, independently versioned; list lives in the `ext-auth` repo. [2026-07-28 Authorization, MCP Authorization Extensions](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization); [modelcontextprotocol/ext-auth](https://github.com/modelcontextprotocol/ext-auth)
- `ext-auth` README lists two extensions, both at Stable with a dated stable revision `2026-07-28`: Enterprise-Managed Authorization and OAuth Client Credentials. [modelcontextprotocol/ext-auth](https://github.com/modelcontextprotocol/ext-auth); a third-party mirror describes the client-credentials extension as draft (conflict noted). [search snippet, modelcontextprotocol.info](https://modelcontextprotocol.info/extensions/auth/oauth-client-credentials/)
- Enterprise-Managed Authorization (`io.modelcontextprotocol/enterprise-managed-authorization`, SEP-990): client obtains an ID-JAG from the enterprise IdP (RFC 8693 token exchange) and exchanges it at the MCP authorization server; the IdP "controls which MCP servers employees can access, and under what conditions"; for MCP authorization servers: "Map IdP claims to permissions ... Define your authorization logic based on these claims." It governs server access and scopes, not individual tools. [MCP EMA extension page](https://modelcontextprotocol.io/extensions/auth/enterprise-managed-authorization)
- OAuth Client Credentials extension (`io.modelcontextprotocol/oauth-client-credentials`): adds the client_credentials grant for non-interactive clients; AS metadata MUST include `token_endpoint_auth_methods_supported` with `private_key_jwt` or `client_secret_basic`; Python SDK has `ClientCredentialsOAuthProvider`. [MCP OAuth Client Credentials extension page](https://modelcontextprotocol.io/extensions/auth/oauth-client-credentials)

### Inferences
- The spec gives you exactly two sanctioned levers for per-caller restriction: (a) vary `tools/list` by the bearer presented (2026-07-28 text), and (b) reject `tools/call` with 403 `insufficient_scope` naming the missing scope. Argument-level restriction (a `category` value) is explicitly in scope of (b) ("determined dynamically based on the specific request arguments"), but the decision logic is entirely yours.
- A server that filters `tools/list` by caller should return `cacheScope: "private"` on that result so a shared cache (APIM, a gateway) does not serve agent A's list to agent B. This follows from the stated purpose of `cacheScope` (controls caching by shared intermediaries); the spec does not spell out the authorization case.
- Because a Foundry agent is a machine client (client_credentials or Entra token exchange), the step-up path is optional for it per the spec; a 403 is effectively terminal for the call. Design the restricted agent so it never needs scopes it cannot get (i.e. hide or reject rather than challenge).
- No SEP or extension in flight defines tool-level or argument-level permission semantics. Gateways (Kong, Agent Router) fill this gap with their own policy models (see Key question 7).

### Gaps
- I did not fetch the full `2025-11-25` authorization page itself; its changes are taken from the changelog and three practitioner blogs that agree with each other.
- The spec does not say how clients should behave when two sessions of the same client receive different tool lists; Foundry's handling of a per-agent-different `tools/list` is not documented (see Key question 6).

## Key question 2: How does an MCP server validate an Entra-issued token (JWKS, audience, issuer v1 vs v2, `roles` vs `scp`, agent-identity marker)?

### Takeaway
Microsoft's own MCP guidance (Entra Agent ID docs, 2026-09-01) says: register the MCP server with `requestedAccessTokenVersion: 2`, set the Application ID URI to the canonical MCP URL so RFC 8707 `resource` matches, publish PRM with `authorization_servers: ["https://login.microsoftonline.com/<tenant-id>/v2.0"]`, validate signature/`iss`/`tid`/`aud`/`exp` with a library, then authorize on `roles` (app-only callers such as agent identities) or `scp` (delegated), and detect agent identities via `xms_par_app_azp`.

### Cited Findings
- Entra guidance, quoted: "Microsoft Entra ID compares that `resource` value against the Application ID URI (also called the identifier URI) configured on your MCP server's app registration. If they match, Microsoft Entra ID issues a token whose audience (`aud`) claim is your MCP server." And: "your MCP server must accept v2 access tokens." Manifest: `"api": { "requestedAccessTokenVersion": 2 }`. Order matters: enable v2 before setting an HTTPS Application ID URI. [Secure an MCP server with Microsoft Entra ID (ms.date 2026-09-01)](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- `identifierUris` is a list; add every URL clients might send as `resource` (example lists `https://mcp.contoso.com`, `https://mcp.contoso.com/mcp`, `https://contoso-mcp.azurewebsites.net`). An Application ID URI cannot end with a slash, so a client sending `resource=https://mcp.contoso.com/` fails with `AADSTS9010010`. [Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- PRM example from the same page: `{"resource": "https://mcp.contoso.com", "authorization_servers": ["https://login.microsoftonline.com/<tenant-id>/v2.0"], "scopes_supported": ["tools.read","tools.execute"], "bearer_methods_supported": ["header"]}`; the `authorization_servers` value must be the v2.0 issuer because "The v1 issuer (`https://sts.windows.net/<tenant-id>/`) doesn't line up with the v2.0 authorization server metadata that clients discover." [Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- Validation checklist, quoted: "verify the token's signature, issuer (`iss`), tenant ID (`tid`), audience (`aud`, which must equal the application ID of your MCP server), and expiry. Then check that the subject (`sub` or `oid`) of the token is authorized for the requested operation using the role (`roles`) claim or another authorization check. For delegated access tokens, also be sure to check the scope (`scp`) claim". Also: "Don't write your own token-validation logic from scratch." [Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- App-only callers: "To request an access token as an agent identity, the MCP client sends an OAuth client credentials grant request and uses a scope value such as `scope=https://mcp.contoso.com/.default`. Entra app roles can be used to limit the access an MCP client has against your MCP server. You assign app roles to the MCP client's agent identity. Assigned roles appear in the `roles` claim of the access token, and your server checks that claim before it runs a tool." [Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- v1 fallback: if you cannot move to v2 tokens, add the `aud` optional claim with `use_guid` so `aud` is always the client-ID GUID and Entra relaxes the Application ID URI restriction. [Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- Claim definitions: `aud` "In v2.0 tokens, this value is always the client ID of the API. In v1.0 tokens, it can be the client ID or the resource URI used in the request." `iss`: "If the token issued is a v2.0 token (see the `ver` claim), the URI ends in `/v2.0`." `appid` (v1 only) and `azp` (v2 only): "The application ID of the client using the token ... may be used in authorization decisions." `scp`: "Only included for user tokens." `roles`: "The client credential flow uses this set of permission in place of user scopes for application tokens. For user tokens, this set of values contains the assigned roles of the user on the target application." `oid`: immutable requestor ID, usable as an authorization key. [Access token claims reference (updated 2026-07-24)](https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference)
- JWKS and issuer formats for agent tokens: verify RS256 against `https://login.microsoftonline.com/<tenant>/discovery/v2.0/keys`; `iss` matches `https://sts.windows.net/<tenant>/` (v1) or `https://login.microsoftonline.com/<tenant>/v2.0` (v2); the agent-identity marker is `xms_par_app_azp`, "present in agent identity tokens and absent in standard app-only tokens. This claim identifies the blueprint that created the agent." Sample is a PyJWT Flask app in `microsoft/entra-agentid-samples` (`sidecar/weather-api`). [Validate agent identity tokens in a downstream API (ms.date 2026-04-28)](https://learn.microsoft.com/en-us/entra/agent-id/how-to-validate-agent-tokens-downstream-api)
- .NET verification helpers: `[RequiredScope("access_as_user")]` or `HttpContext.VerifyUserHasAnyAcceptedScope(...)` check the `scp` claim; `HttpContext.ValidateAppRole("access_as_application")` or `[Authorize(Roles = "access_as_application")]` check `roles`; app-only detection `oid == sub`; set `AllowWebApiToBeAuthorizedByACL` if neither claim is present and you use an ACL instead. [Verify scopes and app roles in a protected web API](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-protected-web-api-verification-scope-app-roles)
- The same page warns against roles assignable to both users and apps: "We recommend that you declare different roles for users and apps to prevent this confusion." [Verify scopes and app roles](https://learn.microsoft.com/en-us/entra/identity-platform/scenario-protected-web-api-verification-scope-app-roles)
- Managed-identity caveat: "The tokens your application receives are cached by the underlying infrastructure. This means that any changes to the managed identity's roles can take significant time to process." [Assign a managed identity to an app role (Azure CLI)](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-to-assign-app-role-managed-identity-cli)

### Inferences
- For a Foundry agent calling with agent identity or project managed identity, the token is app-only: expect `roles` (not `scp`), `azp` = the agent identity's app ID (v2), `oid` = its service principal object ID, and (for agent identities) `xms_par_app_azp` = blueprint app ID. The MCP server can key entitlements on either `roles` (preferred, declarative) or `oid`/`azp` (an ACL keyed on caller identity).
- Illustrative Python verification for the Python MCP SDK's `TokenVerifier` (library-backed, per Microsoft's "don't hand-roll" advice):

```python
# illustrative: PyJWT + PyJWKClient; returns the SDK's AccessToken
import jwt
from mcp.server.auth.provider import AccessToken

JWKS = jwt.PyJWKClient(f"https://login.microsoftonline.com/{TENANT}/discovery/v2.0/keys")

class EntraVerifier:
    async def verify_token(self, token: str) -> AccessToken | None:
        key = JWKS.get_signing_key_from_jwt(token).key
        claims = jwt.decode(
            token, key, algorithms=["RS256"],
            audience=MCP_APP_CLIENT_ID,                      # v2 aud == client ID GUID
            issuer=f"https://login.microsoftonline.com/{TENANT}/v2.0",
        )
        if claims.get("tid") != TENANT:
            return None
        roles = claims.get("roles", [])                      # app-only entitlements
        scopes = (claims.get("scp") or "").split()          # delegated entitlements
        return AccessToken(token=token, client_id=claims.get("azp", ""),
                           scopes=scopes + [f"role:{r}" for r in roles],
                           subject=claims.get("oid"), expires_at=claims["exp"],
                           resource=MCP_CANONICAL_URL, claims=claims)
```

### Gaps
- Microsoft does not publish a complete, maintained Python or TypeScript MCP-server sample that validates Entra app-only tokens and checks `roles`; the official Functions samples rely on App Service built-in auth instead (Key question 4).

## Key question 3: Concrete patterns and SDK/framework support for per-caller tool filtering and argument-level checks (Python SDK, TypeScript SDK, C# SDK, FastMCP)

### Takeaway
All four official stacks let a tool handler read the validated token; only the C# SDK (authorization filters) and FastMCP 3 (component-level `auth=`) hide unauthorized tools from `tools/list` automatically; the TypeScript SDK v2 offers per-tool `scopeChallenge` and a per-request server factory that can register a different tool set per caller; the Python SDK gives only global `required_scopes` plus `get_access_token()` for in-handler checks. Argument-level (category) checks are always in-handler code in every stack.

### Cited Findings

Python SDK (v2 line, implements 2026-07-28):
- `TokenVerifier` is one async method: `async def verify_token(self, token: str) -> AccessToken | None`. `AuthSettings(issuer_url, resource_server_url, required_scopes, validate_token_resource)`; `validate_token_resource` rejects tokens whose `resource` differs from `resource_server_url` (defaults to `False` with a warning; 3.0 expected to default `True`). `AccessToken` fields: `token`, `client_id`, `scopes`, `resource`, `subject`, `expires_at`, `claims`. `required_scopes` is global ("every token must carry all of them"); there is no per-tool scope setting and no built-in JWKS verifier (the bundled example is an RFC 7662 `IntrospectionTokenVerifier`). Handler access: `get_access_token()` from `mcp.server.auth.middleware.auth_context`. [Python SDK v2, Authorization](https://py.sdk.modelcontextprotocol.io/v2/run/authorization/)
- Bearer middleware takes its own `required_scopes` and `resource_metadata_url` for the `WWW-Authenticate` header. [Python SDK bearer_auth API](https://py.sdk.modelcontextprotocol.io/api/mcp/server/auth/middleware/bearer_auth/)
- Security advisory: CVE-2026-116684 (published 2026-10-27) reports that from 1.10.0 until 1.30.0 and in 2.2.0 a token issued for another service could be accepted when the AS serves multiple resources and the `TokenVerifier` does not check audience. [CVE-2026-116684](https://app.opencve.io/cve/CVE-2026-116684)
- The python-sdk README describes v2 but contains no auth content; the GitHub `docs/authorization.md` path returns 404. [python-sdk README](https://github.com/modelcontextprotocol/python-sdk/blob/main/README.md)

TypeScript SDK (v2, published 2026-07-27 as `@modelcontextprotocol/server` and `@modelcontextprotocol/client`, implements 2026-07-28; v1.x `@modelcontextprotocol/sdk` gets fixes for at least six months):
- `requireBearerAuth({ verifier, requiredScopes, resourceMetadataUrl, expectedResource })` from `@modelcontextprotocol/express` (Express) or `@modelcontextprotocol/server` (fetch hosts); missing/invalid/expired token gives `401 invalid_token`, missing required scope gives `403 insufficient_scope`, both with a `WWW-Authenticate: Bearer` challenge. `OAuthTokenVerifier.verifyAccessToken(token)` returns `AuthInfo` (`token`, `clientId`, `scopes`, `expiresAt` required or the gate returns 401, `resource`, `extra`). `mcpAuthMetadataRouter({ oauthMetadata, resourceServerUrl })` serves the RFC 9728 document. Tool handlers read `ctx.http?.authInfo` (undefined over stdio). [TypeScript SDK v2, Serving: Authorization](https://ts.sdk.modelcontextprotocol.io/v2/serving/authorization); [typescript-sdk README](https://github.com/modelcontextprotocol/typescript-sdk/blob/main/README.md)
- Per-operation scope check, quoted example: `server.registerTool('purge-notes', { scopeChallenge: requireScopes('notes:write') }, async () => ({...}))`; `scopeChallenge` also accepts a callback for request-dependent scopes that "returns `undefined` to continue, or the required scope set to send a `403` before the handler runs." [TypeScript SDK v2, Serving: Authorization](https://ts.sdk.modelcontextprotocol.io/v2/serving/authorization)
- Per-caller tool sets: the page's tip says the per-request factory receives `ctx.authInfo` "and can register a different tool set for each caller before any handler runs." There is no `tool.enable`/`disable` API documented on this page. Known bug: `@modelcontextprotocol/express` 2.0.1 ignores `expectedResource`; upgrade together with `@modelcontextprotocol/server`. [TypeScript SDK v2, Serving: Authorization](https://ts.sdk.modelcontextprotocol.io/v2/serving/authorization)

C# SDK (`ModelContextProtocol`, `ModelContextProtocol.AspNetCore`; 1.4.0 stable and 2.0.0-preview.1 as of July 2026):
- Caller identity: the transport copies `HttpContext.User` into `JsonRpcMessage.Context.User`; a tool method can declare a `ClaimsPrincipal? user` parameter, which the SDK hides from the input schema. `AddAuthorizationFilters()` enables `[Authorize]`, `[Authorize(Roles = "...")]`, `[Authorize(Policy = "...")]` and `[AllowAnonymous]` on tools, prompts and resources. Sample `ProtectedMcpServer` uses JWT Bearer, OAuth resource metadata and `RequireAuthorization()` on the MCP endpoint. [C# SDK v2, Identity](https://csharp.sdk.modelcontextprotocol.io/v2/concepts/identity/identity.html)
- List filtering, quoted: "For list operations, the filters automatically remove unauthorized items from the results." Unauthorized calls "throw an `McpException` with 'Access forbidden' message." Custom filters: `WithRequestFilters(f => f.AddListToolsFilter(...))` / `AddCallToolFilter(...)` where `context.User` is a `ClaimsPrincipal` and `context.MatchedPrimitive.Metadata` exposes the tool's attributes; filters registered before `AddAuthorizationFilters()` see unfiltered lists. [C# SDK, Filters](https://csharp.sdk.modelcontextprotocol.io/v1/concepts/filters.html)
- Wiring pattern `AddAuthentication("Bearer").AddJwtBearer(...).AddMcp(...)` with `ResourceMetadata` (resource, authorization servers, scopes) in `ModelContextProtocol.AspNetCore.Authentication`. [McpAuthenticationExtensions API](https://csharp.sdk.modelcontextprotocol.io/api/Microsoft.Extensions.DependencyInjection.McpAuthenticationExtensions.html); [Den Delimarsky, C# SDK authorization](https://den.dev/blog/mcp-csharp-sdk-authorization/); [.NET blog, MCP C# SDK v1.0 (2026-03-05)](https://devblogs.microsoft.com/dotnet/release-v10-of-the-official-mcp-csharp-sdk/)
- `[McpAuthorize(Scopes=...)]` is from a third-party project (Palpid/McpAuthExt), not the official SDK. [Palpid/McpAuthExt](https://github.com/Palpid/McpAuthExt)

FastMCP (gofastmcp.com):
- Azure/Entra: `AzureProvider` (full OAuth proxy; needs `client_secret`; params `client_id`, `tenant_id` required, `base_url`, `required_scopes` required and at least one, `identifier_uri` default `api://{client_id}`, `additional_authorize_scopes`, `base_authority` for Azure Government), `AzureProvider.from_b2c(...)`, `AzureJWTVerifier` (token validation only, "auto-configures JWKS, issuer, and audience from `client_id` and `tenant_id`", validates against the client ID as audience, checks short-form scopes in `scp`), and `EntraOBOToken` tool-parameter dependency for on-behalf-of. The page documents reading `sub`, `email`, `name` via `get_access_token().claims`; it does not document `roles`, `oid` or `azp`, and documents only server-level `required_scopes`. [FastMCP Azure integration](https://gofastmcp.com/integrations/azure)
- Component-level authorization (introduced in FastMCP 3.0.0): `@mcp.tool(auth=require_scopes("write"))`; server-level `AuthMiddleware(auth=require_scopes("api"))`; built-ins `require_scopes(...)` (AND) and `restrict_tag(tag, scopes=[...])`; custom checks are any callable `(AuthContext) -> bool` (sync or async) with `AuthContext.token: AccessToken | None` and `AuthContext.component`. Behaviour: "the component is hidden from list responses and direct access returns not-found"; `AuthMiddleware` gives explicit `AuthorizationError` responses. No `require_roles`/`require_claims` built-in. [FastMCP v3 Authorization](https://gofastmcp.com/v3/servers/authorization)
- Conflict: the unversioned authorization page says component-level `auth` "only controls visibility in list operations" and does not block direct access, advising `AuthMiddleware` for enforcement; the v3 page says direct lookups return not-found. Treat the installed version's docs as authoritative. [FastMCP authorization (unversioned)](https://gofastmcp.com/servers/authorization); [FastMCP v3 Authorization](https://gofastmcp.com/v3/servers/authorization)

### Inferences
- Case A, one tool per category (tool-level authorization suffices):
  - C#: `[Authorize(Roles = "News.Read.Sports")]` on `get_sports_news`; the SDK removes it from `tools/list` and rejects calls for callers without that role, because Entra `roles` map to ASP.NET Core role claims once `AddJwtBearer` is configured with `RoleClaimType = "roles"` (standard ASP.NET behaviour; not MCP-specific).
  - FastMCP 3: `@mcp.tool(auth=has_role("News.Read.Sports"))` where `has_role` is a custom `AuthContext -> bool` reading `ctx.token.claims.get("roles", [])` (the built-in `require_scopes` checks `scopes`, which for app-only Entra tokens would be empty unless your verifier copies `roles` into `scopes`, as in the illustrative verifier above).
  - TypeScript v2: either `scopeChallenge: requireScopes("role:News.Read.Sports")` with a verifier that maps `roles` into `AuthInfo.scopes`, or the per-request factory that registers only the caller's category tools so `tools/list` is already filtered.
  - Python SDK: no list filtering primitive; either build the `FastMCP`/`MCPServer` instance per request from `get_access_token()`, or register all tools and have each handler check `token.claims["roles"]` and return an `isError` result. The latter still exposes tool names to the restricted agent, which is acceptable for enforcement but weaker for prompt hygiene.
- Case B, single tool with a `category` argument (argument-level authorization):
  - Only in-handler code can enforce it in any stack: read the caller's entitlements, compare with `arguments.category` (or filter the returned categories when `category` is omitted), and either return a tool error (`isError: true`) or raise a 403 `insufficient_scope` naming `news.read.<category>`. The TypeScript `scopeChallenge` callback is the one framework hook that formalizes this: it can inspect the request arguments and return the needed scope set.
  - A hybrid that keeps the single-tool shape but still lets the SDK filter: expose the tool's `inputSchema.category` as an `enum` computed per caller (allowed categories only). The LLM then sees only valid values; the handler must still validate because schemas are advisory to the client.
- Because every stack's list filtering is keyed on the bearer of the current request (2026-07-28 removed sessions), two agents hitting the same server with different Entra identities get different lists without any session plumbing.

### Gaps
- FastMCP's Azure page does not say whether `AzureJWTVerifier` accepts app-only (client_credentials) tokens that carry `roles` and no `scp`; given `required_scopes` is mandatory and checked against `scp`, app-only callers may need a custom verifier or `required_scopes=[]`-style configuration. Not verified.
- I found no official Python SDK example of per-caller tool-list filtering.

## Key question 4: Azure Functions MCP extension (mcpToolTrigger) authentication options, built-in Entra (EasyAuth), system keys, and whether a tool can see the caller

### Takeaway
Azure Functions gives two switches: the `mcp_extension` system key (default, `x-functions-key`) and App Service built-in authentication, which implements the MCP OAuth requirements (401 challenge, PRM) and can allow-list caller app IDs and object IDs; Microsoft states plainly that this "doesn't provide granular control to individual MCP tools", and the roles check is your code's job. Whether an `mcpToolTrigger` function can read the `x-ms-client-principal` claims is not documented.

### Cited Findings
- Endpoints: Streamable HTTP `/runtime/webhooks/mcp`, SSE `/runtime/webhooks/mcp/sse` (deprecated). PRM support is preview and is enabled by `WEBSITE_AUTH_PRM_DEFAULT_WITH_SCOPES` (comma-separated scopes, e.g. `api://<client-id>/user_impersonation`). ### Inferences

## Key question 5: Entra app roles as the entitlement model: define category roles, assign to an agent identity or managed identity, exact commands

### Takeaway
Define one app role per category on the MCP server's app registration with `allowedMemberTypes: ["Application"]` (e.g. `News.Read.All`, `News.Read.Sports`), assign them to each agent's service principal via Graph `appRoleAssignments` (no first-class `az` command; use `az rest`), and read the `roles` claim in the server. Microsoft recommends roles for "stable authorization categories" and keeping finer-grained data in your own store; the 700-definition limit and the group-assignment caveat for service principals both matter.

### Cited Findings
- App role manifest shape, quoted from the managed-identity guide: `{"allowedMemberTypes": ["Application"], "displayName": "Read data from MyApi", "id": "00001111-aaaa-2222-bbbb-3333cccc4444", "isEnabled": true, "description": "Allow the application to read data as itself.", "value": "MyApi.Read.All"}`. [Assign a managed identity to an app role (Azure CLI), ms.date 2025-09-09](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-to-assign-app-role-managed-identity-cli)
- Exact assignment commands from the same page:

```bash
# object id of the caller's service principal (user-assigned MI shown; for an agent identity use its SP object id)
oidForMI=$(az resource show --id "$userManagedIdentityResourceId" --query "properties.principalId" -o tsv | tr -d '[:space:]')
# object id of the MCP server's service principal, by app id
serverSPOID=$(az ad sp list --filter "appId eq '$appID'" --query '[0].id' -o tsv | tr -d '[:space:]')
# assign (not exposed directly in az; use Graph)
roleguid="00000000-0000-0000-0000-000000000000"
az rest -m POST -u https://graph.microsoft.com/v1.0/servicePrincipals/$oidForMI/appRoleAssignments \
  -b "{\"principalId\": \"$oidForMI\", \"resourceId\": \"$serverSPOID\",\"appRoleId\": \"$roleguid\"}"
```
[Assign a managed identity to an app role (Azure CLI)](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/how-to-assign-app-role-managed-identity-cli)
- Graph reference: `POST /servicePrincipals/{id}/appRoleAssignments` with `principalId`, `resourceId`, `appRoleId`; Microsoft recommends creating assignments via the resource SP's `appRoleAssignedTo` relationship. [Grant an appRoleAssignment to a service principal](https://learn.microsoft.com/en-US/graph/api/serviceprincipal-post-approleassignments?view=graph-rest-1.0)
- App roles doc (ms.date 2026-09-25): "App roles can also be assigned to the service principal for another application, or to the service principal for a managed identity." "Currently, if you add a service principal to a group, and then assign an app role to that group, Microsoft Entra ID doesn't add the `roles` claim to tokens it issues." Default limit of 700 permission definitions per application/service principal shared with delegated scopes; "Use app roles for stable authorization categories, such as `Reader`, `Writer`, and `Administrator`, rather than defining a role for every resource, customer, or individual action. Keep finer-grained resource permissions in your application's authorization data and enforce them in the application." Role `value` must have no spaces and must exactly match the string the code checks; application permissions need admin consent. [Add app roles and get them from a token](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps)
- Entra MCP guide step 5: create roles with "Allowed member types" = Applications, e.g. `Tools.Execute.All`, then "Assign the role to the agent identity (or other client application) that calls your server." [Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- Foundry agent identity model (ms.date 2026-10-28): each new agent gets its own blueprint and default-instance identity (a special service principal); "A newly created agent identity starts without resource permissions"; the service's authorization model may be "Application permissions or app roles: An API grants the identity application-level permissions for access without a signed-in user"; "For Azure RBAC assignment procedures, use the object ID of the agent identity used for the tool call as the assignee." Runtime: Agent Service requests a token "scoped to the audience of the downstream service" and "The downstream resource validates the token and checks the agent identity's RBAC role assignments before granting or denying access." [Agent identity concepts in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- App Service built-in auth does not evaluate `roles`; only `appid`/`azp` and `oid` allow-lists. [Configure Microsoft Entra authentication, App Service](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-provider-aad)

### Inferences
- Role design for the scenario (illustrative): `News.Read.All` plus `News.Read.<Category>` per category; the server treats `News.Read.All` as implying every category (the spec requires honouring scope hierarchies; apply the same to roles). The unrestricted agent gets `News.Read.All`; the restricted agent gets the subset. This keeps definitions well under 700 and matches Microsoft's "stable categories" advice. If categories are many or volatile, keep a per-caller allow-list keyed on `oid` in the server's own store instead and use a single `News.Read` role as the gate.
- Role assignments on agent identities use the same Graph call as managed identities (the agent identity is a service principal); the Foundry docs do not give an `az` one-liner for app roles, only RBAC.
- Token caching means a role change can take time to show up; design tests to wait or force a new token.

### Gaps
- No Microsoft page shows the `appRoleAssignments` call specifically against a Foundry agent identity's service principal; the model is inferred from "agent identity is a special service principal" plus the managed-identity procedure.

## Key question 6: What does each Foundry agent present to the MCP server, and can two agents in one project be told apart?

### Takeaway
Foundry binds authentication to the project connection, not the agent code; with `agentic-identity` each agent presents its own Entra agent identity (the doc calls this "ideal when you have multiple agents that need different levels of access to the same MCP server"), with `project-managed-identity` all agents look identical, and with `custom-keys` the server sees whatever header you stored, so distinct keys per connection also distinguish agents. Foundry also offers client-side tool allow-lists (`AllowedTools` / `allowed_tools`, `require_approval` per tool), which are governance, not server-side enforcement.

### Cited Findings
- Methods table (ms.date 2026-09-29): Key-based; Microsoft Entra agent identity ("Use agent identity when you want authentication scoped to a specific agent. This approach is ideal when you have multiple agents that need different levels of access to the same MCP server."); Microsoft Entra project managed identity ("when you want all agents in a project to share the same access level"); Microsoft Entra client user delegation (`UserEntraToken` / `AgentOnBehalfOfUser`); OAuth identity passthrough; Unauthenticated. CLI: `azd ai connection create my-mcp-connection --kind remote-tool --target https://<mcp-server-endpoint> --auth-type agentic-identity --audience "<entra-audience>"` (or `--auth-type project-managed-identity`). Key-based example stores `Authorization: Bearer <pat>` in the connection; "People who have access to the project can access an API key stored in a project connection." Managed OAuth refuses to send Microsoft-audience tokens to custom servers: `Cannot pass Microsoft token to untrusted MCP endpoint.` Per-tool approval: `require_approval` accepts `always`, `never`, `{"never":[...]}`, `{"always":[...]}`. [Set up MCP server authentication, Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Connection `authType` values and "whose identity reaches the tool": `none`, `custom-keys` (stored header; `--custom-key "Header=Value"` repeatable), `project-managed-identity`, `agentic-identity` ("Per-agent audit and least privilege"; "The system intentionally rejects a user token"), `oauth2`, `user-entra-token`. "Authentication is a property of the connection, not code in your agent." [Toolbox authentication in Microsoft Foundry (ms.date 2026-08-19)](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-authentication)
- Client-side tool allow-list: .NET `MCPToolDefinition.AllowedTools.Add("microsoft_docs_search")`; Python `allowed_tools` ("pass tool names to allow only those tools"; `[]` sends an explicit empty allow-list). [Hosted MCP tools, Agent Framework (ms.date 2026-10-22)](https://learn.microsoft.com/en-us/agent-framework/agents/tools/hosted-mcp-tools)
- Foundry guidance: "After you select a catalog MCP server, limit the enabled tools to the subset your agent needs. This approach enforces least privilege and governance as part of the Foundry configuration flow." [Build and register an MCP server, Microsoft Foundry (ms.date 2026-09-21)](https://learn.microsoft.com/en-us/azure/foundry/mcp/build-your-own-mcp-server)
- Agent identity token exchange: blueprint credential -> agent identity token -> token scoped to the downstream audience -> passed to the MCP server; "Per-agent identities let you scope permissions and audit activity to individual agents." Entra sign-in logs can be filtered by agent identity. [Agent identity concepts](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Agent Framework hosting an MCP server: .NET wraps an `AIAgent` with `McpServerTool` and registers it with an MCP server; Python uses `as_mcp_server()`; the tutorial has no authentication content. [Agent as MCP tool, Agent Framework](https://learn.microsoft.com/en-us/agent-framework/tutorials/agents/agent-as-mcp-tool)

### Inferences
- For the scenario, the cleanest Entra mapping is: two connections (or one connection per agent) with `--auth-type agentic-identity --audience https://news-mcp.example.com` (the server's Application ID URI), app roles assigned to each agent identity, server authorizes on `roles`. The server then sees `azp`/`oid` of the specific agent, so even an `oid` allow-list works.
- Client-side allow-lists (`AllowedTools`, `require_approval`) stop the model from calling a tool but do not stop a request that reaches the server with the shared credential; they are complementary, not a substitute, and they do nothing for the single-tool-with-category shape.
- Agent Framework does not add an authorization layer when exposing an agent as an MCP server; you get whatever the host (ASP.NET Core JWT bearer + C# SDK filters, or Python SDK auth settings) provides.

### Gaps
- Not documented: whether Foundry caches `tools/list` per connection or per agent, or how it reacts to `notifications/tools/list_changed`; since each connection presents one identity consistently, the per-caller list is stable per agent, which sidesteps the question.
- Not documented: whether `agentic-identity` connections work against Functions-hosted servers yet (Functions page says project managed identity only).

## Key question 7: API-key-based entitlement mapping, and what to do when the third-party server cannot be modified (upstream options and gateway products)

### Takeaway
If the server is yours, an API key can map to a category set exactly like a role, but it is a shared bearer secret with no standard rotation or audience binding and nothing in the MCP spec covers it. If the server is third-party and unmodifiable, the only options are (a) separate credentials per agent that the server already differentiates, or (b) an enforcing proxy in front of it (APIM, Kong AI Gateway tool ACLs, Agent Router/Envoy MCPRoute rules, ContextForge, Microsoft MCP Gateway), and only some gateways go below tool level.

### Cited Findings

API keys:
- Foundry stores shared keys in the project connection (`custom-keys`, header name and value); "Use least-privilege credentials where possible. Rotate tokens regularly. Restrict access to projects that contain shared secrets." [Set up MCP server authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Azure Functions default is one shared system key (`mcp_extension`) for the whole server; Microsoft: "consider using Microsoft Entra ID or OAuth identity authentication to provide enhanced security to your MCP server endpoints in production." [Connect an MCP server on Azure Functions to Foundry](https://learn.microsoft.com/en-us/azure/azure-functions/functions-mcp-foundry-tools)
- The MCP spec's token-theft guidance: short-lived tokens, secure storage; the spec has no API-key profile. [MCP Authorization 2025-06-18, Token Theft](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)

Gateways and proxies (one line each; APIM is covered by another researcher):
- Kong AI Gateway 3.13 "MCP Tool ACLs" (2026-01-14): per-tool allow lists by consumer group with `default_acl` deny; "Kong filters the tool list in the response from the upstream API based on the authenticated user's permissions, so clients never see restricted tools"; tool level only, no argument-level restrictions described. [Kong: Introducing MCP Tool ACLs](https://konghq.com/blog/product-releases/mcp-tool-acls-ai-gateway)
- Agent Router (formerly Envoy AI Gateway, now an Agentic AI Foundation project): `MCPRoute` (`aigateway.envoyproxy.io/v1beta1`) with `spec.securityPolicy.authorization` rules matching JWT `scopes`/`claims` against `backend` and `tool` names, optional CEL expressions, ordered first-match Allow/Deny with `defaultAction`; per-backend `toolSelector` `include`/`includeRegex`. The page does not state whether `tools/list` is filtered by authorization rules. [Agent Router MCP capabilities](https://theagentrouter.ai/docs/capabilities/mcp/)
- IBM ContextForge: two layers, token scoping (JWT `teams` claim, `scopes` list, visibility `public`/`team`/`private`) and RBAC (`platform_admin`, `team_admin`, `developer`, `viewer`; permissions such as `tools.execute`, `servers.use`); a third-party benchmark credits it with per-tool authorization and argument validation. [ContextForge RBAC](https://ibm.github.io/mcp-context-forge/latest/manage/rbac/); [AIMultiple MCP gateway benchmark](https://aimultiple.com/mcp-gateway)
- Microsoft MCP Gateway (open source, Kubernetes/AKS): "a reverse proxy and management layer for Model Context Protocol (MCP) servers"; Entra ID bearer tokens; per-resource `requiredRoles` (e.g. `mcp.engineer`, `mcp.admin`) on each adapter and each registered tool; requires `2026-07-28` clients; no per-tool policy inside a single upstream server documented. [microsoft/mcp-gateway docs](https://microsoft.github.io/mcp-gateway/)
- Kuadrant MCP Gateway (Red Hat, Envoy-based): aggregates MCP servers behind one endpoint with auth/authz policies. [Red Hat: advanced authentication and authorization for an MCP gateway (2025-12-12)](https://developers.redhat.com/articles/2025/12/12/advanced-authentication-authorization-mcp-gateway)
- Lasso MCP Gateway: sources conflict; one benchmark says its plugin surface is guardrails and tracing with no authorization step, a vendor guide says it has tool authorization with parameter validation. [AIMultiple benchmark](https://aimultiple.com/mcp-gateway); [getmaxim.ai list](https://www.getmaxim.ai/articles/top-5-mcp-gateways-for-built-in-routing-and-control/)
- Spec support for gateways: 2026-07-28 requires `Mcp-Method` and `Mcp-Name` headers on Streamable HTTP POSTs so intermediaries can route and authorize by method and tool name without parsing bodies (SEP-2243); tool parameters can be mirrored into `Mcp-Param-{name}` headers via `x-mcp-header`, with a warning not to use it for sensitive values. [2026-07-28 Changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog); [MCP Tools 2026-07-28, x-mcp-header](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)
- Foundry toolbox can front MCP servers with APIM ("Bring-your-own AI gateway ... for rate limiting, logging, and network policy"). [Toolbox authentication in Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-authentication)

### Inferences
- API-key-to-entitlement in your own server (illustrative): a table `{key_hash: {"categories": [...], "expires": ...}}`, keys stored hashed, looked up per request, rotated by issuing a new key and overlapping validity; the Foundry connection holds the key. Limits: any project member can read the connection secret; no audience binding, so a leaked key works from anywhere; no standard revocation signal to the client; the MCP spec gives you no challenge format for "insufficient key", so failures must be plain 401/403.
- When the third-party server cannot change, there are exactly two things that can happen upstream:
  1. Credential separation the server already supports: if the vendor issues keys or OAuth clients with different entitlements (e.g. a "sports-only" key), create one Foundry connection per agent with the matching credential. This works for both tool shapes only if the vendor's entitlement model already covers categories.
  2. An enforcing proxy that terminates the agent's identity (Entra token or per-connection key) and holds the vendor credential: tool-level rules handle the one-tool-per-category shape (Kong, Agent Router, APIM policies on `Mcp-Name`); the single-tool-with-category shape needs a gateway that can read the JSON-RPC body or the `Mcp-Param-Category` header (if the vendor's tool declares `x-mcp-header` on `category`, which you cannot force) and apply argument-level policy (Agent Router CEL, ContextForge argument validation, APIM policy expressions). Response filtering (dropping disallowed categories from results) is only possible in a proxy that parses responses; none of the gateway sources describe that.
- A gateway that filters `tools/list` must set `cacheScope: "private"` on the rewritten result (or disable shared caching) for the same reason as a server that does so.

### Gaps
- I did not verify current Kong, Agent Router, or ContextForge documentation for argument-level (JSON body) authorization; only Agent Router's CEL support is documented at a level that suggests it, and the benchmark claim for ContextForge is secondary.
- No source enumerates which gateways rewrite `tools/list` responses versus only blocking `tools/call`; Kong is the only one that states list filtering explicitly.

## Key question 8: Microsoft guidance on agent-level authorization for MCP tools

### Takeaway
Microsoft's position (Entra MCP guide 2026-09-01, Security blog 2026-07-16, Foundry agent-identity doc 2026-10-28) is consistent: give each agent its own Entra identity, grant it app roles or RBAC per downstream service, re-check claims on every call at the tool/server, and keep the agent's enabled tool set minimal; none of the pages prescribe a per-tool or per-category authorization model inside the MCP server beyond "check the `roles` claim before you run a tool".

### Cited Findings
- Microsoft Security blog (2026-07-16, Yser and Kohlenberg): each agent should be "a unique, dedicated agent principal with a named owner and an explicit purpose"; roles should be "least-privilege, task-based roles that are scoped to the specific resources and data the agent needs"; expose "a curated and approved set of tools/actions to the agent" with "explicit allowlists for high-impact operations"; downstream tools "must re-check claims, roles, and scope on each call"; logs should capture agent identity, role, effective scope, resource, action, on-behalf-of user and correlation IDs. The post does not mention MCP or Entra Agent ID by name. [Least privilege for AI agents: Identity, access, and tool binding](https://www.microsoft.com/en-us/security/blog/2026/07/16/least-privilege-for-ai-agents-identity-access-and-tool-binding)
- Entra MCP guide: "protect it like any other API: require an OAuth 2.0 access token on every request, and validate that token before you run a tool"; app roles "can be used to limit the access an MCP client has against your MCP server". [Secure an MCP server with Microsoft Entra ID](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- Foundry: "Apply least privilege to the identity used for each tool call"; Conditional Access, identity protection and governance apply to agent identities; Entra sign-in logs show "which agent identity obtained a token for which resource". [Agent identity concepts](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Foundry's "MCP Server best practices and security guidance" page (ms.date 2026-08-21) is about the hosted Foundry MCP Server (`https://mcp.ai.azure.com`): RBAC on Foundry resources, Conditional Access on app ID `fcdfa2de-b65b-4b54-9a1c-81c8a18282d9`, no network isolation; it does not cover authorization design for custom servers. [Foundry MCP Server best practices and security guidance](https://learn.microsoft.com/en-us/azure/foundry/mcp/security-best-practices)
- Foundry build-your-own guidance: "Require authentication", "Implement least privilege for downstream calls", "Log and monitor tool calls", and limit enabled tools per agent in Foundry configuration. [Build and register an MCP server, Microsoft Foundry](https://learn.microsoft.com/en-us/azure/foundry/mcp/build-your-own-mcp-server)
- App Service: "Your application code is often the best place to handle custom authorization logic." [Configure Microsoft Entra authentication, App Service](https://learn.microsoft.com/en-us/azure/app-service/configure-authentication-provider-aad)

### Inferences
- Microsoft's guidance plus the spec converge on one architecture for the scenario: agent identity per Foundry agent -> app role per category on the MCP server registration -> server validates v2 token and filters `tools/list` and `tools/call` (or the `category` argument) on `roles` -> Foundry-side `AllowedTools`/approval as defence in depth -> Entra sign-in logs and Foundry tracing for audit.
- Microsoft does not endorse (or forbid) returning a different tool list per caller; the 2026-07-28 spec allows it, and the C# SDK (Microsoft-maintained) implements it by default once `AddAuthorizationFilters()` is on.

### Gaps
- I found no Azure Well-Architected or Cloud Adoption Framework page specific to MCP tool authorization; the search surfaced only the Security blog and general MCP vendor content.
- No Microsoft sample demonstrates argument-level (data-category) authorization in an MCP tool.
