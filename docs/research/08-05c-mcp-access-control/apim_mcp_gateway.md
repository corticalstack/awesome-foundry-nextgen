# Azure API Management (and other Azure-native gateways) as a policy-enforcing gateway between Foundry agents and an unmodifiable third-party MCP server

State as of 2026-10-29. Scenario: third-party news MCP server (remote streamable HTTP), categories exposed either as one tool per category or as one tool with a `category` argument. Agent A unrestricted, Agent B limited to a subset. The news server authenticates APIM with a single third-party API key; per-agent entitlement must be decided in APIM.

Reading key: "Classic APIM" below means the Developer/Basic/Standard/Premium and Basic v2/Standard v2/Premium v2 tiers of the API Management *service* resource. "AI Gateway tier" means the separate preview product (`Microsoft.ApiManagement/aigateways`) that shares the resource provider but has its own portal, resource types and policy model.

## KQ1. APIM MCP server feature set as of October 2026 (pass-through, REST-as-MCP, transports, GA/preview, tiers, limits)

### Takeaway
APIM MCP governance (REST API as MCP server, and pass-through of an existing remote MCP server) is GA since November 2025 on all classic and v2 tiers (not Consumption, not workspaces), supports streamable HTTP and the deprecated HTTP+SSE transport, and gained products, versioning, observability, Bicep/REST automation, native OAuth 2.1 and content safety for MCP during 2026. A separate "AI Gateway tier" (public preview, East US 2 and Sweden Central only) adds federated MCP servers and admin-level tool blocking, but its runtime keys are gateway-wide, so it does not give per-caller tool entitlements either.

### Cited Findings

Two built-in ways to expose MCP servers: "REST API as MCP server" (API operations become tools) and "Existing MCP server" (expose an MCP-compatible server such as LangChain, LangServe, Logic Apps, Functions). [mcp-server-overview](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)

### Inferences
- For the news scenario on classic/v2 APIM, pass-through is the right mode: the third-party server is unmodifiable and its tool surface is defined by the backend, so APIM does not need per-tool sub-resources.
- Agent 365 tool blocking is tenant-admin, server-wide blocking of a tool for all callers. It is not a per-agent entitlement mechanism, so it does not solve "Agent A full, Agent B subset" by itself.
- The Agent 365 doc's "static list of allowed tools" is an AI Gateway tier MCP server property (static tool manifest) rather than a classic APIM feature; the classic "Tools blade" selection applies to REST-backed servers, and the pass-through Bicep examples explicitly leave tools to the backend.

### Gaps
- No document states whether the classic pass-through "Tools blade" selection (which tools are exposed) actually filters `tools/list` from an external backend, or whether it only applies to REST-backed servers. The pass-through resource model says the backend determines the tool surface.
- The AI Gateway tier's "manage models and tools" page redirected to the concepts page and `ai-gateway-setup` returned 404 during this research, so static allowed-tool lists and per-key scoping in that tier are documented only by the Agent 365 page, the concepts page and the in-product docs (not fetched).
- No dedicated September 2026 service release notes were found on GitHub (`release-service-2026-09` returned no release).

## KQ2. Which policies apply to MCP servers, at what scope; per-tool scope; reading the JSON-RPC body; rewriting `tools/list`

### Takeaway
In classic/v2 APIM, policies for an MCP server are a normal API-scope policy document (inbound/backend/outbound/on-error) that runs for every MCP request; there is no per-tool policy scope and no MCP-specific policy or `context` helper. You can read the JSON-RPC request body with `context.Request.Body.As<JObject>(preserveContent: true)` and branch on `method`, `params.name` and `params.arguments.*` in inbound, but the docs explicitly tell you not to touch `context.Response.Body` at MCP scope because it breaks streaming, which rules out rewriting `tools/list` in outbound.

### Cited Findings
- "Currently, policies apply to all API operations exposed as tools in the MCP server." Suggested policies: rate limiting/quota, JWT auth, IP filtering, caching. [mcp-server-overview](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview)
- MCP server policies are edited under the MCP server's "Policies" blade in XML; "API Management evaluates policies configured at the global (all APIs) scope before it evaluates policies at the MCP server scope." Caution: "Don't access the response body by using the `context.Response.Body` variable within MCP server policies. Doing so triggers response buffering, which interferes with the streaming behavior required by MCP servers and might cause them to malfunction." [expose-existing-mcp-server](https://learn.microsoft.com/en-us/azure/api-management/expose-existing-mcp-server)
- REST doc: "Apply a policy at MCP scope ... The server evaluates policies at this scope for every tool invocation." Policies are `Microsoft.ApiManagement/service/apis/policies` on the MCP API. [manage-mcp-servers-rest-api](https://learn.microsoft.com/en-us/azure/api-management/manage-mcp-servers-rest-api)
- General policy scopes are global, workspace, product, API, operation; policies at product scope are not applied when the request uses an API-scoped, all-APIs or built-in all-access subscription. [api-management-howto-policies](https://learn.microsoft.com/en-us/azure/api-management/api-management-howto-policies)
- The policy reference (ms.date 2026-08-24) lists no MCP-specific policy; the only AI-gateway policies are `llm-token-limit`, `llm-emit-token-metric`, `llm-semantic-cache-*` and `llm-content-safety`. [api-management-policies](https://learn.microsoft.com/en-us/azure/api-management/api-management-policies)
- `llm-content-safety` "can also enforce content safety checks on requests or responses for MCP tools or A2A Agent APIs managed in API Management"; scopes global, workspace, product, API (no operation scope); blocked content returns 403; for streaming responses the handler stops forwarding events instead of returning 403. [llm-content-safety-policy](https://learn.microsoft.com/en-us/azure/api-management/llm-content-safety-policy)
- Policy expressions: `IMessageBody.As<T>(bool preserveContent = false)` for `string, byte[], JObject, JToken, JArray, XNode, ...`; by default `As<T>` consumes the original stream, so set `preserveContent: true` to keep the body for the backend. `Newtonsoft.Json.Linq.JObject/JToken/JArray` are fully allowed. `context.Request` exposes `Body`, `Certificate`, `Headers`, `IpAddress`, `Method`, `Url`, and a `Foundry` member (`context.Request.Foundry.Deployment`: the model deployment ID). There is no MCP member on `context`. `context.Subscription` exposes `Id`, `Name`, `Key`, `PrimaryKey`, `SecondaryKey`; `context.Product` exposes `Id`, `Name`; `context.Variables.GetValueOrDefault<T>`; `AsJwt()` / `Jwt.Claims.GetValueOrDefault(claimName, default)`. [api-management-policy-expressions](https://learn.microsoft.com/en-us/azure/api-management/api-management-policy-expressions)
- `set-body` is allowed in inbound, outbound and backend at all scopes; the doc's "Filter response based on product" example reads `context.Response.Body.As<JObject>()` in outbound and removes properties when `context.Product.Name` is `Starter`; Liquid templates are supported for JSON/XML reshaping but "do not work when used inside a return-response policy". [set-body-policy](https://learn.microsoft.com/en-us/azure/api-management/set-body-policy)
- Monitoring doc warning: "Don't access `context.Response.Body` from policies attached to MCP scope. MCP responses are streamed, and reading the body breaks the stream." Built-in MCP telemetry dimensions include `gen_ai.operation.name` (tools/list or tools/call), `gen_ai.tool.name`, `gen_ai.conversation.id` (MCP session ID), `auth.type`, `user_agent.name`, and (opt-in payload logging) `gen_ai.tool.call.arguments` / `gen_ai.tool.call.result`. [monitor-mcp-servers](https://learn.microsoft.com/en-us/azure/api-management/monitor-mcp-servers)
- Community implementation (DEV post, 2025-09-22) of per-tool role checks on an APIM MCP server: `<set-variable name="mcpBody" value="@(context.Request.Body.As<JObject>(preserveContent: true))" />`, branch on `method == "tools/call"`, read `params.name`, validate the JWT with `validate-jwt`, compare the token's `roles` claim to the tool name, and `return-response` 403 on mismatch. The post does not filter `tools/list`. [dev.to imdj](https://dev.to/imdj/fine-grained-role-control-for-mcp-tools-with-apim-2pn7) (community, not Microsoft guidance)
- Agent 365's gateway-side denial shape (HTTP 200, JSON-RPC `result.isError: true`, text "Tool 'delete_file' is blocked by the gateway. Do not retry this tool.") is explicitly chosen so "agents [are] aware of the policy and restrain them from retrying". [agent-365](https://learn.microsoft.com/en-us/azure/api-management/agent-365)
- Foundry governance doc shows MCP-scope policy examples: `rate-limit-by-key` on IP, `ip-filter`, `set-header` for correlation ID and header removal, `choose` + `set-backend-service` for header-based routing. [Foundry tools governance](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/governance)
- Alternative gateways do filter `tools/list` per identity: agentgateway removes unauthorized tools from list responses after the target responds and answers a denied call with JSON-RPC error `-32602` "unknown resource". [agentgateway tool access](https://agentgateway.dev/docs/kubernetes/latest/mcp/tool-access/)

### Inferences
- Tool-level and argument-level authorization in classic/v2 APIM is a policy-expression pattern, not a product feature: read the JSON-RPC body in inbound (`preserveContent: true`), branch on `method`, `params.name`, `params.arguments.category`, and reject with `return-response`. Nothing in the docs prohibits reading the *request* body; the prohibition is on the response body.
- Illustrative (untested) inbound fragment for the scenario, where `allowedCats` is derived from the caller (see KQ3):

  ```xml
  <set-variable name="rpc" value="@(context.Request.Method == "POST" ? context.Request.Body.As<JObject>(preserveContent: true) : null)" />
  <choose>
    <when condition="@{
      var rpc = (JObject)context.Variables["rpc"];
      if (rpc == null || (string)rpc["method"] != "tools/call") return false;
      var allowed = ((string)context.Variables["allowedCats"]).Split(',');   // e.g. "sports,tech" or "*"
      var tool = (string)rpc.SelectToken("params.name");
      var cat  = (string)rpc.SelectToken("params.arguments.category") ?? tool;  // one-tool-with-arg or one-tool-per-category
      return !(allowed.Contains("*") || allowed.Contains(cat));
    }">
      <return-response>
        <set-status code="200" reason="OK" />
        <set-header name="Content-Type" exists-action="override"><value>application/json</value></set-header>
        <set-body>@{
          var id = ((JObject)context.Variables["rpc"])["id"];
          return new JObject(new JProperty("jsonrpc","2.0"), new JProperty("id", id),
            new JProperty("result", new JObject(new JProperty("isError", true),
              new JProperty("content", new JArray(new JObject(new JProperty("type","text"),
                new JProperty("text","Category not permitted for this agent. Do not retry."))))))).ToString();
        }</set-body>
      </return-response>
    </when>
  </choose>
  ```
  Returning a JSON-RPC `isError` result over HTTP 200 mirrors the Agent 365 denial shape; a 403 is also possible but surfaces as a transport error to the agent.
- Rewriting `tools/list` per caller in APIM outbound is effectively unsupported for MCP servers: both the pass-through doc and the monitoring doc say reading the response body breaks the stream, and pass-through responses may be SSE events rather than a single JSON document. Treat denial-on-call as the enforceable control and keep the tool list unfiltered (Agent B's model will see tools it cannot call unless Foundry `allowed_tools` is also set, see KQ4).
- Because the JSON-RPC `method` is in the body, APIM cannot use operation-scope policies to separate `tools/list` from `tools/call`; everything lands on the MCP server scope (plus product/global).

### Gaps
- No Microsoft doc confirms that reading `context.Request.Body` with `preserveContent: true` is safe for MCP pass-through at scale (only the community post demonstrates it). The March 2026 release note fixing "MCP POST request bodies were not forwarded to backend APIs" shows body handling for MCP was still being stabilized in early 2026.
- No doc describes the response shape APIM returns to the client for `tools/list` on pass-through (plain JSON vs SSE), which determines whether any outbound transformation is feasible.
- The roadmap item "Tool-level access policies for granular governance" (Aug 2025) has no matching release note or doc through October 2026; the only shipped tool-level control is Agent 365 blocking on the AI Gateway tier.

## KQ3. Identifying the calling Foundry agent (subscription key, Entra token claims, client certificate, custom header) and mapping identity to entitlements

### Takeaway
APIM can identify the caller by subscription key (`Ocp-Apim-Subscription-Key`, product/subscription per agent), by an Entra token from the agent identity or project managed identity (`validate-azure-ad-token` with `client-application-ids`, `audiences`, `required-claims`, then read `oid`/`appid`/`azp`/`roles` from the `Jwt` object), by client certificate (`validate-client-certificate`, `context.Request.Certificate`), or by any custom header Foundry injects from a key-based project connection. Mapping to entitlements is done in policy (named values, policy fragments, `choose`), and rate limits can be keyed on the same identity.

### Cited Findings
- Key-based inbound auth: "If the MCP server is protected with an API Management subscription key passed in the `Ocp-Apim-Subscription-Key` header, MCP clients can present the key in incoming requests, and API Management validates the key." Token-based: "MCP clients can present OAuth tokens or JWTs issued by Microsoft Entra ID by using an `Authorization` header and validated by API Management" with a `validate-azure-ad-token` example using `client-application-ids`. "Request headers are automatically forwarded (with certain exclusions) to MCP tool invocations." [secure-mcp-servers](https://learn.microsoft.com/en-us/azure/api-management/secure-mcp-servers)
- Products and subscriptions: binding an MCP server to a product means "If the product requires subscriptions, the client must use a valid subscription key for that product"; the Bicep examples set `subscriptionRequired: true`. [manage-mcp-servers-rest-api](https://learn.microsoft.com/en-us/azure/api-management/manage-mcp-servers-rest-api)
- `validate-azure-ad-token` (ms.date 2026-08-18): attributes `tenant-id`, `header-name`/`query-parameter-name`/`token-value`, `failed-validation-httpcode`, `output-token-variable-name` (receives a `Jwt` object); elements `client-application-ids`, `backend-application-ids`, `audiences` (policy expressions allowed), `required-claims` with `claim name=... match="all|any" separator=...`, `decryption-keys`. Usage note: apply at API level for the whole API "or you can apply it on the API operation level and use `claims` for more granular control." [validate-azure-ad-token-policy](https://learn.microsoft.com/en-us/azure/api-management/validate-azure-ad-token-policy)
- `validate-jwt` (other IdPs), `validate-client-certificate` ("Enforces that a certificate presented by a client ... matches specified validation rules and claims"), `check-header`, `ip-filter`, `get-authorization-context` are all listed as authentication/authorization policies on classic, v2, consumption and self-hosted gateways. [api-management-policies](https://learn.microsoft.com/en-us/azure/api-management/api-management-policies)
- Foundry's own recipe for validating a Foundry managed-identity token in APIM: enable the project's system- or user-assigned MI, find the MI's application (client) ID by searching its object ID in Entra enterprise applications, then use `validate-azure-ad-token` with `<client-application-ids><application-id>{{managed-identity-client-id}}` and `<audiences><audience>{{audience-configured-in-foundry-connection}}`. [Foundry BYOM via AI gateway](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/ai-gateway)
- Foundry MCP auth types (ms.date 2026-09-29): Key-based (`custom-keys`, arbitrary header name/value stored in a project connection, e.g. `Authorization: Bearer <PAT>`; "People who have access to the project can access an API key stored in a project connection"); Microsoft Entra agent identity (`--auth-type agentic-identity --audience "<entra-audience>"`, "ideal when you have multiple agents that need different levels of access to the same MCP server"); Microsoft Entra project managed identity (`--auth-type project-managed-identity --audience ...`, "when you want all agents in a project to share the same access level"); client user delegation; OAuth identity passthrough; unauthenticated. [Foundry mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Agent identity (ms.date 2026-10-28): "An agent identity is a special service principal in Microsoft Entra ID, created under an agent blueprint." Runtime token exchange: blueprint credentials -> agent identity token -> "a new access token scoped to the audience of the downstream service" -> "Agent Service passes the scoped access token to the MCP server or A2A endpoint. The downstream resource validates the token and checks the agent identity's RBAC role assignments". "In the current agent object model, creating an agent provisions a unique agent blueprint and the identity for its default instance." Use "the object ID of the agent identity used for the tool call as the assignee" for RBAC. Agent sign-ins appear in Entra sign-in logs filtered by agent type. [Foundry agent-identity concepts](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Entra guidance for MCP servers (ms.date 2026-09-01): validate signature, `iss`, `tid`, `aud`, expiry, then authorize on `sub`/`oid` and `roles` (app-only) or `scp` (delegated). App roles can be defined on the MCP server's app registration with "Allowed member types" = Applications, assigned "to the MCP client's agent identity", and "Assigned roles appear in the `roles` claim of the access token"; agent identities request tokens via client credentials with `scope=https://mcp.contoso.com/.default`. The app registration must use v2 access tokens (`requestedAccessTokenVersion: 2`) and an Application ID URI equal to the MCP server URL for RFC 8707 `resource` matching. [secure-mcp-server-with-entra-id](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- Rate limiting per caller: `rate-limit-by-key` / `quota-by-key` take an arbitrary `counter-key` expression (classic, v2, self-hosted; not Consumption); `rate-limit` / `quota` are per subscription. The pass-through doc's example uses `counter-key="@(context.Request.IpAddress)"`. [api-management-policies](https://learn.microsoft.com/en-us/azure/api-management/api-management-policies); [expose-existing-mcp-server](https://learn.microsoft.com/en-us/azure/api-management/expose-existing-mcp-server)
- Policy control flow: `choose`, `include-fragment` (policy fragments), `set-variable` are available on all gateways. [api-management-policies](https://learn.microsoft.com/en-us/azure/api-management/api-management-policies)
- Community report (Q&A, March 2026): a Foundry agent calling a REST-exported APIM MCP server with key-based auth failed until the extra `x-api-key` header was removed, leaving only `Ocp-Apim-Subscription-Key`; a CORS policy was also suggested. [Microsoft Q&A 5827099](https://learn.microsoft.com/en-us/answers/questions/5827099/trouble-connecting-foundry-agent-to-mcp-server-beh) (community, unverified)

### Inferences
- Three workable identity designs for "Agent A full / Agent B subset":
  1. Subscription keys: two products (`news-all`, `news-limited`) bound to the same pass-through MCP server, one subscription per agent, key stored in each agent's `custom-keys` project connection as `Ocp-Apim-Subscription-Key`. Entitlement = `context.Product.Id` or `context.Subscription.Id`. Simplest; weakness is that anyone with project access can read the key.
  2. Entra agent identity: Foundry connection with `--auth-type agentic-identity --audience <app-id-uri-of-the-APIM-facing-app>`; APIM `validate-azure-ad-token` with `audiences` = that URI and `required-claims` or an expression over `roles` (app roles `News.All`, `News.Sports` assigned per agent identity) or over `oid`/`appid`. This is the least-privilege path and gives per-agent audit in Entra sign-in logs.
  3. Project managed identity: same validation, but all agents in the project share the identity, so it cannot distinguish Agent A from Agent B within one project.
- Entitlement mapping belongs in a policy fragment or named value: e.g. a named value `news-entitlements` holding JSON `{ "<oid-or-subscription-id>": "sports,tech" }` parsed with `JObject.Parse`, or `roles` claim values used directly as the category allow-list.
- Client certificates are supported by APIM but Foundry's MCP connection types list no client-certificate option, so mTLS between Foundry Agent Service and APIM is not a documented path.

### Gaps
- No Microsoft doc shows Foundry requesting an agent-identity token for a *custom* audience (an app registration you own) rather than a Microsoft resource audience; the examples use `https://cognitiveservices.azure.com`. The managed-OAuth restriction "Cannot pass Microsoft token to untrusted MCP endpoint" applies to Microsoft audiences, so a custom audience should be allowed, but this needs a test.

## KQ4. Foundry-side wiring: connecting an agent to an APIM-hosted MCP server (subscription key, Entra token, OAuth), tools catalog / API Center, AI gateway governance

### Takeaway
A Foundry agent connects to the APIM MCP endpoint as an ordinary remote MCP tool (`server_url`, `project_connection_id`, optional `allowed_tools`), with the project connection carrying either a subscription-key header (`custom-keys`), an Entra identity (`agentic-identity` / `project-managed-identity` with an audience), or OAuth. ### Cited Findings

### Inferences
- The scenario does not need the Foundry "AI gateway governance" preview: creating the pass-through MCP server in APIM manually and pointing each agent's connection at `https://<apim>.azure-api.net/<base-path>/mcp` achieves the same routing with full control over policies and auth, and works for existing agents.
- `allowed_tools` is enforced by Agent Service for that agent definition (the model never sees the excluded tools), which cleanly solves the "one tool per category" variant for Agent B on the client side; it cannot restrict a `category` *argument*. It is also editable by anyone who can edit the agent, so APIM remains the authoritative control.
- A `custom-keys` connection with `Ocp-Apim-Subscription-Key` is the lowest-friction wiring and is what the only community report of Foundry -> APIM MCP used successfully.

### Gaps
- No doc explains what identity or headers Foundry sends when the AI-gateway-routed MCP tool path is used (whether Foundry creates an APIM subscription per project or uses MI); the governance doc only says the server must support one of the listed auth methods.
- No doc states whether Foundry honours `Mcp-Session-Id` across calls or re-initializes the MCP session per tool call, which affects how APIM session telemetry and any session-keyed policy behave.

## KQ5. APIM "MCP authorization" (OAuth 2.1, PRM), credential manager for outbound credentials, labs and samples

### Takeaway
Inbound: APIM validates subscription keys or Entra JWTs; since March 2026 it also has native OAuth 2.1 (2025-06-18 spec) for MCP servers, and the PRM/OAuth-server patterns are documented through samples and AI-Gateway labs. Outbound: credential manager handles OAuth 2.0 (authorization code and client credentials) via `get-authorization-context`; a static third-party API key is not a credential-manager object and is injected with `set-header` from a named value.

### Cited Findings
- Inbound options and samples (ms.date 2026-09-11): key-based; `validate-azure-ad-token`; forward `Authorization` to backend with `set-header` or via credential manager; linked samples: "MCP server authorization with Protected Resource Metadata (PRM) sample" (blackchoey/remote-mcp-apim-oauth-prm), AI-Gateway labs `mcp-prm-oauth` and `mcp-client-authorization`, and "Secure Remote MCP Servers using Azure API Management (Experimental)". [mcp-prm-oauth](https://github.com/Azure-Samples/AI-Gateway/tree/main/labs/mcp-prm-oauth); [mcp-client-authorization](https://github.com/Azure-Samples/AI-Gateway/tree/main/labs/mcp-client-authorization)

### Inferences
- For the news scenario the outbound side is trivial: store the third-party key as a secret named value (optionally Key Vault-backed) and add `<set-header name="X-Api-Key" exists-action="override"><value>{{news-api-key}}</value></set-header>` (or `Authorization: Bearer {{...}}`) in inbound. Credential manager is only needed if the news server used OAuth 2.0.
- Inbound OAuth 2.1/PRM on APIM is aimed at interactive MCP clients (VS Code, Copilot Studio). For Foundry server-side agents, subscription key or Entra agent-identity tokens are simpler and avoid the client-side PRM discovery issues reported.
- Strip any inbound `Ocp-Apim-Subscription-Key`/`Authorization` headers before forwarding so the agent's credential does not leak to the third-party server (headers are forwarded by default with "certain exclusions" that are not enumerated).

## KQ6. Alternatives to APIM (custom proxy on ACA/Functions, Front Door/App Gateway, Microsoft MCP Gateway, agentgateway, Foundry Toolbox, Agent 365)

### Takeaway
Only an MCP-aware proxy can filter `tools/list` per caller and inspect arguments; among Azure-native options that means a custom proxy on Container Apps/Functions or an OSS MCP gateway (agentgateway, Microsoft MCP Gateway) on AKS/ACA. L7 gateways (Front Door, Application Gateway) are not MCP-aware. Foundry Toolbox and `allowed_tools` restrict what an agent *sees* but are Foundry-side controls, not a boundary in front of the third-party server.

### Cited Findings
- Custom MCP proxy hosting: Foundry docs direct local MCP servers to Azure Container Apps or Azure Functions; Functions hosting is "Key-based only. OAuth needs API Management", ACA needs "Custom authentication implementation"; both "Stateless only". - agentgateway (Kubernetes docs): `AgentgatewayPolicy` with `backend.mcp.authorization` CEL `matchExpressions` such as `jwt.sub == "alice" && mcp.tool.name == "get_me"`; "tool lists are filtered automatically"; a denied call returns JSON-RPC `-32602` "unknown resource"; the tool-access page describes checks on tool name and JWT claims only. [agentgateway tool access](https://agentgateway.dev/docs/kubernetes/latest/mcp/tool-access/). - Azure Front Door and Application Gateway: no source was fetched; by design they operate on HTTP/L7 (WAF rules, headers, paths) and have no JSON-RPC or MCP semantics, so they can only add network-level protection (WAF, private link, TLS) in front of APIM, as in the `ai-foundry-private-mcp` lab.
- A thin custom proxy (FastMCP/MCP SDK on Container Apps) is the only option that gives all three controls per caller (tool filtering in `tools/list`, tool-call denial, argument inspection) without a dependency on preview tiers; cost is owning code, auth and session handling.

- agentgateway's governance (Linux Foundation / CNCF) and license were not confirmed from its docs page.

## KQ7. Operational constraints: sessions, streamable HTTP/SSE through APIM, timeouts, cost, latency, regions

### Takeaway
APIM pass-through forwards MCP requests and headers to the backend and streams responses; its telemetry reads the MCP session ID, but there is no documented session-affinity feature. The documented traps are response-body access and global payload logging (both break streaming), the `forward-request` timeout (default 300 s, more than 240 s may not be honoured), and Foundry's 100-second synchronous tool-call limit. Consumption tier is excluded; AI Gateway tier is free in preview but only in two regions.

### Cited Findings
- Streaming: "Don't access the response body by using the `context.Response.Body` variable within MCP server policies"; if diagnostic logging is enabled at global scope, "set the Number of payload bytes to log setting for Frontend Response to 0"; known issue "MCP server streaming fails when diagnostic logs are enabled". [expose-existing-mcp-server](https://learn.microsoft.com/en-us/azure/api-management/expose-existing-mcp-server)
- Session visibility: every MCP request row carries `gen_ai.conversation.id` = "MCP session ID" and `network.protocol.version`. [monitor-mcp-servers](https://learn.microsoft.com/en-us/azure/api-management/monitor-mcp-servers)
- Header forwarding: "Request headers are automatically forwarded (with certain exclusions) to MCP tool invocations." [secure-mcp-servers](https://learn.microsoft.com/en-us/azure/api-management/secure-mcp-servers)
- Pass-through semantics: "A passthrough server forwards all MCP requests directly to an external MCP backend." [manage-mcp-servers-rest-api](https://learn.microsoft.com/en-us/azure/api-management/manage-mcp-servers-rest-api)
- `forward-request`: `timeout` default 300 s and "Values greater than 240 seconds may not be honored, because the underlying network infrastructure can drop idle connections after this time"; `buffer-response` default `true`, "Set to `false` with backends such as those implementing server-sent events (SSE) that require content to be returned or streamed immediately"; in the v2 gateway inbound HTTP/2 is downgraded to HTTP/1 toward the backend. [forward-request-policy](https://learn.microsoft.com/en-us/azure/api-management/forward-request-policy)
- March 2026: "policy-driven execution timeouts for MCP servers created from APIs, removing fixed runtime constraints"; fixes for "ClientConnectionFailure or premature timeout behavior" and "SSE streaming behavior for MCP endpoints, preventing early connection termination during delayed backend processing". [release-service-2026-03](https://github.com/Azure/API-Management/releases/tag/release-service-2026-03)
- June 2026: `[DONE]` marker no longer emitted for MCP streams (completion via connection close); multi-line SSE serialization fixed. [release-service-2026-06](https://github.com/Azure/API-Management/releases/tag/release-service-2026-06)
- Foundry: "Non-streaming MCP tool calls have a timeout of 100 seconds"; longer operations need background mode (preview) and an MCP tasks-capable server. [Foundry MCP tool](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Tiers and cost signals: MCP features on Developer/Basic/Standard/Premium and v2 tiers (no Consumption). [mcp-server-overview](https://learn.microsoft.com/en-us/azure/api-management/mcp-server-overview). Foundry "Create new" gateway provisions Basic v2 ("designed for development and testing with SLA support"); production guidance is Standard v2 or Premium v2; "AI Gateway includes a free tier for Azure API Management" (see pricing page). [enable-ai-api-management-gateway-portal](https://learn.microsoft.com/en-us/azure/foundry/configuration/enable-ai-api-management-gateway-portal). AI Gateway tier is free during preview, pricing TBD. [Tech Community 4540170](https://techcommunity.microsoft.com/blog/integrationsonazureblog/ai-gateway-tier-of-api-management-now-in-public-preview/4540170)
- Regions: AI Gateway tier only in East US 2 and Sweden Central during preview. [ai-gateway/overview](https://learn.microsoft.com/en-us/azure/ai-gateway/overview). Credential manager unavailable in sovereign clouds and australiacentral, australiacentral2, indiacentral. [credentials-overview](https://learn.microsoft.com/en-us/azure/api-management/credentials-overview)
- Private networking: a private Foundry resource needs Standard v2/Premium v2 with private endpoint or Premium v2 VNet injection. [enable-ai-api-management-gateway-portal](https://learn.microsoft.com/en-us/azure/foundry/configuration/enable-ai-api-management-gateway-portal)
- MCP Inspector: "use version 0.9.0" when testing an APIM-managed MCP server. [expose-existing-mcp-server](https://learn.microsoft.com/en-us/azure/api-management/expose-existing-mcp-server)

### Inferences
- Session IDs: because APIM reads `Mcp-Session-Id` for telemetry and forwards headers, a single-backend third-party server will keep its own sessions across APIM hops. Session affinity across multiple gateway units is a non-issue for pass-through to one backend; it would matter only for load-balanced backend pools.
- Keep `forward-request` at its default `buffer-response="true"`? The SSE guidance says set it to `false` for SSE backends; for MCP servers APIM's MCP runtime handles streaming itself, and the docs do not say to change it. Leave the backend section as `<forward-request />` (as in all official MCP Bicep samples) unless streaming problems appear.
- Latency: an extra hop plus JWT validation and body parsing is small relative to a news API call; the real latency risk is the 100-second Foundry limit versus a slow third-party server, not APIM.

### Gaps
- No doc describes APIM behaviour for the GET (server-to-client SSE stream) and DELETE (session termination) legs of streamable HTTP in pass-through mode.
- No concrete price list was fetched for Basic v2 / Standard v2; the pricing page was not consulted.

## KQ8. Putting it together for the news scenario (Agent A unrestricted, Agent B subset)

### Takeaway
Recommended APIM design: one pass-through MCP server for the third-party news endpoint; two APIM products (or two Entra app roles) to identify Agent A and Agent B; an inbound policy that injects the single third-party key, derives the caller's allowed categories, parses the JSON-RPC body and returns a JSON-RPC `isError` result for disallowed `tools/call` (by tool name or by `arguments.category`); per-caller `rate-limit-by-key`; and Foundry `allowed_tools` on Agent B as a client-side complement. Filtering `tools/list` per caller is not achievable in APIM policy today.

### Cited Findings
- Products as the per-consumer packaging for MCP servers (GA June 2026) and subscription keys as the caller credential. [Tech Community 4526931](https://techcommunity.microsoft.com/blog/integrationsonazureblog/productize-observe-version-and-automate-mcp-servers-in-azure-api-management/4526931); [secure-mcp-servers](https://learn.microsoft.com/en-us/azure/api-management/secure-mcp-servers)
- Agent identity "ideal when you have multiple agents that need different levels of access to the same MCP server". [Foundry mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- App roles on the protected app registration assigned to agent identities surface in the `roles` claim. [secure-mcp-server-with-entra-id](https://learn.microsoft.com/en-us/entra/agent-id/secure-mcp-server-with-entra-id)
- `validate-azure-ad-token` `required-claims` with `match="any"` and `output-token-variable-name` for reading claims in later expressions. [validate-azure-ad-token-policy](https://learn.microsoft.com/en-us/azure/api-management/validate-azure-ad-token-policy)
- Request body readable as `JObject` with `preserveContent: true`; response body must not be read at MCP scope. [api-management-policy-expressions](https://learn.microsoft.com/en-us/azure/api-management/api-management-policy-expressions); [monitor-mcp-servers](https://learn.microsoft.com/en-us/azure/api-management/monitor-mcp-servers)
- Denial shape used by Microsoft's own gateway-side tool blocking: HTTP 200 + JSON-RPC `result.isError: true` + `_meta` denial code. [agent-365](https://learn.microsoft.com/en-us/azure/api-management/agent-365)
- `allowed_tools` on the Foundry MCP tool as a per-agent allow-list (nonempty list). [Foundry MCP tool](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Payload logging of tool arguments is opt-in per MCP server and can be queried by `gen_ai.tool.name` / `gen_ai.tool.call.arguments` for audit of category requests. [monitor-mcp-servers](https://learn.microsoft.com/en-us/azure/api-management/monitor-mcp-servers)

### Inferences
- Illustrative (untested) skeleton of the MCP-scope policy, subscription-key variant; swap the `set-variable allowedCats` line for a `roles`-claim expression in the Entra variant:

  ```xml
  <inbound>
    <base />
    <!-- 1. identify caller: product bound to this MCP server -->
    <set-variable name="allowedCats" value="@(context.Product.Id == "news-all" ? "*" : "sports,tech")" />
    <!-- Entra variant instead of products:
    <validate-azure-ad-token tenant-id="{{tenant}}" output-token-variable-name="jwt">
      <audiences><audience>{{news-gw-app-id-uri}}</audience></audiences>
      <required-claims><claim name="roles" match="any"><value>News.All</value><value>News.Limited</value></claim></required-claims>
    </validate-azure-ad-token>
    <set-variable name="allowedCats" value="@(((Jwt)context.Variables["jwt"]).Claims.GetValueOrDefault("roles","").Contains("News.All") ? "*" : "sports,tech")" />

    <!-- 2. per-caller rate limit -->
    <rate-limit-by-key calls="60" renewal-period="60" counter-key="@(context.Subscription?.Id ?? context.Request.IpAddress)" />
    <!-- 3. tool / argument entitlement (see KQ2 snippet) -->
    <include-fragment fragment-id="news-mcp-entitlement" />
    <!-- 4. outbound credential to third party; strip inbound creds -->
    <set-header name="Ocp-Apim-Subscription-Key" exists-action="delete" />
    <set-header name="Authorization" exists-action="delete" />
    <set-header name="X-Api-Key" exists-action="override"><value>{{news-third-party-key}}</value></set-header>
  </inbound>
  <backend><forward-request /></backend>
  <outbound><base /></outbound>
  ```
- "One tool per category" variant: Agent B's `allowed_tools` plus the APIM `params.name` check cover it fully. "One tool with a category argument" variant: only the APIM `params.arguments.category` check enforces it; `allowed_tools` cannot help, and the model will still see the full tool description.
- Rewriting the argument (for example forcing `category` to an allowed value) is possible in the same inbound expression by returning a modified body from `set-body` (the set-body doc shows `JObject` mutation on requests), but a rejection is clearer for the model than a silent rewrite.
- Prefer the Entra agent-identity variant for production: per-agent audit in Entra sign-in logs, no shared secret in the project connection, and entitlements expressed as app roles that security teams can govern outside the policy XML.

### Gaps
- End-to-end validation of Foundry agent identity -> APIM `validate-azure-ad-token` with a custom audience for an MCP tool has not been demonstrated in any fetched Microsoft source; the only verified Foundry -> APIM MCP report used a subscription key.
- Whether APIM's MCP runtime wraps `return-response` bodies correctly for a client that sent `Accept: text/event-stream` (SSE-framed response expected) is undocumented; the Agent 365 denial example shows a plain JSON body over HTTP 200, which suggests APIM can answer `tools/call` with plain JSON, but this should be tested with the Foundry client.
