# Foundry-side MCP tool authentication and access-control surface (state as of 2026-10-29)

Scope: the client side of the Microsoft Foundry Agent Service (new object model: versioned agents, Responses API, prompt agents and hosted agents). Classic threads/runs docs under `/azure/foundry-classic/` are only mentioned where they differ. Every Learn page cited below lives under `learn.microsoft.com/en-us/azure/foundry/` unless stated; the page's `ms.date` / `updated_at` metadata is given where it was visible.

Scenario kept in mind throughout: a third-party remote streamable-HTTP news MCP server exposes news categories. Agent A must see all categories, Agent B a subset, and the server (or a gateway in front of it) must be able to tell A from B.

## Key question 1: What MCP authentication methods are documented for Foundry agents, and which are GA vs preview?

### Takeaway
The current Learn page lists six methods: key-based (custom headers stored in a project connection), Microsoft Entra agent identity, Microsoft Entra project managed identity, Microsoft Entra client user delegation (`UserEntraToken` / `AgentOnBehalfOfUser`), OAuth identity passthrough (managed or custom OAuth), and unauthenticated. The MCP tool and the first five methods carry no preview banner on the MCP pages; the explicitly preview-labelled items are `AgentOnBehalfOfUser` (agent identity acting on behalf of the user), the `AgentBlueprint` endpoint scheme, long-running MCP operations, toolboxes, and the .NET SDK.

### Cited Findings

Assign the required roles on the underlying service. | No"; "Microsoft Entra - project managed identity | Use the project managed identity ... | No"; "Microsoft Entra client user delegation | Use `UserEntraToken` or `AgentOnBehalfOfUser` with a supported MCP tool to access a downstream resource in the incoming user's context. | Yes"; "OAuth identity passthrough | Prompt users interacting with your agent to sign in and authorize access to the MCP server. | Yes"; "Unauthenticated access | Use this method only when the MCP server doesn't require authentication. | No" (column 3 = "User context persists") - [Set up MCP server authentication, ms.date 2026-09-29, updated 2026-10-23](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)

## Key question 2: Microsoft Entra agent identity to MCP: which identity, how is audience set, what claims, which agent types, pre-created or auto-created?

### Takeaway
In the current object model every agent gets its own Entra agent identity blueprint plus a "default instance" agent identity, created automatically when the agent is created, with no permissions. For prompt agents the service performs a four-step token exchange and sends a bearer token whose `appid`/`azp`/`oid` identify that agent's identity, to the `audience` configured on the `RemoteTool` connection. Hosted agents obtain the same kind of token themselves from the hosted-agent token service. Docs explicitly recommend agent identity when "multiple agents ... need different levels of access to the same MCP server".

### Cited Findings
- "Use agent identity when you want authentication scoped to a specific agent. This approach is ideal when you have multiple agents that need different levels of access to the same MCP server." and "Agent Service creates a unique identity for the agent's default instance when you create the agent. The identity starts without downstream resource permissions." and "When the agent invokes the MCP server, Agent Service uses the available agent identity to request an authorization token and passes it to the MCP server." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Connection creation for agent identity (verbatim): `azd ai connection create my-mcp-connection --kind remote-tool --target https://<mcp-server-endpoint> --auth-type agentic-identity --audience "<entra-audience>"`; for project MI the same with `--auth-type project-managed-identity`. "Use project managed identity when you want all agents in a project to share the same access level" - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- `azd` flag table: `agentic-identity` requires `--audience <entra-audience>`; `project-managed-identity` has `--audience` "(optional)" - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- "Agentic identity ... The system intentionally rejects a user token. Assign the agent identity access on the target resource." - [tool-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-authentication)
- Auto-creation: "In the current agent object model, creating an agent provisions a unique agent blueprint and the identity for its default instance." and "A newly created agent identity starts without resource permissions. Foundry doesn't automatically assign RBAC roles or other downstream permissions to it." - [agent-identity](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Legacy: "Foundry still provisions a shared agent blueprint and agent identity at the project level. Legacy agents without a unique identity use this shared identity. Newly created agents receive their own blueprint and default instance identity instead." and "Migrating from a legacy shared project identity or Agent Application to the current agent object model changes the agent identity ... existing role assignments don't transfer." - [agent-identity](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Runtime exchange (prompt agents, service-managed): "1. Blueprint authentication ... 2. Agent identity token issuance ... 3. Scoped token request: Agent Service presents the agent identity token back to Microsoft Entra ID and requests a new access token scoped to the audience of the downstream service. The audience is the OAuth resource identifier for the target service (for example, `https://storage.azure.com` for Azure Storage). 4. Authenticated tool call: Agent Service passes the scoped access token to the MCP server or A2A endpoint. The downstream resource validates the token and checks the agent identity's RBAC role assignments before granting or denying access." and "The audience identifies the resource that accepts the token, which isn't necessarily the tool endpoint's URL." - [agent-identity](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Blueprint credential: "Foundry provisions a federated identity credential on the blueprint that trusts the 'Azure Machine Learning' resource provider, a Microsoft-managed first-party application with application ID `0736f41a-0425-4b46-bdb5-1563eff02385`." and "No client secret or certificate is needed. Foundry projects, agent code, and the project managed identity never hold the credential." - [agent-identity](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Authorization models the downstream server can use with the agent identity: "Azure RBAC", "Service-specific data-plane roles", "Application permissions or app roles | An API grants the identity application-level permissions for access without a signed-in user, where supported.", "Resource-specific authorization policies" - [agent-identity](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Agent types: "The same identity model applies to text-based prompt agents and voice-based prompt agents." and for hosted agents: "For hosted agents, the token service lets your code obtain tokens for the current agent instance's identity by default. The project managed identity isn't available to your hosted-agent code." and "Each hosted-agent session runs in its own VM-isolated sandbox, which contains no blueprint credential." - [agent-identity](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Hosted-agent token acquisition: `ManagedIdentityCredential` (and `DefaultAzureCredential`) "accesses the hosted-agent token service; it doesn't give your code access to the project managed identity." REST contract: `GET $IDENTITY_ENDPOINT?resource=<resource-uri>&api-version=2019-08-01` with header `X-IDENTITY-HEADER`; optional `client_id` may only be the current or default instance identity's client ID, "Any other client ID | Rejected". "Send the access token to the target service in the `Authorization` header as `Bearer <access-token>`." - [Hosted agent token service reference, ms.date 2026-10-28](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agent-token-service)
- Token claims (Entra Agent ID reference, updated 2026-08-27), app-only agent token: `idtyp` = `app`; `xms_idrel` = `7` (service principal); `azp`/`appid` = "Application ID of the agent identity"; `roles` = "Permissions granted to the agent identity"; `oid` = "Object ID of the agent identity"; `xms_act_fct` = `11` (AgentIdentity); `xms_sub_fct` = `11`; `scp` "Empty or `/`". `xms_par_app_azp` = "parent application of the authorized party" (the blueprint), and "It isn't recommended to use the parent application ID for authorization decisions, as it would result in widespread access by many agents." "In v2 tokens, you see `azp` instead of `appid`. They both refer to the application ID of the agent identity." - [Token claims reference for agent IDs](https://learn.microsoft.com/en-us/entra/agent-id/agent-token-claims)
- "It has unique identifiers such as the object ID and the app ID, which always have the same value and can be reliably used for authentication and authorization decisions." and "Agent identities can only be issued tokens in the Microsoft Entra tenant where they're created." - [Overview of agent identities in Microsoft Entra](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities)
- Custom-server audience rule (stated for managed OAuth but relevant to any Entra token): "Your custom MCP server must be registered with an audience that you control rather than a known Microsoft audience." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Field report (community Q&A, 2026-05-12): a .NET MCP server validating `aud` and App ID saw the caller alternate between `...-network-resolver-AgentIdentity` (agent-specific) and `...-AgentIdentity` (shared project identity). Moderators attributed it to publish state and advised allow-listing the specific identity; no official platform statement in the thread - [Q&A: Foundry agent app id keeps changing](https://learn.microsoft.com/en-us/answers/questions/5888036/foundry-agent-app-id-keeps-changing)
- Entra governance: "Per-agent identities let you scope permissions and audit activity to individual agents." Agent sign-in logs "show which agent identity obtained a token for which resource" - [agent-identity](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)

### Inferences
- For the news-server scenario, agent identity is the only documented mechanism where the credential is bound to the agent object itself rather than to a connection: one `agentic-identity` connection can be shared by Agent A and Agent B, and the server (or an APIM `validate-jwt` policy) distinguishes them by `appid`/`azp`/`oid`. Per-agent category rights can be expressed as Entra app roles on the server's app registration (`roles` claim) assigned to each agent identity service principal, or as a server-side allow-list keyed on `oid`.
- Identity is per agent (blueprint + default instance), not per agent version: the docs tie the identity to "the agent's default instance" created at agent creation, and the hosted token service says "General hosted agents use only the default instance". Nothing says a new version mints a new identity.
- The audience for a custom third-party server has to be an app registration you (or the vendor) control; Foundry will not mint a token for an arbitrary URL.

### Gaps
- No doc states the exact `appid` the MCP server sees when the connection is `agentic-identity` but the calling agent is a legacy agent using the shared project identity; the Q&A suggests both can appear. Confirm by decoding a token.
- No doc states whether an agent identity survives agent deletion/re-creation with the same name (relevant to stable server-side allow-lists).

## Key question 3: Can two agents in one project use two different project connections that point at the same MCP URL?

### Takeaway
Nothing in the docs prohibits it: a connection is a named project resource holding `target` + `authType` + credentials, and the agent references it by name/ID in `project_connection_id`; the MCP tool page even says the connection's endpoint overrides `server_url`. The documented constraints are about visibility (anyone with project access can read key-based connection secrets), role requirements (Foundry Project Manager to create connections), and the rule "Use a separate connection for each downstream resource" for delegated scopes.

### Cited Findings
- "`project_connection_id`: The connection name that stores the MCP server endpoint, authentication selection, and relevant information. If you provide different endpoints in the connection versus `server_url`, the endpoint in the connection is used." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Visibility: "People who have access to the project can access an API key stored in a project connection. Store only shared secrets in a project connection. For user-specific access, use Microsoft Entra client user delegation or OAuth identity passthrough." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Roles: "The Foundry User role on the Foundry project to create and test agents. If you create a project connection for MCP authentication, you also need the Foundry Project Manager role on that project." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol); "Adding connections requires the Foundry User, Foundry Owner, or Azure Contributor role (or higher)." - [connections-add](https://learn.microsoft.com/en-us/azure/foundry/how-to/connections-add)
- Secret storage: "Foundry stores connections details in a managed Azure Key Vault if no Key Vault connection is created ... Only one Azure Key Vault connection per Foundry resource at a time." - [connections-add](https://learn.microsoft.com/en-us/azure/foundry/how-to/connections-add)
- Portal creation of a key-based MCP connection: "When you connect an MCP server to an agent in the Foundry portal, Foundry creates a project connection for you. Provide the credential name and credential value. For example ... Credential name: `Authorization` / Credential value: `Bearer <your-personal-access-token>`." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- CLI creation of a custom-keys connection: `azd ai connection create my-mcp-conn --kind remote-tool --target https://api.githubcopilot.com/mcp/ --auth-type custom-keys --custom-key "Authorization=******"` and "The `--custom-key "Header=Value"` flag is repeatable when a service needs more than one header." - [tool-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-authentication)
- Microsoft's Python sample reads the connection by ID: "MCP_PROJECT_CONNECTION_ID - The connection resource ID in Custom keys with key equals to "Authorization" and value to be "Bearer <your GitHub PAT token>"" and passes `project_connection_id=os.environ["MCP_PROJECT_CONNECTION_ID"]` - [sample_agent_mcp_with_project_connection.py](https://github.com/Azure/azure-sdk-for-python/blob/main/sdk/ai/azure-ai-projects/samples/agents/tools/sample_agent_mcp_with_project_connection.py)
- Delegated connections: "Use a separate connection for each downstream resource. Don't combine scopes for multiple resources in one connection." and the migration guidance creates "an `AgentOnBehalfOfUser` connection beside the existing connection" for the same tool endpoint, attaching each to a different agent version - [configure-user-delegation](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-user-delegation)
- ARM connection shape used in this repo's lab (category `RemoteTool`, `authType` `None`, `metadata.type` `custom_MCP`, API version `2025-04-01-preview`), registered by name under `.../projects/{project}/connections/{name}` - local notebook `/home/jp/development/corticalstack/awesome-foundry-nextgen/08-agents/08-05-contoso-pmo-mcp/08-05-03-contoso-pmo-tool-catalog.ipynb`
- Connection JSON for delegated MCP (verbatim): `{"properties": {"category": "RemoteTool", "target": "<tool-endpoint>", "authType": "UserEntraToken", "audience": "<resource-audience>", "scopes": ["<fully-qualified-delegated-scope>"], "metadata": {"type": "generic_mcp", "audience": "<resource-audience>"}}}` - [configure-user-delegation](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-user-delegation)

### Inferences
- Two `custom-keys` connections `news-conn-full` and `news-conn-restricted`, both with `target = https://news.example/mcp` but different `Authorization` values, attached to Agent A and Agent B respectively, is a fully supported pattern by the documented model. The server distinguishes agents by API key. The weakness is documented: both keys are readable by anyone with project access, and nothing stops a developer with Foundry User rights from pointing Agent B at `news-conn-full`.
- The same holds for two `oauth2` connections with different client IDs (see question 6) and for two `agentic-identity` connections (pointless: the identity comes from the agent, not the connection).
- Connection uniqueness is by name within the project; no uniqueness-by-target rule is documented.

### Gaps
- No doc explicitly confirms "two connections may share the same `target`"; this is inferred from the data model and the side-by-side migration guidance.
- No per-connection RBAC or per-agent connection binding is documented; access control on connections is project-level.

## Key question 4: What does the `MCPTool` / `type: "mcp"` definition look like in the Python SDK and REST, and are custom headers per agent still supported and secret-safe?

### Takeaway
`azure-ai-projects` 2.9.0 (`main` on GitHub) models `MCPTool` with `type="mcp"`, `server_label` (required), `server_url` | `connector_id` | `tunnel_id`, `authorization`, `headers: dict[str,str]`, `allowed_tools: list[str] | MCPToolFilter`, `allowed_callers`, `require_approval`, `defer_loading`, `project_connection_id`, and a deprecated `tool_configs`. The REST body is the same JSON inside `tools[]` of the agent definition. `headers` still exists but the Foundry docs steer you to connections "instead of passing them at runtime"; no doc says headers in an agent definition are redacted.

### Cited Findings
- Field list and types (Learn reference, updated 2026-08-25): `type` "Always `mcp`. Required."; `server_label` "Required."; `server_url` "One of `server_url`, `connector_id`, or `tunnel_id` must be provided."; `authorization` "An OAuth access token that can be used with a remote MCP server ... Your application must handle the OAuth authorization flow and provide the token here."; `headers` `dict[str, str]`; `allowed_tools` `list[str]` or `MCPToolFilter`; `allowed_callers`; `require_approval` `MCPToolRequireApproval | "always" | "never"`; `defer_loading` "Whether this MCP tool is deferred and discovered via tool search."; `project_connection_id` "The connection ID in the project for the MCP server. The connection stores authentication and other connection details needed to connect to the MCP server."; `tool_configs` "Deprecated." - [MCPTool class](https://learn.microsoft.com/en-us/python/api/azure-ai-projects/azure.ai.projects.models.mcptool)
- Same fields in SDK source at `VERSION = "2.9.0"`; `MCPToolFilter` has `tool_names: list[str]` ("MCP allowed tools.") and `read_only: bool` ("If an MCP server is annotated with `readOnlyHint`, it will match this filter."); `MCPToolRequireApproval` has `always: MCPToolFilter` and `never: MCPToolFilter`. `MCPToolboxTool` (toolbox variant) adds `tool_configs` "Keys are tool names or `*` (catch-all default) ... Unknown tool names are silently ignored at runtime." - [azure-sdk-for-python _models.py](https://github.com/Azure/azure-sdk-for-python/blob/main/sdk/ai/azure-ai-projects/azure/ai/projects/models/_models.py)
- Prompt-agent Python sample (verbatim core): `tool = MCPTool(server_label="api-specs", server_url="https://api.githubcopilot.com/mcp", require_approval="always", project_connection_id=MCP_CONNECTION_NAME)` then `project.agents.create_version(agent_name=..., definition=PromptAgentDefinition(model="gpt-5-mini", instructions=..., tools=[tool]))` - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)

- Headers acknowledged: "The MCP tool allows you to pass custom headers, such as authentication keys or schemas, that a remote MCP server might need. Review all data that you share with remote MCP servers and log the data for auditing purposes." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Preference for connections: "Pass an API key, a personal access token (PAT), or other credentials to MCP servers that support key-based authentication. - Classic contrast: the classic `azure.ai.agents` `McpTool` used `update_headers(key, value)` and passed `mcp_tool.headers` at run submission (per-run headers) - [classic samples page (search snippet)](https://learn.microsoft.com/en-my/Azure/foundry-classic/agents/how-to/tools-classic/model-context-protocol-samples)

### Inferences
- Per-agent custom headers are still part of the schema (`headers` on `MCPTool`), so Agent A and Agent B could carry different `Authorization` headers directly in their definitions. Because an agent definition is a readable project object (GET `/agents/{name}/versions/{v}`), those header values should be assumed readable by any principal that can read the agent; no doc claims redaction. Connections are the documented secret-safe path.
- `connector_id`, `tunnel_id`, `authorization`, `allowed_callers`, `defer_loading` come from the OpenAI Responses schema; the Foundry MCP docs do not describe them, so treat their behaviour in Foundry Agent Service as undocumented.

### Gaps
- The Foundry REST reference (`ai.azure.com/api-reference`) is a JavaScript app and was not fetchable; the field list above is from the Python SDK and Learn pages, not from the raw OpenAPI.
- Not found: any statement that header values set on an agent are masked when the agent is read back, or that they are stored in Key Vault.

## Key question 5: What does `allowed_tools` do, is it enforced server-side, and when does Foundry call `tools/list`?

### Takeaway
`allowed_tools` is a per-agent allow-list of tool names (or an `MCPToolFilter` by name/read-only annotation) that limits what the agent "can access and use"; an empty list means all tools. It lives in the agent definition and is never part of the MCP wire protocol, so enforcement is in the Foundry runtime only. The docs describe tool discovery as happening "at runtime" for toolboxes; no doc gives the exact moment for direct MCP tools.

### Cited Findings
- "`allowed_tools`: An optional list of tools that this agent can access and use. If you omit this value or set it to an empty list (`[]`), the agent can access all tools exposed by the MCP server. To allow only specific tools, provide a nonempty list of their names." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Best practice: "To restrict tool access, set `allowed_tools` to a nonempty list of tool names. An empty list (`[]`) allows all tools exposed by the MCP server, not zero tools." and "Review `allowed_tools`, approval settings, and connection permissions when the server's operator, exposed tools, or behavior changes." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- "enforce permissions and approval requirements independently of model-generated decisions." and "Treat provider-supplied descriptions as untrusted input." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Portal catalog equivalence: "Selecting a subset of tools in the catalog UI is equivalent to specifying an `allowed_tools` list in code." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Name matching is literal: "If you set `allowed_tools`, make sure the tool name matches what the MCP server exposes." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- `require_approval` semantics: default `always`; `never`; `{"never":[...]}`; `{"always":[...]}`; approval surfaces as an `mcp_approval_request` output item answered with `mcp_approval_response` in the same conversation ("Don't use `previous_response_id`, which isn't supported by this harness" for the Copilot harness) - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Filter model: `MCPToolFilter.tool_names` and `MCPToolFilter.read_only` ("If an MCP server is annotated with `readOnlyHint`, it will match this filter.") - [azure-sdk-for-python _models.py](https://github.com/Azure/azure-sdk-for-python/blob/main/sdk/ai/azure-ai-projects/azure/ai/projects/models/_models.py)
- Discovery timing (toolbox): "Your agent connects to one MCP-compatible endpoint and discovers every tool at runtime." - [Toolbox overview](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/toolbox-overview)
- Timeouts: "Non-streaming MCP tool calls have a timeout of 100 seconds." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Toolbox per-tool config: `tool_configs` on `MCPToolboxTool` "Keys are tool names or `*` ... Unknown tool names are silently ignored at runtime." - [azure-sdk-for-python _models.py](https://github.com/Azure/azure-sdk-for-python/blob/main/sdk/ai/azure-ai-projects/azure/ai/projects/models/_models.py)

### Inferences
- `allowed_tools` and `require_approval` are client-side (Foundry runtime) controls. The MCP server receives ordinary `tools/list` and `tools/call` requests and has no way to see the allow-list. For the news scenario, setting `allowed_tools` on Agent B restricts which tool names the model may call, but it cannot restrict tool arguments (for example a `category` parameter on a shared `get_news` tool) and it does not make Agent B distinguishable to the server. Server-side category restriction needs an identity or credential signal (questions 2, 3, 6).
- "Unknown tool names are silently ignored" (toolbox) and "make sure the tool name matches" (direct) imply the allow-list is applied by name against whatever the server's `tools/list` returns at run time, not validated at agent-create time.

### Gaps
- No Learn page states whether Foundry issues `tools/list` on every response, once per conversation, or caches it; the classic Responses `mcp_list_tools` output item is not described on the new-service MCP page.
- No explicit sentence "allowed_tools is not enforced by the MCP server"; this is derived from the protocol and the field's location.

## Key question 6: OAuth identity passthrough: flow, where the client registration lives, what reaches the server, audience, end-user vs agent identity, per-agent client IDs

### Takeaway
OAuth identity passthrough (`authType: OAuth2`) stores the OAuth client registration (client ID, optional secret, auth/token/refresh URLs, scopes) in the project connection, drives a consent-link flow via an `oauth_consent_request` output item, stores and refreshes each user's tokens, and calls the MCP server with that user's credentials. Authorization state is partitioned per user per connection per project, and the identity presented downstream is the end user's, not the agent's. Managed-OAuth Entra tokens for Microsoft audiences are blocked from reaching custom servers.

### Cited Findings
- "Use OAuth identity passthrough to prompt users interacting with your agent to sign in to the MCP server and its underlying service. Agent Service securely stores the user's credentials and uses them only within the context of the agent communicating with the MCP server." and "After the user signs in and consents, the agent can discover and invoke tools on the MCP server with that user's credentials." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Two options: "With managed OAuth, Microsoft or the MCP server publisher manages the OAuth app. With custom OAuth, you bring your own OAuth app registration." Custom OAuth inputs: "Client ID: required; Client secret: optional; Auth URL: required; Refresh URL: required; Token URL: required; Scopes: optional (include `offline_access` ...). When you specify multiple scopes, separate them with a single space". "If you use custom OAuth, you receive a redirect URL after configuration. Add the redirect URL to your OAuth app" - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Connection property names: `authType` `OAuth2`; `connectorName` "Required for managed OAuth"; `credentials.clientId`; `credentials.clientSecret` "A secret stored in the project connection"; `authorizationUrl`; `tokenUrl`; `refreshUrl`; `scopes` - [configure-user-delegation](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-user-delegation)
- Managed connector names (only these servers support Foundry-managed OAuth): `foundrydatabricksmcp`, `foundrygithubmcp`, `foundryinfobipmcp`, `foundryinfobiprcsmcp`, `foundryinfobipsmsmcp`, `foundrylsegmcp`, `foundrymorningstarmcp`, `foundryneonmcp`, `foundrypipedreammcp`, `foundryvercelmcp`. "For other OAuth-enabled MCP servers, provide your own app registration." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Scope of state: "The scope of OAuth is per tool (connection) name per Foundry project. Each new user using a new tool (connection) in a Foundry project is prompted to provide consent." Consent link is in output item type `oauth_consent_request`, field `consent_link` (example host `logic-swedencentral-001.consent.azure-apihub.net`); continue with `previous_response_id` after consent. "Once the user has signed in and given consent once, they don't need to give consent in the future." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Partitioning: "Agent Service stores and refreshes the resulting credentials. It partitions the authorization state by user and connection, so each user's downstream credentials remain isolated." - [User delegation for tools (concept), updated 2026-10-23](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/user-delegation)
- Multi-user hosted agents: "When a service-to-service integration calls a hosted agent for multiple end users, set `x-ms-user-identity` to a stable value that identifies the user associated with each request. Agent Service uses this value to partition OAuth authorization state" - [configure-user-delegation](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-user-delegation)
- Audience restriction: "When using managed OAuth with Microsoft Entra, Agent Service restricts tokens scoped to a known Microsoft audience from being sent to custom or third-party MCP servers. If you attempt this, Agent Service returns the error: `Cannot pass Microsoft token to untrusted MCP endpoint.` Your custom MCP server must be registered with an audience that you control rather than a known Microsoft audience. Don't design your MCP server to rely on passthrough of its authentication token to a downstream Microsoft service." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Caller requirements: "users interacting with your agent need at least the Foundry Agent Consumer role on the project ... The user's Microsoft Entra tenant must match the tenant of your Foundry project. Cross-tenant token exchange isn't supported." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Identity presented downstream: "User delegation | The signed-in user, through Microsoft Entra on-behalf-of-user behavior or a separate OAuth sign-in"; "Agent identity | The agent as an independent Microsoft Entra principal" - [user-delegation](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/user-delegation)
- Entra OBO to a custom MCP server is a different method: "For Microsoft Entra on-behalf-of-user access to a custom MCP server, use `AgentOnBehalfOfUser`, not `UserEntraToken`." and "Foundry can act on behalf of the user for a limited set of Microsoft-owned tools. It can't do so for custom servers or third-party integrations." In the `AgentOnBehalfOfUser` case "The downstream token represents both the user and the agent, which allows the resource to make authorization decisions about the agent." (preview, requires `AgentBlueprint` endpoint scheme) - [configure-user-delegation](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-user-delegation), [user-delegation](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/user-delegation)
- Entra claims in that delegated case: `idtyp` = `user`, `azp`/`appid` = agent identity app ID, `scp` = delegated permissions, `oid` = user object ID, `xms_act_fct` = `11` - [agent-token-claims](https://learn.microsoft.com/en-us/entra/agent-id/agent-token-claims)
- Channel limitation (Microsoft Q&A, March to May 2026): OAuth passthrough works on the Responses API path (playground, direct `/responses`) but not when the agent is published to Microsoft 365 Copilot or Teams via the Activity Protocol; there "the MCP server received only the project managed identity". Moderator confirmed, no ETA; a Microsoft employee reported a workaround where the MCP server runs its own OAuth sign-in - [Q&A: OAuth identity passthrough not supported for Foundry agents published to M365 Copilot](https://learn.microsoft.com/en-us/answers/questions/5839438/oauth-identity-passthrough-not-supported-for-found)
- Toolbox variant: direct toolbox clients can use `OAuth2` per-tool sign-in but "can't use `AgentOnBehalfOfUser`" and "can't use agent blueprint sign-in"; the first OAuth call through a toolbox returns JSON-RPC error `-32006` "User consent is required. Please visit: https://..." - [tool-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-authentication), [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)

### Inferences
- The access token the OAuth provider issues is what reaches the MCP server; Foundry is the OAuth client (it owns the redirect URL, stores the client secret, refreshes tokens). The server therefore sees the user as subject and the connection's client ID as the client/`azp`.
- Per-agent OAuth client IDs are achievable: register two OAuth clients at the news server's IdP (full vs restricted), create two `OAuth2` connections with the same `target`, attach one to each agent. The server can then scope categories by client ID while still knowing the user. Cost: every user consents separately per connection ("per tool (connection) name per Foundry project"), and the method only preserves identity on Responses-API callers, not Bot Framework channels.
- OAuth passthrough does not identify the agent by itself; it identifies the user. Agent distinction comes only from using different client registrations.

### Gaps
- No doc states the exact header or token format sent to the MCP server under `OAuth2` (assumed `Authorization: Bearer <provider access token>`).
- No doc states whether the consent-link redirect URL is per project or per connection.

## Key question 7: Is there an MCP "tool catalog" / toolbox registry with per-agent assignment and an authorization binding?

### Takeaway
Two registries exist: (a) the portal "Add Tools > Catalog" plus project connections of category `RemoteTool` (shown under Build > Tools), which is just connection storage referenced by `project_connection_id`; and (b) Foundry Toolboxes (public preview), project-level versioned bundles exposed as one MCP endpoint, where auth is centralised on connections and the calling agent authenticates to the toolbox with its own Entra identity (`https://ai.azure.com/.default`). Neither has a documented per-agent assignment ACL; gating is project RBAC (Foundry User on the project for the agent identity) and whatever you configure inside each toolbox.

### Cited Findings
- Catalog: "In addition to connecting arbitrary remote MCP servers by URL, you can add some MCP servers directly from the Foundry Add Tools catalog. For example, Azure DevOps MCP Server is available as a catalog entry." and the Azure DevOps flow: "Choose which Azure DevOps tools to expose to your agent. You can select a subset of tools to control exactly what the agent can access." - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Custom MCP catalog entries are ARM connections: `PUT .../connections/{name}?api-version=2025-04-01-preview` with `{"properties": {"category": "RemoteTool", "authType": "None", "target": <url>, "metadata": {"type": "custom_MCP"}}}`; listed by filtering `category == RemoteTool` and `metadata.type == custom_MCP`; portal page `.../Build/tools` - local notebook `/home/jp/development/corticalstack/awesome-foundry-nextgen/08-agents/08-05-contoso-pmo-mcp/08-05-03-contoso-pmo-tool-catalog.ipynb`
- Toolbox definition: "Toolbox provides a centralized way to manage and share tools ... expose them through a single MCP-compatible endpoint" with "Centralized authentication. The toolbox handles credential injection, token refresh, and policy enforcement at runtime by using Microsoft Entra ID and OAuth identity passthrough, so consuming agents don't manage per-tool credentials." - [Toolbox overview, ms.date 2026-10-26](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/toolbox-overview)
- Toolbox RBAC prerequisites: "Grant the Foundry User role on the Foundry project to each identity that applies to your scenario: Developer (always required) ...; Agent identity (required if using a prompt agent) - the agent's managed identity that calls tools at runtime; End user (required only for OAuth flows)". "use the agent identity's object ID as the assignee." - [toolbox how-to](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/toolbox)
- Toolbox endpoints: consumer `{project_endpoint}/toolboxes/{toolbox_name}/mcp?api-version=v1` (serves `default_version`); developer `{project_endpoint}/toolboxes/{toolbox_name}/versions/{version}/mcp?api-version=v1`; clients send `Authorization: Bearer <token for https://ai.azure.com/.default>` - [toolbox how-to](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/toolbox)
- Agent-to-toolbox identity: "Agent-to-toolbox boundary (the stable one). The agent authenticates to the platform with its own agent identity. This identity gates access to the toolbox itself, not the individual tools inside it." and "Tool-to-data boundary (the per-user one)." - [tool-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-authentication)
- Prompt agents attach a toolbox as a normal `mcp` tool with a `remote-tool` connection of `--auth-type user-entra-token --audience https://ai.azure.com` ("Use a user Entra token so the caller's identity is passed through") - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Hosted agents attach via `FoundryToolbox(credential, url=TOOLBOX_MCP_URL)` (Python Agent Framework) or `AddFoundryToolboxes(credential, toolboxName)` (.NET); "It forwards the current hosted request's `x-agent-foundry-call-id` so the toolbox proxy can resolve the caller context." - [tool-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/tool-authentication), [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Toolbox YAML references connections by name and "never embeds credentials"; versions are "immutable snapshots"; each `MCPToolboxTool` carries its own `project_connection_id`, `require_approval`, `allowed_tools`, `tool_configs` - [toolbox how-to](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/toolbox), [azure-sdk-for-python _models.py](https://github.com/Azure/azure-sdk-for-python/blob/main/sdk/ai/azure-ai-projects/azure/ai/projects/models/_models.py)
- Toolbox governance scope: "Govern | Apply authentication, authorization, guardrails, observability, and version management at the toolbox level." - [toolbox-overview](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/toolbox-overview)
- Network isolation for toolboxes exists as a separate article (August 2026) - [What's new August 2026](https://learn.microsoft.com/en-us/azure/foundry/whats-new-foundry)

### Inferences
- For the news scenario, toolboxes give a clean way to build two curated views of the same server: `news-toolbox-full` (connection with key A, all tools) and `news-toolbox-restricted` (connection with key B, `allowed_tools` subset), each attached to one agent. The server still distinguishes by the key behind each toolbox, and the toolbox proxy enforces the allow-list before the request leaves Foundry. Access to each toolbox is gated only by project-level RBAC, so this is a configuration boundary, not a hard authorization boundary.
- The catalog (`RemoteTool` connections) has no concept of "assigned agents"; any agent in the project can reference any connection.

### Gaps
- Not documented: whether a toolbox forwards the calling agent's identity to a downstream `agentic-identity` connection (which agent's token the MCP server sees when two agents share one toolbox).
- Not documented: per-toolbox RBAC roles or scopes narrower than the project.

## Key question 8: Are there Microsoft samples showing per-agent credentials to the same MCP server?

### Takeaway
No. Microsoft's samples show one connection per agent (GitHub PAT in a Custom keys connection) and the migration guide shows two connections to the same tool endpoint attached to different agent versions, but no sample creates two agents with different credentials to one server.

### Cited Findings
- Python SDK samples: `sample_agent_mcp.py` (no auth, `gitmcp.io`), `sample_agent_mcp_with_project_connection.py` (GitHub MCP with `project_connection_id` from a Custom keys connection holding `Authorization: Bearer <PAT>`), plus async variants - [samples/agents/tools](https://github.com/Azure/azure-sdk-for-python/tree/main/sdk/ai/azure-ai-projects/samples/agents/tools)
- .NET samples referenced by the docs: `Sample19_MCP.md` and `Sample20_MCP_Connection.md` in `Azure.AI.Extensions.OpenAI` - [model-context-protocol](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/tools/model-context-protocol)
- Side-by-side connections to one endpoint (migration guidance): "Create an `AgentOnBehalfOfUser` connection beside the existing connection ... Attach the new connection only to a separate test version of the agent. Keep the production version configured with the existing connection, and don't expose both connections for the same tool in one agent version." - [configure-user-delegation](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-user-delegation)
- Doc-level statement that agent identity is the intended per-agent mechanism: "ideal when you have multiple agents that need different levels of access to the same MCP server." - [mcp-authentication](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Infrastructure samples repo (connections Bicep, private MCP networking template `19-private-network-agent-tools`) - [microsoft-foundry/foundry-samples](https://github.com/microsoft-foundry/foundry-samples/tree/main/infrastructure/infrastructure-setup-bicep/01-connections)

### Inferences
- Summary of Foundry-side options that make Agent A and Agent B distinguishable to the news server or a gateway, ranked by how strongly the distinction is bound to the agent:
  1. Entra agent identity (`agentic-identity` connection, audience = the server's own app registration): bound to the agent object, auto-provisioned, visible as `appid`/`oid`/`roles` claims; shareable single connection; server or APIM enforces categories per identity. Requires the server to accept Entra tokens.
  2. Two `custom-keys` connections with different API keys (or different `headers` in each agent definition): simple, works with any third-party server, but keys are project-readable and the binding is only by convention.
  3. Two `OAuth2` connections with different client IDs: distinguishes agents by OAuth client while preserving the end user; double consent per user; Responses API callers only.
  4. Two toolboxes wrapping the same server with different connections and `allowed_tools`: adds a Foundry-side filter and central credential management; distinction still comes from the connection credential inside each toolbox.
  5. `allowed_tools` / `require_approval` alone: Foundry-side only, invisible to the server, cannot constrain arguments.

### Gaps
- No Microsoft sample or blog post found that demonstrates APIM or an MCP server authorizing per Foundry agent identity; the TrueFoundry and Q&A sources describe it but are secondary.
