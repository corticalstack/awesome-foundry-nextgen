# Microsoft Entra Agent ID and the identity a Foundry agent uses to call an MCP server

State as of 2026-10-29. All Learn pages cited were fetched on this date; ms.date / updated_at values are quoted where they matter. "Foundry" = Microsoft Foundry (docs under learn.microsoft.com/en-us/azure/foundry/). "Prompt agent" = declarative Foundry-run agent. "Hosted agent" = customer container on Microsoft-managed compute with a durable Foundry agent object.

## Q1. What is Microsoft Entra Agent ID as of October 2026, and what are its objects?

### Takeaway
Entra Agent ID is generally available (the Entra "What's new in Agent ID" page, ms.date 2026-05-01, opens with "Microsoft Entra Agent ID is now generally available"). It defines four directory objects: agent identity blueprint (an application-type object that holds credentials and app roles), agent identity blueprint principal (the blueprint's service-principal-like presence in a tenant), agent identity (a service principal subtype that is the actual subject of tokens), and agent's user account (optional user object paired 1:1 to an agent identity). Foundry creates one blueprint plus one agent identity per agent object (not per version, not per project in the current model); legacy agents share a project-level blueprint and identity.

### Cited Findings
- "Microsoft Entra Agent ID is now generally available. This release brings first-class identity and access management to AI agents" (page ms.date 2026-05-01, updated_at 2026-08-13). [Source](https://learn.microsoft.com/en-us/entra/agent-id/whats-new-agent-id)
- "Microsoft Entra Agent ID is a product within Microsoft Entra that provides the platform for creating and managing agent identities and agent identity blueprints. Agent ID is available for all Microsoft Entra customers." Extending Entra security features (Conditional Access, ID Protection, governance) to agents "requires Microsoft Agent 365", which is included with Microsoft 365 E7 and available as an add-on to E5/A5/Business Premium. [Source](https://learn.microsoft.com/en-us/entra/agent-id/what-are-agent-identities)
- Agent identity definition: "An agent identity is a special service principal in Microsoft Entra ID. It represents an identity that the agent identity blueprint created and is authorized to impersonate. It doesn't have credentials on its own." Agent identities can request tokens (subject = agent identity), receive tokens (audience = agent identity), and request user tokens via OBO (actor = agent identity). [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities)
- Agent identity blueprint definition: "an object in Microsoft Entra ID that serves as a template for creating agent identities." Shared properties: description, app roles ("Define the roles that can be given to users and other principals when using the agent"), verified publisher, authentication protocol settings (for example OptionalClaims). "A blueprint can perform exactly one operation in the tenant: provision or deprovision agent identities." It has an OAuth client ID, credentials, and the special Graph permission `AgentIdentity.CreateAsManager`. [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-blueprint)
- Agent identity blueprint principal: "an object in Microsoft Entra Agent ID that represents the presence of an agent identity blueprint within a specific tenant." When the blueprint acquires tokens, "the resulting token's oid (object ID) claim references the agent identity blueprint principal." Audit log actions by the blueprint are attributed to the principal. Single-tenant and multitenant blueprints both get a principal in each tenant. [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-blueprint)
- Agent's user account: "an optional account that pairs 1:1 with an agent identity ... Use an agent's user account only when the agent must access systems that require a user object. An agent's user account doesn't replace the agent identity, both must exist." Traditional service principals and regular user accounts are explicitly "not recommended for AI agents". [Source](https://learn.microsoft.com/en-us/entra/agent-id/key-concepts)
- Graph object model: `agentIdentity` is in Microsoft Graph v1.0 (page ms.date 2026-08-26), "Inherits from servicePrincipal", `odata.type` = `#microsoft.graph.agentIdentity`, `servicePrincipalType` is "Set to ServiceIdentity for all agent identities", `agentIdentityBlueprintId` = "The appId of the agent identity blueprint that defines the configuration for this agent identity", `createdByAppId`, `sponsors`, `owners`, `customSecurityAttributes`, `tags`. Relationships include `appRoleAssignments`, `appRoleAssignedTo`, `memberOf`, `oauth2PermissionGrants`, `ownedObjects`. [Source](https://learn.microsoft.com/en-us/graph/api/resources/agentidentity)
- Agent identities are "modeled as single-tenant service principals with a new 'agent' subtype classification." They "inherit their protocol properties from their parent agent identity blueprint through the ParentID relationship" and "require their parent agent identity blueprint for impersonation and token exchange operations." "Agent identities can be granted permissions directly and appear in sign-in logs when tokens are issued for agent operations." [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-service-principals)
- Earlier Foundry versions used standard application service principals for agents: "Before the Microsoft agent identity platform was introduced, some Microsoft applications, including earlier versions of Microsoft Copilot Studio and Azure AI Foundry, used standard application service principals to secure their agents." These show up in the admin center with "Uses agent identity" = No. [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-service-principals); column semantics in [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-lists)
- How Foundry maps onto these objects (page ms.date 2026-10-28): "In the current agent object model, creating an agent provisions a unique agent blueprint and the identity for its default instance." "An agent identity blueprint models the agent and is the parent object for its associated agent identities." "An agent identity is a special service principal in Microsoft Entra ID, created under an agent blueprint. It represents an agent instance when it accesses downstream resources." "The same identity model applies to text-based prompt agents and voice-based prompt agents." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Per-agent, not per-version: "The agent's identity, endpoint, and authorization surface stay consistent as its underlying versions evolve, so consumers always interact with the same entity." The agent object carries `instance_identity` ("The agent's unique Microsoft Entra identity (principal_id, client_id)", read-only) and `blueprint` / `blueprint_reference` ("Reference to the agent's Microsoft Entra agent blueprint (principal_id, client_id, or type, blueprint_id)", read-only). [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-agent)
- Legacy vs new: "Newly created agents receive a unique Entra Agent Blueprint and Entra Agent Identity by default." Legacy agents (created before the object model update) have `agent.identity` null / `instance_identity` null and "use the shared project identity and blueprint." "There's currently no way to upgrade a legacy agent to a unique identity in place." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/migrate-agent-applications)
- "Foundry still provisions a shared agent blueprint and agent identity at the project level. Legacy agents without a unique identity use this shared identity." "For legacy identities, deleting the Foundry project removes its shared agent blueprint and identity." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Older description still live in the Entra governance docs (ms.date 2026-06-05): "When the first agent in a Foundry project is created, Microsoft Foundry provisions a default agent identity blueprint and a default agent identity for the project, and agents in the project authenticate by using the shared project's agent identity. Publishing an agent automatically creates a dedicated agent identity blueprint and agent identity". This describes the legacy (publish-time) model. [Source](https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview)
- Foundry is listed as a managed "Microsoft product integration" creation channel alongside Copilot Studio and Security Copilot; "Administrators can control agent identity creation via these channels by using the administrative tools for each respective product." [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-id-creation-channels)

### Inferences
- Per-agent-object identity means two prompt agents in the same project have two distinct service principals, each with its own blueprint, which is the precondition for giving them different app roles on the same MCP server.
- The Entra governance page and the Foundry agent-identity page disagree on when the dedicated identity is minted (publish vs create). The Foundry page is four months newer and is the product's own doc; treat "create" as current and "publish" as the legacy behavior.

### Gaps
- No Microsoft doc states the display-name pattern Foundry uses for auto-created blueprints and identities. Read `instance_identity` from the agent object instead of guessing by name.
- The agent-identities page says object ID and app ID "always have the same value" for an agent identity, while the Foundry agent object exposes both `principal_id` and `client_id`. I found no doc that reconciles these; read both values from the API rather than assuming equality.

## Q2. Does a prompt agent have its own identity distinct from the project managed identity?

### Takeaway
Yes. Foundry docs state that creating an agent provisions a unique blueprint and agent identity, that this identity "starts without resource permissions", and that the project managed identity is a separate, legacy-compatible option for tool connections.

### Cited Findings
- "Agent Service creates a unique identity for the agent's default instance when you create the agent. The identity starts without downstream resource permissions. Legacy agents can use the shared project identity." The MCP connection CLI offers two Entra auth types: `--auth-type agentic-identity` ("Use the agent identity") and `--auth-type project-managed-identity` ("Use the project managed identity"), both with `--audience "<entra-audience>"`. [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- "Use agent identity when you want authentication scoped to a specific agent. This approach is ideal when you have multiple agents that need different levels of access to the same MCP server." "Use project managed identity when you want all agents in a project to share the same access level". [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- "A newly created agent identity starts without resource permissions. Foundry doesn't automatically assign RBAC roles or other downstream permissions to it." "Foundry projects, agent code, and the project managed identity never hold the credential" (the blueprint FIC). [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Hosted agents table: "Microsoft Entra ID (agent identity, per-agent)" is "The identity the agent container authenticates with at runtime"; "Project managed identity (project-wide)" is "Used by the platform for infrastructure operations ... Not the agent's runtime identity." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents)
- Blueprint credential: "Foundry provisions a federated identity credential on the blueprint that trusts the 'Azure Machine Learning' resource provider, a Microsoft-managed first-party application with application ID 0736f41a-0425-4b46-bdb5-1563eff02385. This isn't 'Azure Machine Learning Services,' the principal used to sign in to the Foundry portal." Example FIC subject: `/eid1/c/pub/t/<base64url tenant>/a/<base64url appid>/AzureAI/FMI`. [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- The project managed identity itself can be user-assigned only at project creation: "user-assigned managed identities are supported only when configured during the Foundry project creation. Changing the project identity type after creation isn't supported." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agent-permissions)

### Inferences
- "Project managed identity" and "agent identity" are two different Entra principals with different token issuance paths (managed identity endpoint vs blueprint FIC exchange). A resource server that authorizes on `appid`/`oid` will see different values depending on which auth type the connection uses.

### Gaps
- None material.

## Q3. Does a hosted agent have a dedicated Entra identity, and what kind?

### Takeaway
Yes: a hosted agent gets a dedicated Entra agent identity (blueprint plus agent identity), created at deploy time, not a user-assigned or system-assigned managed identity. Code reaches it through a token service that imitates the managed identity endpoint. No doc describes bringing your own identity for the agent.

### Cited Findings
- "Every Hosted agent deployed to a Foundry project gets its own dedicated Microsoft Entra ID (agent identity) and dedicated endpoint, both created automatically at deploy time. You don't need to configure managed identities or routing manually." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents)
- "The agent automatically gets an agent blueprint and agent identity." For agent applications (legacy): "The agent application automatically gets an agent blueprint and agent identity. If you configure any explicit role assignments for the Hosted agent's agent identity ... repeat those assignments for the agent application's agent identity." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agent-permissions)
- "For hosted agents, the token service lets your code obtain tokens for the current agent instance's identity by default. The project managed identity isn't available to your hosted-agent code." Each session "runs in its own VM-isolated sandbox, which contains no blueprint credential." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Token service contract (page ms.date 2026-10-28): "The Azure Identity SDKs obtain tokens for the agent identity through ManagedIdentityCredential. Despite its name, this credential accesses the hosted-agent token service; it doesn't give your code access to the project managed identity." Env vars `IDENTITY_ENDPOINT` and `IDENTITY_HEADER`; GET with `resource`, `api-version=2019-08-01`, header `X-IDENTITY-HEADER`, optional `client_id`. "Identity selection accepts only a client ID, not a principal ID, object ID, or Azure resource ID." "Any other client ID: Rejected. The caller can't select an arbitrary identity." Response includes `client_id` of the identity represented by the token. [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agent-token-service)
- Instances: "By default, the token service uses the agent identity of the current instance. The agent identity associated with the agent definition represents the default instance. General hosted agents use only the default instance, so the current and default instance identities are the same. For autopilot agents, the current instance's identity is distinct from the default instance's identity." Autopilot agents (Microsoft 365) can also obtain a "blueprint exchange token" bound to the current instance identity. [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agent-token-service)
- Hosted agents reached by Microsoft 365 channels run OBO when a user token is present; otherwise "the agent authenticates using its own Microsoft Entra ID (agent identity), typically via managed identity, to access downstream services." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents)
- Hosted agents are listed in 31 regions on a GA-style page with no preview banner (ms.date 2026-10-19). [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agents)

### Inferences
- The phrase "typically via managed identity" on the hosted-agents page refers to the token service's managed-identity-shaped endpoint, not to a real Azure managed identity resource. The token service page is explicit that the token is for the agent identity.
- Because `client_id` selection is restricted to the current/default instance (and the blueprint for autopilot), a hosted agent cannot impersonate another agent's identity even if it knows the client ID.

### Gaps
- No doc describes attaching a customer-owned user-assigned managed identity or a customer-created agent identity to a hosted agent. Treat "bring your own agent identity" as unsupported until documented.
- No doc states whether hosted-agent sessions of a general hosted agent ever get distinct identities; the token service page says only autopilot agents have per-instance identities.

## Q4. How does the agent identity get a token for a custom resource (api://news-mcp), and what is in it?

### Takeaway
The blueprint authenticates with its FIC, requests an exchange token naming the child agent identity via `fmi_path`, then the agent identity uses that exchange token as a client assertion in a client-credentials request for the target audience. The resulting token is an app-only token with `idtyp=app`, `appid`/`azp` = agent identity app ID, `oid` = agent identity object ID, `roles` = assigned app roles, plus agent marker claims `xms_act_fct`/`xms_sub_fct` = 11 and `xms_par_app_azp` = blueprint app ID.

### Cited Findings
- Foundry runtime exchange for service-managed tools: (1) "Agent Service presents the blueprint's OAuth credentials to Microsoft Entra ID"; (2) "Microsoft Entra ID validates the blueprint credentials and issues a token for the specific agent identity"; (3) "Agent Service presents the agent identity token back to Microsoft Entra ID and requests a new access token scoped to the audience of the downstream service. The audience is the OAuth resource identifier for the target service"; (4) "Agent Service passes the scoped access token to the MCP server or A2A endpoint. The downstream resource validates the token and checks the agent identity's RBAC role assignments before granting or denying access." "The audience identifies the resource that accepts the token, which isn't necessarily the tool endpoint's URL." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- MCP connection: `azd ai connection create my-mcp-connection --kind remote-tool --target https://<mcp-server-endpoint> --auth-type agentic-identity --audience "<entra-audience>"`. "When the agent invokes the MCP server, Agent Service uses the available agent identity to request an authorization token and passes it to the MCP server." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Protocol (Entra): step 1 `POST /oauth2/v2.0/token` with `client_id=AgentBlueprint&scope=api://AzureADTokenExchange/.default&fmi_path=AgentIdentity&client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer&client_assertion=TUAMI&grant_type=client_credentials`, where "fmi_path: The client ID (app ID) of the agent identity." Step 2 `client_id=AgentIdentity&scope=https://resource.example.com/.default&client_assertion_type=...jwt-bearer&client_assertion={T1}&grant_type=client_credentials`. Step 3: "Microsoft Entra ID validates that T1 (aud) == Agent identity parent app == Agent identity blueprint". "Only a single agent identity blueprint can impersonate an agent identity." [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-autonomous-app-oauth-flow)
- Supported grants: blueprints support `client_credentials`, `jwt-bearer`, `refresh_token`; agent identities support `client_credentials` and `jwt-bearer` (client credential and OBO) and `refresh_token`. "Agents aren't supported for interactive (/authorize) flows". "Public client capabilities aren't available". [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-oauth-protocols)
- Sample autonomous token (v1): `aud`, `iss`, `appid`, `appidacr: "2"`, `idtyp: "app"`, `oid`, `sub`, `tid`, `ver: "1.0"`, `xms_act_fct: "3 9 11"`, `xms_idrel: "7 10"`, `xms_sub_fct: "9 3 11"`, `xms_tnt_fct: "3 9"`, `xms_par_app_azp: "30cf4c22-9985-4ef7-8756-91cc888176bd"`. "In v2 tokens, you see azp instead of appid. They both refer to the application ID of the agent identity." [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-token-claims)
- Claim semantics: `oid` = "Agent ID service principal OID for app-only scenarios"; `idtyp` values `user`, `app`; `xms_idrel` 7 = service principal, 33 = federated managed identity; `xms_act_fct`/`xms_sub_fct`/`xms_tnt_fct` are space-separated integer facets where 11 = AgentIdentity and 13 = AgentIDUser; `xms_par_app_azp` = "parent application of the authorized party ... It isn't recommended to use the parent application ID for authorization decisions, as it would result in widespread access by many agents." Autonomous scenario table: `idtyp=app`, `xms_idrel=7`, `azp/appid` = agent identity app ID, `roles` = "Permissions granted to the agent identity", `oid` = agent identity object ID, `xms_act_fct=11`, `xms_sub_fct=11`, `scp` "Empty or / (unscoped)". [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-token-claims)
- Downstream API validation checklist: signature against `https://login.microsoftonline.com/<tenant>/discovery/v2.0/keys`; issuer `https://sts.windows.net/<tenant>/` or `https://login.microsoftonline.com/<tenant>/v2.0`; audience; and "Agent identity marker: The xms_par_app_azp claim is present in agent identity tokens and absent in standard app-only tokens. This claim identifies the blueprint that created the agent." Sample at github.com/microsoft/entra-agentid-samples (sidecar/weather-api). [Source](https://learn.microsoft.com/en-us/entra/agent-id/how-to-validate-agent-tokens-downstream-api)
- Generic claim definitions: `roles` = "The set of permissions exposed by the application that the requesting application or user has been given permission to call. The client credential flow uses this set of permission in place of user scopes for application tokens." `appid` (v1) / `azp` (v2) "may be used in authorization decisions." `oid` is "The immutable identifier for the requestor ... can be used as a key in database tables." `scp` is "Only included for user tokens." [Source](https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference)
- Agent identity has "object ID and the app ID, which always have the same value and can be reliably used for authentication and authorization decisions." Agent identities "can only be issued tokens in the Microsoft Entra tenant where they're created." [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-identities)
- Sidecar flow naming: T1 = blueprint client-credentials token, TR = agent token for the downstream API (`idtyp=app`); OBO adds Tc (user token) and uses `assertion=Tc`, `client_assertion=T1`, `grant_type=jwt-bearer`. [Source](https://learn.microsoft.com/en-us/entra/agent-id/sidecar-local-development)
- For managed OAuth (not agent identity) Foundry blocks Microsoft-audience tokens going to custom servers: "Agent Service restricts tokens scoped to a known Microsoft audience from being sent to custom or third-party MCP servers ... Your custom MCP server must be registered with an audience that you control". [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)

### Inferences
- For `--audience "api://news-mcp"` the news MCP server must be an Entra app registration (or service principal) whose Application ID URI is `api://news-mcp`; Foundry will request `api://news-mcp/.default` and the v1 token's `aud` will be either the URI or the app's client ID depending on the registration (per the generic `aud` rule).
- The Foundry doc's phrase "checks the agent identity's RBAC role assignments" describes the Azure-resource case; for a custom API the equivalent check is on `roles` (app roles) or a server-side allowlist keyed by `oid`/`appid`.
- There is no sponsor, owner, or Foundry project claim in the token. Sponsor/owner live on the directory object and are visible in sign-in logs, not in the JWT.

### Gaps
- No doc gives a worked example of a Foundry-issued agent token for a custom `api://` audience; the claim set above is from the Entra agent-token reference plus the generic claims reference.
- No doc states whether Foundry requests v1 or v2 tokens for MCP connections (`appid` vs `azp`). A resource server should accept both.

## Q5. Can app roles be assigned to an agent identity's service principal like for a managed identity?

### Takeaway
Yes. The Graph `agentIdentity` resource exposes `appRoleAssignments`, and the Entra enterprise-apps doc gives the exact Graph call: `POST /servicePrincipals/{resourceSpId}/appRoleAssignedTo` with `principalId` = agent identity object id. The role must have `allowedMemberTypes` containing `Application`. The resulting `roles` claim appears in the agent's app-only token.

### Cited Findings
- "For applications that recognize role claims on service principals, you can assign an agent's service principal or agent identity to an application's app role. When you assign to app roles, this results in application permissions." "First, confirm that app role in the application's manifest has an allowedMemberTypes of Application ... Then, you can assign an app role to an agent identity or service principal, by using the Microsoft Entra admin center, Microsoft Graph or Microsoft Graph PowerShell." PowerShell example: body `{ principalId = $PrincipalId; resourceId = $ResourceId; appRoleId = $AppRoleId }` posted to `https://graph.microsoft.com/v1.0/servicePrincipals/$ResourceId/appRoleAssignedTo`, where `$PrincipalId` is "the id of the agent identity" and `$ResourceId` is "the id of the target application service principal". [Source](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/assign-agent-identities-to-applications)
- Graph v1.0 `agentIdentity` methods include "List appRoleAssignments: Get the app roles that this agent identity is assigned", "Create appRoleAssignment" (serviceprincipal-post-approleassignments), "Delete appRoleAssignment", and "List appRoleAssignedTo: Get the users, groups, and agent identities assigned app roles for this agent identity." [Source](https://learn.microsoft.com/en-us/graph/api/resources/agentidentity)
- Declaring roles: "App roles can also be assigned to the service principal for another application, or to the service principal for a managed identity." Role settings: Allowed member types `Users/Groups` or `Applications` ("When available to applications, app roles appear as application permissions"), `Value` "Specifies the value of the roles claim that the application should expect in the token ... can't contain spaces." "When the app role is set to Enabled, any users, applications, or groups who are assigned have the app role included in their tokens." Limit: "default limit of 700 permission definitions per application or service principal, shared with exposed delegated permission scopes." [Source](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps)
- Group indirection does not work for service principals: "Currently, if you add a service principal to a group, and then assign an app role to that group, Microsoft Entra ID doesn't add the roles claim to tokens it issues." [Source](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps)
- Agent service principals "support both application permissions (for autonomous operations) and delegated permissions ... Permissions can be assigned directly to an agent identity or inherited from the blueprint. When InheritDelegatedPermissions is enabled, agent identities inherit delegated permissions from the blueprint". [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-service-principals)
- Inheritable permissions are documented for delegated scopes: "Inheritable permissions let agent identities automatically inherit OAuth 2.0 delegated permission scopes from their parent blueprint." Limits: "Maximum of 10 resource apps per blueprint. For enumerated scopes, maximum of 40 scopes per resource app." Configured via `inheritablePermissions` on the `agentIdentityBlueprint` application resource. [Source](https://learn.microsoft.com/en-us/entra/agent-id/manage-agent-identities-admin)
- Foundry's own list of authorization mechanisms includes "Application permissions or app roles: An API grants the identity application-level permissions for access without a signed-in user, where supported." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Blocked high-privilege grants apply to Graph permissions, not to your own app roles: `Application.ReadWrite.All`, `RoleManagement.ReadWrite.All`, `User.ReadWrite.All`, `Directory.AccessAsUser.All` "can't be granted through Microsoft Graph or the Microsoft Entra admin center" for agents. [Source](https://learn.microsoft.com/en-us/entra/agent-id/faq)
- The admin consent workflow "doesn't work correctly for permissions requested by agent identities. Users should contact their Microsoft Entra tenant admin to request that permissions be granted directly to the agent identity." [Source](https://learn.microsoft.com/en-us/entra/agent-id/faq)
- Entra admin center shows, per agent identity, "The agent's access via this agent identity's granted permissions and Microsoft Entra roles" (Entra ID > Agents > Agent identities > select agent > View Access). [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-lists)

### Inferences
- `az cli` has no agent-identity-specific command in the docs fetched; `az rest --method POST --url "https://graph.microsoft.com/v1.0/servicePrincipals/{resourceSpId}/appRoleAssignedTo" --body '{...}'` is the equivalent of the PowerShell example (a plain Graph call), and `az ad app permission` is for app registrations and so does not apply to an agent identity that has no application object of its own.
- The admin center path in howto-add-app-roles (App registrations > API permissions > My APIs) operates on an app registration's `requiredResourceAccess`. The agent identity has no app registration of its own (its blueprint does), so direct Graph assignment on the agent identity SP is the reliable path for per-agent roles. Since Foundry gives each agent its own blueprint, blueprint-level inheritance would not differentiate agents anyway.
- A single agent identity can hold multiple app roles on the same resource; the `roles` array lists all of them.

### Gaps
- No doc states whether app roles (application permissions) on a custom API can be inherited from a blueprint to its agent identities; inheritance docs only mention delegated scopes. For this scenario it does not matter because the roles are assigned per agent identity.
- No doc shows an admin-center UI for adding an app role assignment to an agent identity object (the "View Access" pane shows granted permissions; whether it can add them is not documented).

## Q6. Can an agent identity be put in a security group, and will tokens carry a groups claim?

### Takeaway
Group membership is supported (Graph `memberOf`/`transitiveMemberOf`, and access packages can grant security group membership to agent identities), with limits (no role-assignable groups, no administrative units). But Microsoft's optional-claims doc states that group claims are only emitted for user principals, and the app-roles doc says a service principal in a group that holds an app role does not get a `roles` claim. For a third-party MCP server, groups are therefore not a reliable authorization signal in the token.

### Cited Findings
- `agentIdentity` Graph methods: "List direct memberships: Get the groups that this agent identity is a direct member of" and "List transitive memberships". [Source](https://learn.microsoft.com/en-us/graph/api/resources/agentidentity)
- Access packages: "With access packages, you're able to assign agent identities access to the following resources: Security Group memberships; OAuth API permissions ... delegated and application permissions for Microsoft Graph and applications; Microsoft Entra roles". Policy option: "For users, service principals, and agent identities in your directory" then "All agents". [Source](https://learn.microsoft.com/en-us/entra/id-governance/agent-id-governance-overview)
- Authorization overview lists "group memberships" among the ways to grant an agent access. [Source](https://learn.microsoft.com/en-us/entra/agent-id/authorization-agent-id)
- Restrictions: "Agent identities can't be members of role-assignable groups." "Agent identities, agent identity blueprints, and agent identity blueprint principals can't be added to administrative units." An agent's user account "can be added to Microsoft Entra groups, including dynamic groups". [Source](https://learn.microsoft.com/en-us/entra/agent-id/faq)
- Groups claim for non-user principals: "Group optional claims are only emitted in the JWT for user principals. Service principals aren't included in group optional claims emitted in the JWT." (section "Configure groups optional claims", page ms.date 2026-08-11). [Source](https://learn.microsoft.com/en-us/entra/identity-platform/optional-claims)
- Group-to-app-role indirection: "if you add a service principal to a group, and then assign an app role to that group, Microsoft Entra ID doesn't add the roles claim to tokens it issues." Microsoft's comparison: app roles are "Provided in the roles claim", groups "Provided in groups claim"; app roles are "specific to an application ... move with the application", groups "aren't specific to an app, but to a Microsoft Entra tenant." [Source](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps)
- Group claim mechanics for the record: `groupMembershipClaims` values `All`, `SecurityGroup`, `DirectoryRole`, `ApplicationGroup`, `None`; JWT overage at 200 groups replaces the claim with a Graph link; Microsoft recommends app roles over groups for new apps. [Source](https://learn.microsoft.com/en-us/entra/identity/hybrid/connect/how-to-connect-fed-group-claims); [Source](https://learn.microsoft.com/en-us/entra/identity-platform/access-token-claims-reference)
- Conditional Access cannot scope agent users by group: "Scoping a Conditional Access policy to include or exclude agent's user account based on their group membership" is listed as not supported. [Source](https://learn.microsoft.com/en-us/entra/identity/conditional-access/agent-id)
- Azure RBAC does evaluate group membership for service principals: "Role assignments are transitive for groups" and ARM retrieves "all the role assignments ... that apply to the resource" during evaluation. [Source](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview)

### Inferences
- The optional-claims sentence sits inside the section on customizing group claim formats; it is the only Microsoft statement found about group claims for service principals and it says they are not emitted. Combined with the app-roles note, a third-party server should not expect to see `groups` or group-derived `roles` in an agent identity's app-only token. If you want group-based entitlement for an agent, resolve it server-side via Graph `transitiveMemberOf` on the `oid`, which costs a Graph call and a Graph permission for the server.
- Groups remain useful for Azure RBAC (ARM evaluates them itself) and for access-package-driven lifecycle, but not for a token claim read by a non-Microsoft API.

### Gaps
- I found no Agent ID doc that explicitly tests or states groups-claim behavior for agent identity tokens; the evidence is the generic service-principal statement above. Verify empirically before relying on either outcome.

## Q7. Can Azure RBAC roles be assigned to an agent identity, and what does that mean for a third-party MCP server?

### Takeaway
Azure RBAC role assignments (built-in or custom) can be made to an agent identity, exactly as for a service principal; blueprints cannot be assigned Azure roles. Azure RBAC is evaluated by Azure Resource Manager at ARM scopes (management group, subscription, resource group, resource), so a third-party MCP server that is not an Azure RBAC-integrated data plane cannot consume those assignments from the token; it would have to query Azure itself.

### Cited Findings
- "Agent identities can be assigned Azure RBAC roles and Microsoft Entra built-in roles, the same as standard service principals. Agent identity blueprints can't be assigned Azure RBAC roles." [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-service-principals)
- "If an agent needs to access Azure resources: Assign Azure roles for those specific resources. For example, to let an agent read an Azure Key Vault, give its identity a Key Vault Reader role on that vault." [Source](https://learn.microsoft.com/en-us/entra/agent-id/authorization-agent-id)
- Foundry: "For Azure RBAC assignment procedures, use the object ID of the agent identity used for the tool call as the assignee." Mechanisms table distinguishes "Azure RBAC" (role assignments at an Azure resource scope), "Service-specific data-plane roles" (for example Cosmos DB, "These aren't Azure RBAC role assignments"), "Application permissions or app roles", and "Resource-specific authorization policies". "Authentication identifies the agent to the downstream service. The service's authorization model determines what that identity can do." [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)
- Azure RBAC definition and scope: "Azure RBAC is an authorization system built on Azure Resource Manager that provides fine-grained access management to Azure resources." "In Azure, you can specify a scope at four levels: management group, subscription, resource group, or resource." Evaluation: "A user (or service principal) acquires a token for Azure Resource Manager ... Azure Resource Manager retrieves all the role assignments and deny assignments that apply to the resource ... These steps apply to Azure Resource Manager or data plane services integrated with Azure RBAC." Role assignment = security principal + role definition + scope. [Source](https://learn.microsoft.com/en-us/azure/role-based-access-control/overview)
- Checking access is documented as a portal feature ("Check access" on Access control (IAM), which lists assignments "at this scope and inherited to this scope"); programmatic listing is via the Role Assignments REST API with filters such as `assignedTo('{objectId}')`. [Source](https://learn.microsoft.com/en-us/azure/role-based-access-control/check-access); [Source](https://learn.microsoft.com/en-us/azure/role-based-access-control/role-assignments-list-rest)
- Hosted agents: "The agent identity can access model inferencing through the project endpoint and session storage by default. For external resources (for example, your own Azure Storage), assign RBAC roles manually to the agent's Microsoft Entra ID." Custom role example with `az role definition create` and `az role assignment create --assignee <object-id> --role ... --scope ...`. [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/hosted-agent-permissions)

### Inferences
- An Azure role assignment produces no claim in a token for `api://news-mcp`; `roles` carries app roles, not Azure roles. A third-party server could only use Azure RBAC by holding its own Azure credential and calling the Role Assignments API (or by being an RBAC-integrated Azure data plane such as Storage or Cosmos DB), which is heavier than app roles and ties the server to an Azure subscription.
- Azure RBAC is the right mechanism when the MCP server fronts an Azure resource that natively checks RBAC (for example an MCP server that passes the agent token straight to Azure Storage). For a news API with its own entitlement model, app roles or a server-side allowlist on `oid`/`appid` are the fit.

### Gaps
- I did not find a current Learn reference page for a `Microsoft.Authorization/checkAccess` REST operation (searches returned only the portal quickstart and role-assignment list/create APIs). Programmatic evaluation should use the Role Assignments list API with `assignedTo(...)` plus the caller's own scope logic, or Azure SDK equivalents.

## Scenario: two Foundry agents, one news MCP server, "News.All" vs "News.Sports"

### Takeaway
Register the news MCP server as an Entra app with Application ID URI `api://news-mcp` and two app roles (`News.All`, `News.Sports`, allowedMemberTypes Application). Create the two agents (each gets its own agent identity), read each `instance_identity.principal_id`, assign one app role to each via Graph `appRoleAssignedTo`, and configure each agent's MCP connection with `--auth-type agentic-identity --audience api://news-mcp`. The server validates signature, issuer, audience, confirms `idtyp=app` and (optionally) `xms_par_app_azp` presence, then reads `roles` to decide; `oid`/`appid` identify which agent is calling for logging or an allowlist.

### Cited Findings
- Declare roles with Allowed member types = Applications and a space-free `Value`; the value "should exactly match the string referenced in the application's code." [Source](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps)
- Assign per agent: `POST https://graph.microsoft.com/v1.0/servicePrincipals/{newsMcpSpObjectId}/appRoleAssignedTo` with `{ principalId: <agent identity object id>, resourceId: <newsMcpSpObjectId>, appRoleId: <role id> }`. [Source](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/assign-agent-identities-to-applications)
- Read each agent's identity: `GET {project_endpoint}/agents/{agent_name}?api-version=v1` returns `instance_identity.principal_id` and `.client_id`. [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/configure-agent)
- Connection: `azd ai connection create <name> --kind remote-tool --target https://<mcp-server-endpoint> --auth-type agentic-identity --audience "<entra-audience>"`; "ideal when you have multiple agents that need different levels of access to the same MCP server." Agent tool definition uses `project_connection_id` to bind the connection. [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/how-to/mcp-authentication)
- Token the server will see (autonomous scenario): `idtyp=app`, `xms_idrel=7`, `azp`/`appid` = agent identity app ID, `roles` = permissions granted to the agent identity, `oid` = agent identity object ID, `xms_act_fct=11`, `xms_sub_fct=11`, `xms_par_app_azp` = blueprint app ID; "It isn't recommended to use the parent application ID for authorization decisions". [Source](https://learn.microsoft.com/en-us/entra/agent-id/agent-token-claims)
- Validation checks: signature (JWKS), issuer, audience, agent marker `xms_par_app_azp`. [Source](https://learn.microsoft.com/en-us/entra/agent-id/how-to-validate-agent-tokens-downstream-api)
- Foundry note on what the agent identity gives you: "Per-agent identities let you scope permissions and audit activity to individual agents." Entra sign-in logs "show which agent identity obtained a token for which resource". [Source](https://learn.microsoft.com/en-us/azure/foundry/agents/concepts/agent-identity)

### Inferences
- Step order matters: the app role assignment needs the agent identity's object ID, which exists only after the agent is created, so create agents first, then assign roles, then test. Foundry notes the same ordering constraint for Azure RBAC ("it can't be created until after the agent is created").
- If a gateway (for example APIM) fronts the MCP server, it can enforce the same decision with a JWT validation policy that requires `roles` to contain `News.All` or `News.Sports`, and can map `oid` to a tenant-side entitlement table; no Azure RBAC call is needed.
- A pure server-side allowlist keyed on `oid` (no app roles) also works and needs no Entra configuration on the resource app beyond the registration, but it moves entitlement data out of the directory and loses the admin-center "View Access" audit view.
- Migrating a legacy agent (shared project identity) to the new model mints a new identity, so role assignments must be re-created; Foundry says "existing role assignments don't transfer."

### Gaps
- No Microsoft end-to-end sample shows a Foundry agent calling a custom-audience MCP server with app roles; the pieces above are assembled from separate docs. Validate the exact `aud` format (URI vs client ID) and v1/v2 claim names (`appid` vs `azp`) against a real token before hardcoding.
